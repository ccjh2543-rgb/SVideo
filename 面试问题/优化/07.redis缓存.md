# 一、你已经有的（全部保留，都是刚需）
## 1. Token 登录令牌
- 结构：String
- Key：`user:token:{tokenStr}`
- 存：用户ID、登录信息
- 过期：固定过期（登录有效期）
- 作用：鉴权、免登录

## 2. 接口限流缓存
- 结构：String / Hash
- Key：`limit:api:{userId}:{apiPath}`
- 存：请求次数、时间窗口
- 过期：按时间窗口自动过期
- 作用：防刷接口、防暴力请求

## 3. 非冷视频 基础展示元数据（核心）
- 结构：Hash
- Key：`video:meta:{videoId}`
- 存：**前端列表必用字段**
  标题、封面url、播放url、作者ID、创建时间
- 规则：
  只缓存**非冷视频**（7天内 / 热度达标）；冷门视频**绝不进缓存**
  懒加载写入，靠 Redis LRU 自动淘汰旧热视频
- 不做频繁删缓存，视频信息变更时**主动删一次**即可

## 4. 全网热门榜 ZSet
- 结构：ZSet
- Key：`rank:hot:minute:{分钟粒度}`
- 存：videoId，score=热度值
- 只存ID，不存详情，详情走上面 `video:meta` 批量拿

## 5. 热门榜合并快照
- 结构：ZSet / Hash
- 作用：聚合多时段热榜，给首页热门页用，避免实时计算

## 6. 关注流 Inbox（小博主推送到粉丝）
- 结构：List
- Key：`feed:inbox:{userId}`
- 存：视频ID
- 规则：**LPUSH + LTRIM 固定长度**（只保留50~100条），防大Key

## 7. 大博主 Outbox
- 结构：List
- Key：`feed:outbox:{authorId}`
- 存：自己最新几条视频ID
- 规则：同样 LTRIM 截断，只存最新5~10条

# 二、你**现在缺失、必须补上**的3类（少了架构跑不通）
## 8. 点赞相关两套（必补，解决你之前缓存不一致痛点）
### 8.1 视频点赞计数器（Redis做主库，异步落MySQL）
- 结构：String
- Key：`video:like:count:{videoId}`
- 操作：`INCR / DECR` 原子增减
- 规则：
  1. 点赞/取消 只操作Redis，主流程不碰DB、不删缓存
  2. 发 MQ 异步更新 MySQL likes_count
  3. 前端查点赞数**只读Redis**

### 8.2 用户点赞状态集合（去重、秒显已点赞）
- 结构：Set
- Key：`user:like:set:{userId}`
- 存：该用户点过赞的所有 videoId
- 作用：进入视频页瞬间判断「是否已点赞」，不用查库、防重复点赞

## 9. 关注关系缓存（必补）
- 结构：String / Hash
- Key：`follow:rel:{userId}:{authorId}`
- 存：0/1 是否关注
- 作用：刷视频、进博主主页，毫秒级判关注状态，不用查库
- 维护：关注/取关时**直接写/删缓存**

## 10. 博主元数据缓存（必补，你之前设计的那张表）
- 结构：Hash
- Key：`author:info:{authorId}`
- 存：粉丝数、最后发布时间、是否大V、作品数
- 作用：
  1. 快速区分大小博主（走Inbox还是Outbox）
  2. 过滤长期不发视频的沉默博主
  3. 客户端比对时间，做关注更新小红点

# 三、可选（小项目可以先不做，后期再加）
不用现在搞，避免混乱：
1. 布隆过滤器：防缓存穿透
2. 空值缓存：缓存已删除视频ID，防止一直穿透打库
3. 用户个人主页最近视频List
4. 评论数、收藏数计数器（和点赞一套逻辑）

---

# 四、明确：**绝对不要放进 Redis 的东西**（避免越做越乱、内存爆炸）
1. 全局最新视频大List/ZSet（翻页漂移、无意义）
2. 所有冷门、半年前的老旧视频
3. 视频长简介、审核字段、后台冗余字段
4. 无脑把所有刷到的视频都塞缓存（靠「热度+时间门槛」过滤）

---

# 五、最终定型：你项目只需要这 **10类 Redis 缓存**
1. Token 登录
2. 接口限流
3. 非冷视频基础元数据
4. 热门榜 ZSet
5. 热门榜合并快照
6. 用户 Inbox 关注流
7. 大博主 Outbox
8. 视频点赞计数器 + 用户点赞Set
9. 关注关系状态缓存
10. 博主元数据缓存

**就这10类，不多不少，刚好支撑你整个短视频业务**，架构闭环、没有冗余、不会内存爆炸、缓存一致性也好解决。
