# 一、4 个评论缓存设计（完全对标你的点赞/视频架构）
## 1. 视频评论总数计数器（必做）
**对标：视频点赞计数器**
- 结构：`String`
- Key：`video:comment:count:{videoId}`
- 作用：记录视频总评论数，列表页快速展示
- 操作：发布评论 `INCR`，删除评论 `DECR`（Redis 原子操作）
- 持久化：发布/删除评论 → 发 MQ 异步更新 MySQL
- 读取：**只读 Redis**，不查库

## 2. 视频主评论列表缓存（必做）
**对标：Inbox/Outbox 列表**
- 结构：`List`
- Key：`video:comment:list:{videoId}`
- 存：**最新的50条主评论ID**（只存ID，不存详情）
- 规则：
  - 发布新评论：`LPUSH` 头部插入
  - `LTRIM 0 49` 固定长度，**绝对不膨胀**
  - 只缓存最新热评论，冷数据不进缓存
- 读取：`LRANGE 0 9` 拿前10条，翻页走 MySQL

## 3. 单条评论点赞计数器（必做）
**对标：视频点赞计数器**
- 结构：`String`
- Key：`comment:like:count:{commentId}`
- 作用：单条评论的点赞数
- 操作：`INCR/DECR` 原子增减
- 持久化：异步 MQ 落库 MySQL

## 4. 用户评论点赞状态集合（必做）
**对标：用户视频点赞集合**
- 结构：`Set`
- Key：`user:comment:like:{userId}`
- 存：用户点赞过的 **评论ID**
- 作用：判断是否已点赞，防重复点赞，不查库

# 三、完整业务流程（和你点赞逻辑完全一致，零学习成本）
## 1. 发布评论
1. Redis 评论总数 `INCR`
2. Redis 评论列表 `LPUSH` + `LTRIM`
3. 发送 MQ 异步写入 MySQL
4. 直接返回成功

## 2. 加载视频评论列表

3. 组装返回，**全程不查库**

## 3. 评论点赞
1. Redis 评论点赞数 `INCR`
2. Redis 用户点赞集合 `SADD`
3. 发送 MQ 异步更新 MySQL
4. 无删缓存、无同步写库

# 四、为什么这么设计？（完全贴合你的架构）
1. **动态计数独立存储**
   评论数、点赞数 → 独立 String，原子操作，不和静态数据耦合
2. **列表固定长度**
   用 `LTRIM` 裁剪，杜绝大Key，和 Inbox/Outbox 完全一样
3. **只缓存热数据**
   只存前50条最新评论，翻页走数据库，和视频流逻辑一致
4. **异步持久化**
   所有写操作不碰 MySQL，和点赞架构统一
5. **无缓存不一致**
   读写全走 Redis，不用删缓存
