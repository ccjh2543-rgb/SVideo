# 先给你吃两颗定心丸
## 1. 点赞表、评论表这种亿级大数据表，放数据库**完全不慢**
你担心的「查询效果差」，**是不会写索引/不会查导致的，不是数据库不行**。
数据库的定位就是：**存全量、持久化、冷数据**，只要设计正确，单表千万~亿数据，毫秒级查询。

## 2. Redis绝对不会占太多内存
因为我们**只存热数据、极小数据、固定长度数据**，99%的冷数据、全量数据，一律丢给数据库，Redis只扛首页/热流量。

# 一、核心原则：数据库 和 Redis 彻底分工（划清红线，永不混乱）
## 🔥 数据库（MySQL）：只做 3 件事
1. **存全量原始数据**（所有用户、视频、评论、点赞、关注记录，永久保存）
2. **存冷数据**（历史视频、旧评论、用户很久以前的点赞）
3. **兜底查询**（翻页、冷门数据、后台统计）

> 大数据量表（点赞/评论/关注）：**必须放数据库**，这是它们的归宿，Redis绝不存全量！

## 🚀 Redis：只做 3 件事
1. **高频计数**（点赞数、评论数、播放数、粉丝数）
2. **高频状态**（是否点赞、是否关注、是否收藏）
3. **热数据列表**（首页关注流、热门视频、前50条评论）

> Redis **绝不存全量数据**，所有列表固定长度、所有数据只留热的，内存永远可控。

# 二、解决你最大的焦虑：大数据量表（点赞/评论）放数据库，真的不慢！
我拿**用户点赞表、评论表**举例，告诉你怎么优化到毫秒级：

## 1. 用户点赞表（`user_like`）：亿级数据也快
```sql
CREATE TABLE user_like (
  id BIGINT PRIMARY KEY,
  user_id BIGINT,    // 用户ID
  video_id BIGINT,   // 视频ID
  create_time DATETIME
);
// 核心：加两个联合索引（查询全靠它）
INDEX idx_user_video (user_id, video_id),  // 判断「是否点赞」
INDEX idx_user_time (user_id, create_time) // 查询「我的点赞列表」
```
### 查询场景：
- 判断是否点赞：`SELECT 1 FROM user_like WHERE user_id=? AND video_id=?`
  → **索引命中，0.1ms返回**
- 查我的点赞：`SELECT video_id FROM user_like WHERE user_id=? ORDER BY create_time DESC LIMIT 10`
  → **索引命中，毫秒级**

## 2. 视频评论表（`video_comment`）：千万数据无压力
```sql
CREATE TABLE video_comment (
  id BIGINT PRIMARY KEY,
  video_id BIGINT,
  user_id BIGINT,
  content VARCHAR(255),
  create_time DATETIME,
  likes INT
);
// 索引
INDEX idx_video_time (video_id, create_time), // 最新评论
INDEX idx_video_likes (video_id, likes)       // 最热评论
```
### 排序功能（最新/最热）：
直接靠数据库索引排序，**不用Redis，不用复杂计算**，短视频99%的列表排序，数据库索引完全扛得住。

# 三、解决第二个焦虑：Redis 为什么不会内存爆炸？
因为我们**严格遵守3条铁律**，只存最小、最热的数据：
1. **只存ID，不存完整对象**（关注流/评论流/热榜，全是视频ID/评论ID）
2. **所有列表固定长度，自动裁剪**（Inbox/Outbox/评论列表，最多存50~100条）
3. **只缓存热数据**（7天内/热度达标视频，冷门视频绝不进Redis）

### 算笔账：100万用户，Redis内存占用极低
- 1个ID占8字节
- 1个用户Inbox存100条ID → 800字节
- 100万用户 → **800MB内存**
- 加上所有计数、状态、热榜 → **总内存4~8G完全够用**

# 四、所有复杂交互 + 琐碎功能，统一简化为 3 套模板
你不用为「关注、点赞、评论、收藏、评论点赞」 each 设计一套逻辑，**全部复用3套模板**，瞬间简化90%复杂度：

## 模板1：所有计数（点赞/评论/收藏/粉丝/播放）
- Redis：String 原子自增
- DB：异步持久化
- 读取：只读Redis

## 模板2：所有状态（是否点赞/是否关注/是否收藏）
- Redis：Set 存ID
- DB：异步落库
- 读取：只读Redis

## 模板3：所有列表（视频/评论/关注）
- Redis：List 存热数据（前50条）
- DB：存全量，负责翻页/冷数据
- 排序：最新/最热 → 靠数据库索引

# 五、你说的「琐碎功能」，极简实现（不加新缓存）
### 1. 评论里显示「你关注的人」
- 查评论时，批量拿评论用户ID
- 查**关注关系缓存**（你已有的`follow:rel`）
- 内存标记一下即可，**不加新缓存**

### 2. 评论按最新/最热排序
- 最新：数据库`video_id + create_time`索引
- 最热：数据库`video_id + likes`索引
- **不用Redis计算，直接查库**

### 3. 博主视频按最新/最热排序
- 最新：`author_id + create_time`索引
- 最热：`author_id + likes`索引
- 热数据缓存Redis List，冷数据查库
