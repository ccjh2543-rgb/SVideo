## 一、先告诉你：为什么「每次点赞删缓存」性能极差？
1. **同步阻塞**：点赞接口要等Redis删缓存完成，高并发下直接拖慢接口
2. **无效操作**：热门视频1秒1000赞，就要删1000次缓存，纯浪费
3. **缓存抖动**：删完缓存，下一次请求又要回源查库，数据库压力反弹
4. **数据不一致**：删缓存和DB更新时序错乱，会出现脏数据

**这是反模式，绝对不能用！**

## 二、短视频点赞 工业级标准方案（最优解）
### 核心设计
1. **点赞数 存在 Redis String**（`video:like:{视频ID}`）
2. **点赞/取消：直接 Redis 原子自增/自减**（O(1) 性能天花板）
3. **数据库更新：扔 RabbitMQ 异步执行**（不和主流程绑定）
4. **读取点赞数：只读 Redis**（永远不查库）
5. **无删缓存、无同步写库、无不一致**

### 完整流程（完美解决你的问题）
#### 1. 用户点赞 / 取消点赞（主流程，毫秒级）
```go
// 1. Redis 原子自增/自减（核心！不阻塞、高性能）
if 点赞 {
    redis.Incr("video:like:" + videoID)  // +1
} else {
    redis.Decr("video:like:" + videoID)  // -1
}

// 2. 发送MQ消息，异步更新数据库（主流程直接返回，不等待）
rabbitmq.Publish(LikeMessage{
    videoID: videoID,
    isLike:  isLike,
})

// 3. 直接返回成功！结束
```

#### 2. MQ消费者 异步更新DB（后台慢慢跑，不影响用户）
```go
// 消费者逻辑
func consumeLikeMsg(msg LikeMessage) {
    // 数据库原子更新（只做持久化，不影响性能）
    if msg.isLike {
        db.Model(&Video{}).Where("id=?", msg.videoID).
            UpdateColumn("likes_count", gorm.Expr("likes_count + 1"))
    } else {
        db.Model(&Video{}).Where("id=?", msg.videoID).
            UpdateColumn("likes_count", gorm.Expr("likes_count - 1"))
    }
}
```

#### 3. 前端获取点赞数（只读Redis）
```go
// 永远读缓存，不查库
likes := redis.Get("video:like:" + videoID)
```

## 三、这个方案为什么完美？
### 1. **性能极致**
- Redis 自增是**单线程原子操作**，1秒能抗**10万+点赞**
- 主流程**无数据库操作、无删缓存**，接口延迟<1ms

### 2. **无缓存不一致**
- 读写都走 Redis，**根本不需要删缓存**
- 数据天然一致，没有脏数据

### 3. **数据库零压力**
- DB 只做异步持久化，MQ削峰，哪怕瞬间万赞，DB也稳稳的

### 4. **最终一致性**
- 点赞数允许**短暂的DB和Redis不一致**（短视频场景完全接受）
- 异步消费最终会同步，定时任务还能兜底校对
