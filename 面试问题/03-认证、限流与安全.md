## 问题 1：讲一下你的 JWT 认证流程，为什么说它是"双层验证"？

⭐⭐ **难度**：进阶  
**考察点**：JWT 原理、Token 管理、安全设计

### 问题
> "很多项目只用 JWT 自带的签名验证就够了，你们的项目为什么还要在数据库里存一份 Token 做比对？说一下完整认证流程。"

### 参考答案

**典型的 JWT 问题**：
JWT 签发后，服务器无法主动让它失效。用户修改密码后，旧的 JWT 在过期前依然有效。

**你的项目的双层验证机制**：

```
第一层：JWT 签名验证（auth/jwt.go）
        ↓ 解析 HS256 签名，提取 Claims
        ↓ 验证签名有效 → 通过
        ↓ 签名无效 → 返回 401
        
第二层：Token 有效性比对（middleware/jwt/jwt.go）
        ↓ 从 Redis/DB 查询该用户当前的有效 Token
        ↓ 和 JWT 中的 token 字段比对
        ↓ 一致 → 放行
        ↓ 不一致 → 返回 401（Token 已被覆盖/踢下线）
```

**完整代码流程**：

```go
// 第一层：JWT 签名验证
func ParseToken(tokenString string) (*Claims, error) {
    token, err := jwt.ParseWithClaims(tokenString, &Claims{}, func(token *jwt.Token) (interface{}, error) {
        // 验证签名算法
        return jwtSecret(), nil
    })
    // 提取用户信息
    claims := token.Claims.(*Claims)
    return claims, nil
}

// 第二层：Token 有效性验证
func JWTAuth(repo, cache) gin.HandlerFunc {
    return func(c *gin.Context) {
        // 1. JWT 签名验证
        claims, err := auth.ParseToken(tokenString)
        
        // 2. 从 Redis（优先）或 DB 获取当前有效 Token
        storedToken := getStoredToken(claims.AccountID)
        
        // 3. 比对
        if tokenString != storedToken {
            c.AbortWithStatus(401)
            return
        }
        c.Next()
    }
}
```

**什么时候 Token 会失效**：

| 触发操作 | 发生什么 | 效果 |
|---------|---------|------|
| 用户登录 | 生成新 Token，覆盖旧 Token | 旧设备被踢下线 |
| 用户修改密码 | 生成新 Token，覆盖旧 Token | 所有设备需要重新登录 |
| 用户登出 | Token 置空 | 当前 Token 立即失效 |

### 加分点
- 能提到 Redis 缓存 Token 的超时和降级：50ms 超时保护，Redis 不可用时降级到 DB
- 能解释为什么 JWT 本身无法"踢下线"：JWT 是无状态的，服务器没有保存签发记录，无法主动让 Token 失效
- 能对比其他 Token 方案：Session（服务端有状态，适合传统 Web）、OAuth2.0（适合第三方授权）

## 问题 2：JWT 无状态认证和有状态的 Session 认证，你的项目为什么选 JWT？

⭐⭐ **难度**：进阶  
**考察点**：认证方案选型、无状态 vs 有状态

### 问题
> "你的项目用 JWT 做认证，但你又把 Token 存在了数据库里，这不就变成有状态了吗？为什么不直接用 Session？"

### 参考答案

这是一个非常好的问题。你的项目实际上是 **混合模式**：JWT 做身份证明，DB/Redis 做 Token 状态管理。

**JWT 与 Session 的对比**：

| 维度 | Session | JWT（纯无状态） | 你的方案（混合） |
|------|---------|----------------|----------------|
| 服务器状态 | 有状态（存 Session） | 无状态 | 弱状态（只存 Token，不存 Session） |
| 存储位置 | 服务端内存/Redis | 客户端（Cookie/LocalStorage） | 客户端 + Redis/DB |
| 踢下线能力 | ✅ 天然支持 | ❌ 做不到 | ✅ 覆盖 Token 即可 |
| 跨服务共享 | ❌ 需要共享 Session 存储 | ✅ 直接验证签名 | ✅ 共享 Redis 即可 |
| 安全性 | ✅ 非对称加密 | ⚠️ Token 泄露后无法撤销 | ✅ 泄露后覆盖 Token |

**为什么这样设计**：

1. **不需要 Session 存储**：Session 要存大量的会话数据（购物车、登录状态等），而你的项目只需要存一个 Token 字符串
2. **减轻 Redis 压力**：不需要每次请求都去 Redis 拉取完整 Session，JWT 本身已经包含了用户身份信息
3. **兼容微服务**：JWT 签名验证不需要访问共享存储，其他微服务可以直接验证用户身份
4. **主动失效能力**：Redis/DB 中存 Token 的唯一目的就是支持"踢下线"

**你的项目 Token 的存储设计**：

```go
// 登录时：
// 1. 生成 Token
token, _ := auth.GenerateToken(accountID, username)

// 2. 存到 DB（必选，兜底用）
account.Token = token
db.Save(account)

// 3. 存到 Redis（可选，加速用，50ms 超时）
cache.SetBytes(ctx, "token:"+accountID, token, 24h)

// 验证时：
// 1. 优先查 Redis
storedToken, err := cache.GetBytes(ctx, "token:"+accountID)
if err != nil {
    // 2. Redis 不可用 → 查 DB
    account := repo.FindByID(accountID)
    storedToken = account.Token
}
```

### 加分点
- 能提到 Session 的缺点：多实例部署时需要共享 Session 存储（如 Redis），否则用户会被随机踢下线
- 能提到 Session 在单体应用中的优势：实现简单，天然支持主动失效
- 能提到 JWT 的大小问题：JWT 包含用户信息，比 Session ID 大很多，每次请求都携带会增加带宽消耗

## 问题 3：SoftJWTAuth 和 JWTAuth 有什么区别？为什么 Feed 流要用 Soft 版本？

⭐⭐ **难度**：进阶  
**考察点**：未登录用户的处理策略、产品需求驱动设计

### 问题
> "项目里有两个 JWT 中间件：`JWTAuth` 和 `SoftJWTAuth`，它们有什么区别？为什么 Feed 流接口要用 Soft 版本？"

### 参考答案

**两个中间件的区别**：

```go
// JWTAuth：严格模式
func JWTAuth(...) gin.HandlerFunc {
    return func(c *gin.Context) {
        claims, err := auth.ParseToken(token)
        if err != nil {
            c.AbortWithStatusJSON(401, gin.H{"error": "unauthorized"})
            return  // ❌ 未登录直接拒绝
        }
        c.Set("account_id", claims.AccountID)
        c.Next()
    }
}

// SoftJWTAuth：宽松模式
func SoftJWTAuth(...) gin.HandlerFunc {
    return func(c *gin.Context) {
        claims, err := auth.ParseToken(token)
        if err != nil {
            // ✅ 未登录也不拒绝，用户 ID 设为 0
            c.Set("account_id", uint(0))
            c.Next()
            return
        }
        c.Set("account_id", claims.AccountID)
        c.Next()
    }
}
```

**为什么 Feed 流需要 Soft 模式**：

Feed 流有一个产品需求：**登录用户看到"我已点赞"，未登录用户看到"去登录"**

```go
// FeedService 中：
if viewerAccountID > 0 {
    // 登录用户：检查每条视频我有没有点赞
    for _, video := range videoList {
        video.IsLiked = f.likeRepo.CheckIsLiked(ctx, viewerAccountID, video.ID)
    }
} else {
    // 未登录用户：全部标记为未点赞
    for _, video := range videoList {
        video.IsLiked = false
    }
}
```

**路由配置的对比**：

```go
// 严格模式：关注、点赞、发布等需要登录的操作
protectedSocialGroup.Use(jwt.JWTAuth(...))

// 宽松模式：Feed 流列表，未登录也能刷
feedGroup.Use(jwt.SoftJWTAuth(...))
```

### 加分点
- 能提到产品层面的考虑：抖音/小红书即使未登录也能刷视频，这是冷启动体验
- 能提到 `c.Set("account_id", uint(0))` 后面所有代码不需要做 nil 判断，统一用 > 0 判断是否登录，代码更简洁
- 能提到更多中间件的模式：权限校验（AdminOnly）、接口版本控制等

## 问题 4：你的限流中间件是怎么实现的？"滑动窗口"和"固定窗口"有什么区别？

⭐⭐ **难度**：进阶  
**考察点**：限流算法、Redis INCR 原子操作

### 问题
> "你的限流中间件基于 Redis 实现，说下它是滑动窗口还是固定窗口？为什么选择滑动窗口而不是固定窗口？"

### 参考答案

**项目用的是滑动窗口**，基于 Redis 的 `INCR + PEXPIRE` Lua 脚本原子实现：

```go
func (c *Client) IncrementWithExpire(ctx context.Context, key string, expire time.Duration) (int64, error) {
    // Lua 脚本：原子操作
    // 如果 key 不存在 → INCR 设为 1 并设置过期时间
    // 如果 key 已存在 → INCR +1，不修改过期时间
    script := `
        local count = redis.call('INCR', KEYS[1])
        if count == 1 then
            redis.call('PEXPIRE', KEYS[1], ARGV[1])
        end
        return count
    `
    return c.Eval(ctx, script, []string{key}, expire.Milliseconds()).Int64()
}
```

**固定窗口 vs 滑动窗口**：

固定窗口的问题：
```
固定窗口：每分钟最多 10 次
    00:00:59 → 10 次请求 （第 1 秒用完了额度）
    00:01:00 → 10 次请求 （窗口重置，又能用了）
    
    实际上 00:00:59 ~ 00:01:00 这 2 秒内发生了 20 次请求！
    这就是"窗口边界突刺"问题
```

滑动窗口的效果：
```
滑动窗口：每分钟最多 10 次
    无论从哪个时间点看过去 60 秒，请求数都不会超过 10
    边界突刺问题被平滑了
```

**项目中的限流配置**：

| 接口 | 限流规则 | 维度 |
|------|---------|------|
| 登录 | 10 次/分钟/IP | IP |
| 注册 | 5 次/小时/IP | IP |
| 点赞 | 30 次/分钟/账号 | 用户 ID |
| 评论 | 10 次/分钟/账号 | 用户 ID |
| 关注 | 20 次/分钟/账号 | 用户 ID |

**为什么登录用 IP 维度，点赞用账号维度**？

IP 维度：
- 用户还没登录，没有账号 ID
- 适合登录、注册等未登录场景
- 缺点：同一个公司出口 IP 相同，会误伤

账号维度：
- 用户已登录，使用 JWT 中的 AccountID
- 精确到人，不会误伤
- 适合点赞、评论等需要登录的操作

### 加分点
- 能提到 Redis 限流的缺陷：Redis 挂了限流失效，所有请求放行。建议加上本地内存限流（如令牌桶）作为第二层保护
- 能提到 `PEXPIRE` 的单位是毫秒，精度更高，且 INCR 命令是原子的，不用担心并发安全问题
- 能对比其他限流算法：令牌桶（允许突发流量）、漏桶（平滑流量）、计数器（简单但边界突刺）

## 问题 5：密码是怎么存储的？为什么不用 MD5？

⭐⭐ **难度**：基础  
**考察点**：密码安全、哈希算法

### 问题
> "用户的密码在数据库里是怎么存的？为什么不用 MD5 或 SHA256？"

### 参考答案

**项目使用 bcrypt 算法**：

```go
import "golang.org/x/crypto/bcrypt"

// 注册时：哈希存储
func (s *AccountService) CreateAccount(ctx context.Context, account *Account) error {
    // bcrypt.GenerateFromPassword 自动生成随机 salt
    // bcrypt.DefaultCost = 10（迭代次数 2^10 = 1024 次）
    passwordHash, err := bcrypt.GenerateFromPassword([]byte(account.Password), bcrypt.DefaultCost)
    account.Password = string(passwordHash)
    return s.repo.CreateAccount(ctx, account)
}

// 登录时：比对哈希
func (s *AccountService) Login(username, password string) (string, error) {
    account, _ := s.FindByUsername(username)
    // bcrypt.CompareHashAndPassword 从哈希中提取 salt 重新计算并比对
    err := bcrypt.CompareHashAndPassword([]byte(account.Password), []byte(password))
    if err != nil {
        return "", errors.New("密码错误")
    }
    // 生成 JWT Token
    return auth.GenerateToken(account.ID, account.Username)
}
```

**为什么不能用 MD5/SHA256**：

| 算法 | 特点 | 安全性 |
|------|------|--------|
| MD5 | 128 位，碰撞已破解 | ❌ 极端不安全，已被弃用 |
| SHA256 | 256 位，抗碰撞 | ⚠️ 无 salt，彩虹表可破解 |
| bcrypt | 内置 salt + 可调迭代次数 | ✅ 对抗 GPU 暴力破解 |

**bcrypt 的密码学原理**：
1. 自动生成 16 字节随机 salt
2. 算法本身就是慢哈希（默认 1024 轮迭代）
3. 迭代次数可调，硬件升级后可以增加成本（不影响已有密码）

### 加分点
- 能提到 bcrypt 的 cost 参数含义：每增加 1，计算时间翻倍。`cost=10` 大约 100ms，`cost=14` 大约 1 秒
- 能提到更现代的密码哈希算法：Argon2（2023 年 OWASP 推荐的首选），scrypt（内存密集型，抗 GPU）
- 能提到密码存储的"最小暴露"原则：不在日志中打印密码、不返回密码给前端、密码字段不出现在 API 响应中

## 问题 6：限流中间件如果参数配置错了（比如 maxRequests = 0），会怎么样？

⭐⭐ **难度**：基础  
**考察点**：防御性编程、容错意识

### 问题
> "你看你的限流中间件里有个判断：`if maxRequests <= 0`，为什么这样写？如果忘了配置限流参数，会直接拦住所有请求吗？"

### 参考答案

```go
// 限流参数校验
if cache == nil || keyFunc == nil || maxRequests <= 0 || window <= 0 {
    c.Next()  // ← 直接放行！就当限流不存在
    return
}
```

**设计哲学：非核心功能挂了，不能影响核心业务**

| 参数问题 | 如果不做校验会发生什么？ | 现在的行为 |
|---------|----------------------|-----------|
| `maxRequests = 0` | Redis 计数 > 0 永远成立，所有人被拦住 | ✅ 放行，限流失效 |
| `cache = nil`（Redis 挂了） | 空指针 panic，整个服务崩了 | ✅ 放行，限流失效 |
| `window = 0` | PEXPIRE 设为 0，key 立刻过期 | ✅ 放行，限流失效 |

**宁可没保护，也不能把用户挡在门外**。

### 加分点
- 能提到"防御性编程"的思想：永远假设外部参数可能是错误的，永远假设依赖可能挂掉
- 能提到这个设计和 JWT 中间件的对比：JWT 校验失败必须拦截（安全第一），限流失败可以放行（体验第一）

## 问题 7：你的项目用 JWT 做认证，JWT 的安全性缺陷有哪些？怎么弥补？

⭐⭐⭐ **难度**：深度  
**考察点**：安全攻防、JWT 漏洞知识

### 问题
> "JWT 有哪些已知的安全风险？你的项目做了哪些防护？"

### 参考答案

**JWT 的六大安全风险及应对**：

| 风险 | 说明 | 项目中的防护 |
|------|------|-------------|
| 1. none 算法攻击 | 攻击者把 alg 改成 none，绕过签名验证 | ✅ 代码中显式检查签名算法：`token.Method.Alg() != HS256` |
| 2. 密钥泄露 | HS256 的密钥被偷，攻击者可伪造任意 Token | ✅ 密钥从环境变量读取，不写死在代码里 |
| 3. Token 泄露 | 别人拿到你的 Token 就能冒充你 | ✅ 双层验证 + HTTPS + 短过期时间（24小时） |
| 4. 重放攻击 | 用截获的 Token 重复请求 | ⚠️ 没有做，但 HTTPS 可以缓解 |
| 5. 信息泄露 | JWT 的 Payload 只是 Base64 编码，不是加密 | ✅ 不在 Payload 中放敏感信息（密码、手机号等） |
| 6. 过期时间过长 | 过期时间太久，泄露后风险大 | ✅ 24 小时过期 |

**签名算法验证的关键代码**：
```go
func ParseToken(tokenString string) (*Claims, error) {
    token, err := jwt.ParseWithClaims(tokenString, &Claims{}, func(token *jwt.Token) (interface{}, error) {
        // 验证签名算法：如果不是 HS256，直接拒绝
        // 防止攻击者把 alg 改成 none 绕过验证
        if token.Method == nil || token.Method.Alg() != jwt.SigningMethodHS256.Alg() {
            return nil, errors.New("unexpected signing method")
        }
        return jwtSecret(), nil
    })
}
```

### 加分点
- 能提到 none 攻击的经典案例：著名的"auth0 漏洞"，很多项目直接把 alg=none 的 Token 当成有效
- 能提到密钥管理的最佳实践：定期轮换密钥、不同环境用不同密钥、密钥不提交到 Git
- 能提到更安全的做法：使用 RS256（非对称加密），API 服务只有公钥，即使被攻破也无法伪造 Token
