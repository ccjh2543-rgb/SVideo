## 问题 1：为什么要把点赞、关注、评论这些操作设计成异步的？直接用同步写数据库有什么问题？

⭐ **难度**：基础  
**考察点**：同步 vs 异步的选型判断、性能优化思维

### 问题
> "我看到你的点赞操作是先发 MQ 消息，然后 Worker 再去数据库写入。为什么不直接同步写数据库？这样做带来了什么好处和代价？"

### 参考答案

**同步写的问题**（以点赞为例）：
```
用户点击点赞
    ↓
1. INSERT INTO likes (500ms) ← 用户等
2. UPDATE video SET likes_count++ (200ms) ← 继续等
3. UPDATE popularity (200ms) ← 还在等
4. 返回"点赞成功"给用户 (总耗时 900ms+) ← 用户快走了
```

**异步写的方案**：
```
用户点击点赞
    ↓
1. LikeMQ.Publish() (3ms) ← 消息进队列
2. 返回"点赞成功"给用户 (总耗时 3ms)  ← 秒回！
    ↓
【后厨 Worker】慢慢处理
3. INSERT INTO likes (500ms)
4. UPDATE likes_count (200ms)
5. UpdatePopularity (200ms)
```

**带来的好处**：

| 维度 | 同步 | 异步（你的方案） |
|------|------|----------------|
| 用户体验 | 等待 900ms，手都抬起来了 | 3ms 返回，秒级响应 |
| 吞吐量 | 数据库扛不住高并发 | MQ 削峰，Worker 慢慢消费 |
| 系统耦合 | 点赞代码直接耦合数据库 | 点赞代码只依赖 MQ，和数据库解耦 |
| 扩容能力 | 数据库是瓶颈 | 可以加 Worker 机器 |

**付出的代价**：
1. **最终一致性**：用户点了赞，红心立刻亮了，但数据库可能 100ms 后才更新
2. **复杂度上升**：需要 MQ 中间件、Worker 进程、消息确认机制
3. **消息丢失风险**：MQ 挂了消息可能丢失（项目用持久化 + ACK 保证）

### 加分点
- 能根据业务场景区分：账号注册/登录必须同步（用户要等结果），点赞/关注可以异步（用户感知不到延迟）
- 能引用项目中的实际限流值：点赞接口限流 30 次/分钟，正常用户不会产生大量并发

## 问题 2：你的 Worker 进程是怎么处理消息的？消息消费失败怎么办？

⭐⭐ **难度**：进阶  
**考察点**：消息队列消费模式、ACK 机制、重试策略

### 问题
> "你的 Worker 消费消息时用到了 `Ack` 和 `Nack`，能解释一下这两个方法的区别吗？如果 Worker 在处理消息时 panic 了，消息会丢失吗？"

### 参考答案

**Worker 的通用消费模式**：

```go
func (w *LikeWorker) handleDelivery(ctx context.Context, d amqp.Delivery) {
    err := w.process(ctx, d.Body)  // 处理消息
    
    if err != nil {
        // 处理失败：Nack(false, true)
        // requeue=true → 重新入队，稍后重试
        d.Nack(false, true)
        return
    }
    
    // 处理成功：Ack(false)
    // 告诉 RabbitMQ 这条消息可以删了
    d.Ack(false)
}
```

**Ack vs Nack 详解**：

| 方法 | 含义 | 参数说明 |
|------|------|---------|
| `Ack(multiple)` | 确认消息已成功处理 | `multiple=false` 只确认当前这条 |
| `Nack(multiple, requeue)` | 拒绝消息 | `requeue=true` 重新入队重试，`false` 直接丢弃 |

**如果 Worker panic 了**：
1. Worker 进程崩溃，RabbitMQ 检测到连接断开
2. 所有**未 Ack** 的消息自动重新入队（RabbitMQ 的自动恢复机制）
3. 其他 Worker 进程或重启后的 Worker 会重新消费这些消息
4. **消息不会丢失** ✅

**项目的错误处理策略**：

```go
func (w *LikeWorker) process(ctx context.Context, body []byte) error {
    var evt LikeEvent
    // 1. 解析失败 → 直接丢弃（requeue=false）
    // 坏数据重试一万次也解析不出来，不要阻塞队列
    if err := json.Unmarshal(body, &evt); err != nil {
        return nil  // 返回 nil → Ack，就当处理完了
    }
    
    switch evt.Action {
    case "like":
        err := w.likes.LikeIgnoreDuplicate(ctx, evt.UserID, evt.VideoID)
        
        var mysqlErr *mysql.MySQLError
        // 2. 重复关注/点赞 → 直接丢弃（幂等，不是错误）
        if errors.As(err, &mysqlErr) && mysqlErr.Number == 1062 {
            return nil  // 返回 nil → Ack
        }
        
        // 3. 真正的错误（比如数据库连接断开）→ 重新入队重试
        return err  // 返回 error → Nack(true)
    }
}
```

**三种处理结果**：
| 场景 | 动作 | 说明 |
|------|------|------|
| 处理成功 | `Ack(false)` | 消息出队，正常结束 |
| 可恢复错误（DB 挂了） | `Nack(false, true)` | 重新入队重试 |
| 不可恢复错误（反序列化失败） | `Ack(false)` | 直接丢弃，不给队列塞垃圾 |

代码位置：[worker/likeworker.go](file:///f:/zhuomian/项目/feedsystem_video_go-main/backend/internal/worker/likeworker.go)

### 加分点
- 能提到幂等消费：即使消息重复投递，业务层面不会产生重复数据
- 能提到死信队列（DLQ）：重复重试 N 次后还是失败的消息，应该投递到死信队列人工处理，而不是无限重试
- 能提到 Worker 的优雅关闭：通过 `signal.NotifyContext` 捕获 SIGTERM，正在处理的消息处理完再退出

## 问题 3：你的系统选择了 RabbitMQ，而不是 Kafka 或 Redis Stream，为什么？

⭐⭐ **难度**：进阶  
**考察点**：消息中间件选型、场景匹配

### 问题
> "为什么选 RabbitMQ 而不是 Kafka？在你的场景下，RabbitMQ 有什么优势？有什么劣势？"

### 参考答案

**RabbitMQ 相比 Kafka 的优势**：

| 维度 | RabbitMQ | Kafka |
|------|---------|-------|
| 消息模型 | Exchange + Queue，灵活路由 | Topic + Partition，线性吞吐 |
| 路由能力 | Topic/Direct/Fanout，消息级路由 | 只有 Topic |
| 延迟 | < 1ms | > 5ms（批量） |
| 吞吐量 | 万级/秒 | 百万级/秒 |
| 运维复杂度 | 低，自带 Management UI | 高，需要 Zookeeper |

**为什么在这个项目选 RabbitMQ**：

1. **需要灵活的路由**：每个业务有自己的 Exchange 和 Routing Key（`social.*`、`like.*`、`comment.*`）
2. **延迟敏感但吞吐量不高**：点赞/关注/评论的并发远没到 Kafka 的百万级别场景
3. **运维友好**：项目通过 Docker Compose 一键部署，自带 Management UI

**项目的 Exchange 设计**：

| Exchange | 类型 | 用途 |
|----------|------|------|
| `social.events` | topic | 关注/取关事件 |
| `like.events` | topic | 点赞/取消点赞事件 |
| `comment.events` | topic | 发布/删除评论事件 |
| `video.popularity.events` | topic | 热度更新事件 |
| `video.timeline.events` | topic | 时间线更新事件 |

**什么时候应该用 Kafka**：
- 需要更高的吞吐量（秒级百万消息）
- 需要消息回溯消费（重放历史数据）
- 需要长时间保存消息（日志场景）

### 加分点
- 能提到 RabbitMQ 的缺陷：消息堆积时性能会下降，且没有 Kafka 的顺序消费保证
- 能说明项目中使用的是 Topic Exchange，以及为什么选 topic 而不是 direct 或 fanout
- 能提到 RabbitMQ 的 `Qos(prefetch)` 设置：`ch.Qos(50, 0, false)` 限制 Worker 同时处理的消息数量，防止消息堆积到内存

## 问题 4：你的 Outbox（事务发件箱）模式是怎么设计的？解决了什么问题？

⭐⭐⭐ **难度**：深度  
**考察点**：分布式事务、消息可靠性、本地事务与消息发送的一致性

### 问题
> "项目中用到了 Outbox 模式来保证视频发布时消息不丢失，能详细讲一下这个模式是怎么工作的吗？解决了什么问题？"

### 参考答案

**问题背景**：
用户发布视频时，需要做两件事：
1. 将视频信息写入 MySQL（`videos` 表）
2. 通知 Feed 流系统更新时间线（发 MQ 消息）

如果先写 DB 再发 MQ：
```go
// ❌ 方案一：先 DB 再 MQ
db.Create(&video)           // ✅ 成功
mq.Publish(timelineEvent)   // ❌ 发送失败 → 视频白发布了
```

如果先发 MQ 再写 DB：
```go
// ❌ 方案二：先 MQ 再 DB
mq.Publish(timelineEvent)   // ✅ 成功
db.Create(&video)           // ❌ 失败 → Feed 流有这条视频，但视频不存在
```

**Outbox 模式解决这个两难问题**：

```
用户发布视频
    ↓
【同一个本地事务】
1. INSERT INTO videos (...)
2. INSERT INTO outbox_msgs (topic, payload, status='pending', created_at)
    ↓ 事务提交 ✅
    ↓
【Outbox Poller】（常驻 goroutine，每 100ms 轮询）
3. SELECT * FROM outbox_msgs WHERE status='pending' ORDER BY id LIMIT 50
4. FOR EACH msg:
   a. mq.Publish(msg.topic, msg.payload)
   b. UPDATE outbox_msgs SET status='published' WHERE id=msg.id
```

**为什么可靠**：
- 步骤 1 和 2 在同一个数据库事务中，要么都成功要么都失败（ACID 保证）
- Poller 轮询 `status='pending'` 的消息，即使 MQ 发送失败，下次轮询会重试
- 最终一致性保证：消息要么不发，发了就一定被消费

代码位置：
- Outbox 表定义：[worker/outboxworker.go](file:///f:/zhuomian/项目/feedsystem_video_go-main/backend/internal/worker/outboxworker.go)
- Poller 启动：[http/router.go](file:///f:/zhuomian/项目/feedsystem_video_go-main/backend/internal/http/router.go#L160-L163)

### 加分点
- 能指出 Outbox 模式的性能瓶颈：轮询方式有延迟（100ms 级别），且对数据库有额外查询压力
- 能提到 CDC（Change Data Capture）是 Outbox 的升级版，通过监听 MySQL binlog 来捕获数据变更，零延迟
- 能提到至少一次（at-least-once）投递语义：Poller 可能存在重复发送的情况，所以下游消费端必须幂等

## 问题 5：你的 Worker 怎么保证"最多处理一次"或"至少处理一次"？

⭐⭐ **难度**：进阶  
**考察点**：消息投递语义、幂等设计

### 问题
> "消息队列有 at-most-once、at-least-once、exactly-once 三种投递语义，你的系统用的是哪种？怎么保证的？"

### 参考答案

**项目的投递语义：at-least-once（至少一次）**

原因：
1. MQ 消息是持久化的（`amqp.Persistent`）
2. Worker 使用手动 ACK
3. Worker crash 后未 ACK 的消息自动重新入队

**重复消息的处理（幂等设计）**：

点赞操作的幂等：
```go
func (r *LikeRepository) LikeIgnoreDuplicate(ctx context.Context, userID, videoID uint) error {
    // INSERT IGNORE：如果 (user_id, video_id) 已存在，静默跳过
    // 不会报错，也不会覆盖已有数据
    return r.db.WithContext(ctx).
        Where("user_id = ? AND video_id = ?", userID, videoID).
        FirstOrCreate(&Like{}).Error
}
```

关注操作的幂等：
```go
switch evt.Action {
case "follow":
    err := w.repo.Follow(ctx, ...)
    
    var mysqlErr *mysql.MySQLError
    // MySQL 1062 = 唯一键冲突（已经关注过了）
    // 直接丢弃，不认为是错误
    if errors.As(err, &mysqlErr) && mysqlErr.Number == 1062 {
        return nil  // 幂等：返回成功
    }
    return err
}
```

**幂等设计的三种常见方案**：

| 方案 | 实现 | 本项目用 |
|------|------|---------|
| 业务键唯一约束 | UNIXIQUE INDEX | ✅ 点赞 (user_id, video_id)、关注 (follower_id, vlogger_id) |
| 全局去重 ID | 每条消息携带唯一 ID，消费前检查 | ⚠️ Event 中有 EventID，但未做消费去重 |
| 状态机幂等 | 检查当前状态，只有允许的状态转换才执行 | ❌ 未使用 |

### 加分点
- 能指出 at-least-once + 幂等 ≈ exactly-once 效果
- 能指出项目中没有做全局 ID 去重（EventID 存在但未消费前检查），如果 Poller 重复投递同一条消息，Like 会 INSERT IGNORE，但 Comment 没有类似的去重机制
- 能提到 Producer 端的幂等（MQ 发送时设置消息去重 ID）

## 问题 6：如果 RabbitMQ 挂了，你的系统还能用吗？怎么降级的？

⭐⭐ **难度**：进阶  
**考察点**：高可用设计、降级策略、容错

### 问题
> "RabbitMQ 宕机了，用户还能点赞、关注、评论吗？怎么做的降级？"

### 参考答案

**RabbitMQ 宕机的整体影响**：

```
MQ 挂了
    ↓
LikeMQ = nil   → LikeService 切换为同步写 DB
CommentMQ = nil → CommentService 切换为同步写 DB + 热度
SocialMQ = nil → SocialService 切换为同步写 DB
PopularityMQ = nil → 热度更新降级，不更新 Redis 热度
TimelineMQ = nil → Outbox Poller 和 Consumer 不启动
```

**核心降级代码**：

```go
// 每个 MQ 初始化失败时，标记为 nil
likeMQ, err := rabbitmq.NewLikeMQ(rmq)
if err != nil {
    likeMQ = nil  // MQ 不可用
}

// Service 层判断：MQ 不可用就走同步
func (s *LikeService) Like(ctx context.Context, userID, videoID uint) error {
    if s.likeMQ != nil {
        // ✅ MQ 可用：异步模式
        return s.likeMQ.Like(ctx, userID, videoID)
    }
    // ✅ MQ 不可用：同步降级，直接写数据库
    return s.likeRepo.LikeIgnoreDuplicate(ctx, userID, videoID)
}
```

**用户感知**：
- MQ 挂了 = 写操作从异步变成同步
- 用户点赞时，红心可能会等 100ms 才亮（同步写 DB 的耗时）
- 但功能完全正常，**用户不会知道 MQ 挂了**

**项目启动时的容错**：
```go
// Worker 不依赖 MQ 启动
var ch *amqp.Channel
conn, err := amqp.Dial(url)
if err != nil {
    // MQ 不可用：Worker 进程继续运行，只是没有队列可消费
    log.Printf("Worker process will idle - no RabbitMQ connection available")
}
```

### 加分点
- 能提到 MQ 挂了后的"消息堆积"问题：MQ 恢复后，Worker 开始消费堆积的消息，数据库可能瞬间承受大量写入。建议在 Worker 启动时做速率控制（Qos + 渐进式消费）
- 能对比 Kafka consumer group 的 rebalance 机制：RabbitMQ 没有 rebalance，Worker 数量变化不影响队列
- 能提到消息的持久化可靠性：`amqp.Persistent` 保证 RabbitMQ 重启后消息不丢

## 问题 7：Worker 进程退出时，怎么保证正在处理的消息不丢失？

⭐⭐ **难度**：进阶  
**考察点**：优雅关闭、信号处理、context 控制

### 问题
> "线上要发布新版本，你需要重启 Worker 进程，怎么保证正在处理的消息不会丢失？"

### 参考答案

**Worker 的优雅关闭机制**：

```go
func main() {
    // 1. 创建可以被信号取消的 context
    ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
    defer stop()
    
    // 2. 启动 Worker（阻塞在 Run 方法中）
    go func() {
        errCh <- socialWorker.Run(ctx)
    }()
    
    // 3. 等待信号
    <-ctx.Done()  // 收到 SIGTERM 或 Ctrl+C
    
    // 4. defer stop() 触发，context 取消
    // worker.Run() 中的 select 收到 ctx.Done()
}
```

**Worker 内部**：
```go
func (w *SocialWorker) Run(ctx context.Context) error {
    // 注册消费者
    deliveries, _ := w.ch.Consume(w.queue, "", false, ...)
    
    for {
        select {
        case <-ctx.Done():  // 收到关闭信号
            // ！！！正在处理的消息不丢失！
            // RabbitMQ 检测到连接断开，未 ACK 的消息自动重新入队
            return ctx.Err()
        case d := <-deliveries:
            w.handleDelivery(ctx, d)
        }
    }
}
```

**关闭流程时序**：

```
运维人员发送 SIGTERM
    ↓
Worker 进程收到信号
    ↓
ctx.Done() 触发
    ↓
正在处理的消息未调用 Ack
    ↓
RabbitMQ 检测到 Worker 断开连接
    ↓
自动将未 Ack 的消息重新入队
    ↓
另一个 Worker 实例 / 重启后的 Worker 消费这条消息
    ↓
✅ 消息不丢失！
```

### 加分点
- 能提到 Docker 部署的优雅关闭：`docker stop` 会发送 SIGTERM，`docker-compose down` 会按依赖顺序关闭
- 能提到 `stop()` 调用两次的效果：第一次触发关闭，第二次强制退出
- 能提到处理中的请求和消息的超时兜底：如果 Worker 卡住了，`context.WithTimeout` 兜底

## 问题 8：项目中每条消息都在消息体里带了 `EventID`，这是干什么用的？

⭐⭐ **难度**：基础  
**考察点**：消息追踪、全链路 ID、排查能力

### 问题
> "我看到点赞事件 `LikeEvent` 里有一个 `EventID` 字段，这个 ID 是怎么生成的？有什么用？"

### 参考答案

**EventID 的用途**：

```go
type LikeEvent struct {
    EventID    string    `json:"event_id"`    // 唯一追踪 ID
    Action     string    `json:"action"`      // like / unlike
    UserID     uint      `json:"user_id"`
    VideoID    uint      `json:"video_id"`
    OccurredAt time.Time `json:"occurred_at"` // 事件发生时间
}
```

**三个核心作用**：

1. **全链路追踪**：API 日志中记录 EventID → Worker 日志中也记录 EventID，将一次操作的整条链路串起来
2. **消息去重（潜在用途）**：消费端可以检查 EventID 是否已经处理过，实现去重消费
3. **业务审计**：通过 EventID 可以精确追溯："谁在什么时间对哪个视频做了什么操作"

**EventID 生成方式**：
```go
id, err := newEventID(16)
// 生成 16 字节的随机 ID，通常用 UUID 或 Snowflake 算法
```

### 加分点
- 能提到底层的 ID 生成算法：Random UUID vs Snowflake vs ULID 的优缺点对比
- 能提到日志中打印 EventID 的最佳实践：线上排查问题时，可以 `grep event_id=xxx 日志文件` 快速找到完整的处理链路
- 能指出项目中虽然定义了 EventID，但目前没有做消费端的去重校验，这是可以优化的点
