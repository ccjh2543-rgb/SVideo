## 问题 1：讲一下项目中数据表的设计，特别是有哪些关键的索引？

⭐⭐ **难度**：基础  
**考察点**：数据库表设计、索引策略

### 问题
> "介绍一下你的数据库表设计，关键的索引有哪些？为什么这样设计索引？"

### 参考答案

**核心表及关键索引设计**：

**1. Social（关注关系表）**
```go
type Social struct {
    ID         uint
    FollowerID uint  // 关注者 ID
    VloggerID  uint  // 被关注者 ID
}
```

关键索引：
```sql
INDEX idx_social_follower (follower_id)                    -- 查"我关注了谁"
INDEX idx_social_vlogger (vlogger_id)                      -- 查"谁关注了我"
UNIQUE INDEX idx_social_follower_vlogger (follower_id, vlogger_id)  -- 防止重复关注
```

**2. Like（点赞表）**
```sql
UNIQUE INDEX idx_like_user_video (user_id, video_id)  -- 防止重复点赞
INDEX idx_like_video (video_id)                        -- 查"视频有哪些点赞"
INDEX idx_like_user (user_id)                          -- 查"我点赞了哪些视频"
```

**3. Comment（评论表）**
```sql
INDEX idx_comment_video (video_id)                     -- 查"视频的评论列表"
```

**4. Video（视频表）**
```sql
INDEX idx_video_author (author_id)                     -- 查"作者的所有视频"
INDEX idx_video_create_time (create_time)              -- Feed流时间排序
INDEX idx_video_likes_count (likes_count)              -- 热门榜排序
INDEX idx_video_popularity (popularity)                -- 热度推荐排序
```

**5. Account（用户表）**
```sql
UNIQUE INDEX idx_account_username (username)           -- 用户名唯一
```

**索引设计原则**：
- **联合唯一索引**防止重复数据（关注/点赞等高频操作）
- **单字段索引**覆盖常见查询条件（WHERE + ORDER BY）
- Feed 流排序字段（create_time, likes_count, popularity）都建了索引

### 加分点
- 能提到复合索引的"最左前缀"原则：`INDEX(a, b)` 可以覆盖 `WHERE a = ?` 和 `WHERE a = ? AND b = ?` 两种查询
- 能提到索引的代价：写入变慢、占用磁盘空间，索引不是越多越好
- 能提到 `EXPLAIN` 分析查询是否走索引的实践经验

## 问题 2：项目中哪里用到了数据库事务？为什么这里必须要用事务？

⭐⭐ **难度**：进阶  
**考察点**：事务理解、ACID、数据一致性

### 问题
> "你的项目中哪些地方用到了数据库事务？为什么这些操作不能分成两条独立的 SQL？"

### 参考答案

**项目中的事务使用场景**：

**1. CommentService 的 Fallback 同步写入**：

```go
func (s *CommentService) Publish(ctx context.Context, ...) error {
    if s.commentMQ != nil {
        // 异步模式：发 MQ 即可
        return s.commentMQ.Publish(ctx, event)
    }
    
    // MQ 挂了 → 同步降级写入（必须用事务）
    return s.commentRepo.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        // 1. 创建评论（INSERT INTO comments）
        if err := tx.Create(comment).Error; err != nil {
            return err  // 回滚
        }
        // 2. 更新视频评论数（UPDATE videos SET comments_count++）
        if err := tx.Model(&video.Video{}).Where("id = ?", videoID).
            Update("comments_count", gorm.Expr("comments_count + 1")).Error; err != nil {
            return err  // 回滚
        }
        // 3. 更新热度（UPDATE videos SET popularity++）
        if err := tx.Model(&video.Video{}).Where("id = ?", videoID).
            Update("popularity", gorm.Expr("popularity + 1")).Error; err != nil {
            return err  // 回滚
        }
        return nil  // 全部成功才提交
    })
}
```

**2. AccountService 的 RenameWithToken（修改用户名时同时更新 Token）**

```go
func (r *AccountRepository) RenameWithToken(ctx context.Context, id uint, newUsername string, token string) error {
    return r.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        // 1. 更新用户名
        result := tx.Model(&Account{}).Where("id = ?", id).Update("username", newUsername)
        // 2. 更新 Token（用户改名后原 Token 失效，需要重新登录）
        tx.Model(&Account{}).Where("id = ?", id).Update("token", token)
        // 要么都成功，要么都失败
        return nil
    })
}
```

**为什么一定要用事务**：

```
不加事务的后果：
    第一步：创建评论 ✅ 
    第二步：更新评论数 ❌ （数据库连接中断）
    
    结果：评论存在，但评论数没加 → 数据不一致
         用户以为评论没发成功，再发一次 → 两条重复评论
```

事务保证了三者的 ACID 特性，**要么全部成功，要么全部回滚**。

### 加分点
- 能对比 GORM 的事务 API：`tx = db.Begin()` / `tx.Commit()` / `tx.Rollback()` vs `db.Transaction(func(tx) { ... })` 闭包自动处理
- 能指出事务的代价：持有行锁/表锁的时间变长，高并发下可能引起死锁
- 能提到乐观锁 vs 悲观锁：评论数 +1 用 `gorm.Expr("comments_count + 1")` 是乐观的原子更新，不需要事务也可以

## 问题 3：关注流查询用了子查询（IN）而不是 JOIN，为什么子查询更快？

⭐⭐ **难度**：进阶  
**考察点**：SQL 优化、执行计划、子查询 vs JOIN

### 问题
> "你写关注流查询的时候，用了子查询 `WHERE author_id IN (SELECT vlogger_id FROM social WHERE follower_id = ?)`，为什么不用 JOIN？"

### 参考答案

**两种写法的对比**：

```sql
-- 方案 A：你的写法（子查询 IN）
SELECT * FROM video 
WHERE author_id IN (
    SELECT vlogger_id FROM social WHERE follower_id = 123
)
ORDER BY create_time DESC LIMIT 10;

-- 方案 B：JOIN 写法
SELECT video.* FROM video 
JOIN social ON video.author_id = social.vlogger_id 
WHERE social.follower_id = 123
ORDER BY video.create_time DESC LIMIT 10;
```

**为什么子查询更快**：

1. **子查询的执行计划**：
```
1. SELECT vlogger_id FROM social WHERE follower_id = 123  → 走索引，查 200 个关注的人
2. SELECT * FROM video WHERE author_id IN (200个ID)     → 走索引，查 10 条
```

2. **JOIN 的执行计划**：
```
1. JOIN social ON video.author_id = social.vlogger_id    → 笛卡尔积！Video和Social全表
2. WHERE social.follower_id = 123                        → 再过滤
```

**关键差异**：如果一个人关注了 200 个博主：
- 子查询：先查出 200 个 ID → 用这 200 个 ID 去查 video 表（走索引）
- JOIN：先关联两个大表生成中间结果 → 再筛选

**数据量越大，差距越悬殊**：
| 数据量 | 子查询 | JOIN |
|--------|--------|------|
| 10 万视频，200 个关注 | 1-5ms | 10-50ms |
| 100 万视频，2000 个关注 | 5-10ms | 100-500ms |
| 1000 万视频 | 10-20ms | 可能超时 |

### 加分点
- 能提到 `JOIN` 和 `IN` 的 MySQL 优化器可能自动改写：某些版本中 MySQL 会优化为相同计划，但业务安全起见，手写子查询更可控
- 能提到 `EXISTS` 替代 `IN` 的场景：当子查询结果集很大时，`EXISTS` 通常更快（半连接优化）
- 能提到索引设计的重要性：`social` 表的 `(follower_id, vlogger_id)` 联合索引和 video 表的 `(author_id, create_time)` 复合索引保证了两个查询都走索引

## 问题 4：你的 Go 项目如何传递 context？context 里都放了什么？

⭐⭐ **难度**：基础  
**考察点**：context 使用、链路追踪、超时控制

### 问题
> "介绍一下你的项目中 context 是怎么传递的？从 HTTP 请求到数据库查询，context 经历了什么？"

### 参考答案

**context 的完整传递链路**：

```
Gin HTTP 请求
    ↓
c.Request.Context()  ← Gin 自动创建的 context
    ↓
Handler 层
    ↓ 传递 ctx
Service 层
    ↓ 传递 ctx（或加上 WithTimeout）
Repository 层
    ↓ 传递 ctx
db.WithContext(ctx).Find(...)  ← GORM 使用 context
```

**项目中 context 存放的内容**：
1. **用户 ID**（通过 `c.Set("account_id", ...)` 放入，通过 `jwt.GetAccountID(c)` 取出）
2. **超时控制**（Redis 操作套上 50ms 超时）
3. **优雅关闭信号**（Worker 的 signal.NotifyContext）

**具体代码示例**：

```go
// Handler 层：从 JWT 提取用户 ID
viewerAccountID, err := jwt.GetAccountID(c)
// 把 ctx 传给 Service
feedItems, err := f.service.ListLatest(c.Request.Context(), req.Limit, latestTime, viewerAccountID)

// Service 层：传给 Repository
func (f *FeedService) ListLatest(ctx context.Context, ...) {
    // ...
    return f.repo.ListLatest(ctx, limit, latestBefore)
}

// Repository 层：用 context 做数据库查询
func (repo *FeedRepository) ListLatest(ctx context.Context, ...) {
    return repo.db.WithContext(ctx).Model(&Video{}).
        Order("create_time DESC").
        Limit(limit).Find(&videos).Error
}

// Service 层：Redis 操作加超时
cacheCtx, cancel := context.WithTimeout(ctx, 50*time.Millisecond)
defer cancel()
results, err := f.rediscache.MGet(cacheCtx, cacheKeys...)
```

### 加分点
- 能提到 context 的四大作用：超时控制（WithTimeout）、取消信号（WithCancel）、传值（WithValue）、Deadline
- 能提到"context 应该显示传递，不要放在结构体里"的 Go 最佳实践
- 能提到 GORM 的 `WithContext` 支持事务传递：`tx.WithContext(ctx)` 确保事务内的所有操作遵循同一个 context

## 问题 5：项目中大量使用 `if err != nil`，Go 的错误处理和其他语言比有什么不同？

⭐⭐ **难度**：进阶  
**考察点**：Go 错误处理哲学、errors.Is / errors.As

### 问题
> "很多人觉得 Go 的 `if err != nil` 太啰嗦，你怎么看？你的项目中用到了 `errors.As` 和 `errors.Is`，谈一下它们的区别。"

### 参考答案

**Go 错误处理的设计哲学**：

其他语言（Java/Python）用异常机制：
```java
try {
    userService.login(username, password);
} catch (Exception e) {
    // 你不知道 catch 了什么，可能吞掉不该吞的错误
}
```

Go 用返回值机制：
```go
token, err := userService.Login(username, password)
if err != nil {
    // 清清楚楚知道这里可能出错
    return "", err
}
// err 被处理了，你可以放心用 token
```

**项目中 `errors.Is` vs `errors.As` 的使用**：

```go
import (
    "errors"
    "github.com/go-sql-driver/mysql"
)

// errors.Is：判断错误链中是否包含某类错误（值比较）
func (s *AccountService) Rename(ctx, ...) error {
    err := s.repo.Rename(ctx, ...)
    if errors.Is(err, gorm.ErrRecordNotFound) {
        // Is：判断错误是否等于某个特定值
        return err  // 用户不存在
    }
}

// errors.As：判断错误链中是否包含某种类型（类型断言）
func handleLikeEvent(ctx, evt) error {
    err := w.likes.Like(ctx, evt.UserID, evt.VideoID)
    
    var mysqlErr *mysql.MySQLError
    if errors.As(err, &mysqlErr) && mysqlErr.Number == 1062 {
        // As：判断错误是否属于 MySQL 错误类型，并提取具体错误号
        // 1062 = 唯一键冲突（重复点赞），直接返回成功（幂等）
        return nil
    }
    return err
}
```

**区别总结**：

| 方法 | 用途 | 示例 |
|------|------|------|
| `errors.Is(err, target)` | 错误链中是否包含特定**值** | `Is(err, gorm.ErrRecordNotFound)` |
| `errors.As(err, &target)` | 错误链中是否包含特定**类型** | `As(err, &mysqlErr)` |

### 加分点
- 能提到 Go 1.20 的 `errors.Join`：合并多个错误
- 能提到 Go 错误处理的"三个黄金法则"：永远不要忽略错误、不要用 panic 代替错误处理、给错误添加上下文（`fmt.Errorf("xxx: %w", err)`）
- 能对比项目中前后端错误码的设计：前端收到 429（限流）应该展示不同的提示文案，401（未登录）跳转到登录页

## 问题 6：Docker 多阶段构建怎么优化最终镜像大小的？

⭐⭐ **难度**：进阶  
**考察点**：容器化、镜像优化、Dockerfile

### 问题
> "你们的 Docker 多阶段构建是怎么做的？最终镜像有多大？怎么优化的？"

### 参考答案

**Dockerfile 核心**：

```dockerfile
# Stage 1: 编译
FROM golang:1.24.5 AS build

WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download

COPY . .

# 编译优化
RUN CGO_ENABLED=0 GOOS=linux go build -trimpath -ldflags="-s -w" -o /app/api ./cmd/main.go

# Stage 2: 运行
FROM alpine:3.21

# 安全配置
RUN adduser -D -g '' app && \
    apk --no-cache add ca-certificates tzdata

COPY --from=build /app/api /app/api

USER app
EXPOSE 8080
CMD ["/app/api"]
```

**优化效果对比**：

| 版本 | 镜像大小 |
|------|---------|
| 基础 Go 镜像直接运行 | ~800MB |
| Alpine + 多阶段构建 | ~15MB |
| **你的项目** | **≈ 15-20MB** |

**核心优化手段**：

1. **`CGO_ENABLED=0`**：禁用 C 语言绑定，生成纯静态链接的二进制，不依赖 libc
2. **`-ldflags="-s -w"`**：去掉调试信息和符号表，约减少 30% 体积
3. **`-trimpath`**：去掉编译路径信息，进一步减小体积
4. **多阶段构建**：编译环境和运行环境完全隔离，运行环境只有二进制 + Alpine 最小系统
5. **Alpine 基础镜像**：基于 musl libc 的微型 Linux，从 ~800MB 降到 ~5MB

### 加分点
- 能提到 Docker 的健康检查配置：`docker-compose.yml` 中用了 `healthcheck` + `depends_on.condition`
- 能提到非 root 用户的安全实践：`USER app` 防止容器被攻破后直接获得 root 权限
- 能提到 `docker compose up` 的启动顺序控制：MySQL → Redis → RabbitMQ → backend → worker

## 问题 7：项目中怎么实现依赖注入的？没有用框架吗？

⭐⭐ **难度**：基础  
**考察点**：依赖注入、控制反转、Go 工程实践

### 问题
> "你的项目没有用 wire 这样的 DI 框架，是怎么做依赖注入的？这种手动注入的方式有什么优缺点？"

### 参考答案

**项目使用手动依赖注入**：

```go
// router.go 中"手动连接"所有依赖
func SetRouter(db *gorm.DB, cache *rediscache.Client, rmq *rabbitmq.RabbitMQ) *gin.Engine {
    // 1. 创建 Repository（依赖 DB）
    accountRepository := account.NewAccountRepository(db)
    
    // 2. 创建 Service（依赖 Repository 和其他组件）
    accountService := account.NewAccountService(accountRepository, cache)
    
    // 3. 创建 Handler（依赖 Service）
    accountHandler := account.NewAccountHandler(accountService)
    
    // 4. 注册路由（依赖 Handler）
    accountGroup.POST("/login", loginLimiter, accountHandler.Login)
}
```

**依赖链**：
```
DB → Repository → Service → Handler → Router
               ↑              ↑
           Redis/MQ        Limiter
```

**手动注入的优缺点**：

| 维度 | 手动注入 | Wire 框架 |
|------|---------|-----------|
| 代码量 | 多写几行 | 少写代码 |
| 可读性 | 依赖关系一目了然 | 需要了解 Wire 语法 |
| 编译检查 | ✅ 编译期检查类型是否正确 | ✅ 编译期生成代码 |
| 重构友好 | 改构造函数时所有调用处都要改 | 自动更新 |
| 学习成本 | 无 | 需要学习 Wire |
| 适合场景 | 中小型项目 | 大型项目（几十个模块） |

**为什么不选 Wire**：
- 项目规模适中，手动注入清晰可读
- 避免了框架依赖和代码生成的学习成本
- Go 的哲学偏向显式多于隐式

### 加分点
- 能提到"构造函数统一接收依赖"的约定：所有模块都通过 `NewXxx(deps...)` 方式创建，不使用全局变量或 init() 函数
- 能提到这种模式的测试友好性：单元测试时传入 Mock 依赖即可
- 能提到"依赖倒置"原则：高层模块不依赖低层模块，都依赖抽象接口

## 问题 8：项目启动时做了 AutoMigrate，生产环境也这样做吗？

⭐⭐ **难度**：进阶  
**考察点**：数据库迁移、CI/CD、生产安全

### 问题
> "你的项目在启动时 GORM 会自动迁移表结构（AutoMigrate），生产环境也这么做吗？有什么风险？"

### 参考答案

**AutoMigrate 的适用场景**：

```go
// cmd/main.go 启动时
if err := db.AutoMigrate(sqlDB); err != nil {
    log.Fatalf("Failed to auto migrate: %v", err)
}
```

**开发环境**：✅ 完全没问题，方便快速迭代

**生产环境的三个风险**：

1. **自动加字段可能引起 panic**：GORM AutoMigrate 会新增 NOT NULL 字段，但已有数据行该字段为 NULL，导致查询报错
2. **自动删字段可能丢数据**：结构体中删掉一个字段后 AutoMigrate 会删掉对应列，数据丢失无法恢复
3. **大表加索引会锁表**：如果视频表有 1000 万行，加索引需要几分钟，期间整个表被锁

**生产环境的正确做法**：

1. **使用数据库迁移工具**：`golang-migrate/migrate` 或 `pressly/goose`
2. **编写版本化迁移文件**：
```sql
-- 001_create_users.sql
CREATE TABLE IF NOT EXISTS users (...);

-- 002_add_email_column.sql
ALTER TABLE users ADD COLUMN email VARCHAR(255);
```

3. **CI/CD 中运行迁移**：
```
1. 代码审查
2. 测试环境运行迁移
3. 生产环境运行迁移（先于新版本部署）
```

### 加分点
- 能提到"向前兼容"原则：生产环境的数据库迁移必须是向前兼容的，旧版代码+迁移后的数据库 要能正常工作
- 能提到分阶段部署：先运行只加字段不删字段的迁移 → 新版本部署 → 再运行清理迁移
- 能提到"索引创建"的问题：`CREATE INDEX` 最好用 `ALGORITHM=INPLACE, LOCK=NONE` 避免锁表
