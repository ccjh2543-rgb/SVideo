## 问题 1：请画出你的系统整体架构图，并讲解一次完整的点赞操作的数据流

⭐⭐⭐ **难度**：深度  
**考察点**：全局架构理解、全链路数据流、同步+异步思维

### 问题
> "能给我在白板上画出你的系统架构图吗？然后从用户点击点赞按钮开始，到数据库更新完成，讲一下完整的数据流。"

### 参考答案

**架构图**：

```
┌────────────────────────────────────────────────────────────────────┐
│                        用户 (前端 / 移动端)                         │
└──────────────────────────┬─────────────────────────────────────────┘
                           │ HTTP POST /like/like
                           ▼
┌────────────────────────────────────────────────────────────────────┐
│                    Gin HTTP Server (API 进程)                       │
│                                                                     │
│  1. LikeHandler.Like()                                              │
│     ├── JWT Auth (解析用户 ID)                                     │
│     ├── Ratelimit (30次/分钟/账号)                                  │
│     └── LikeService.Like()                                         │
│           ├── Redis 检查是否已点赞                                  │
│           ├── LikeMQ.Publish() → RabbitMQ                          │
│           └── 返回"点赞成功"(200)                                  │
└──────────────────────────┬─────────────────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────────────────┐
│                    RabbitMQ (消息队列)                              │
│                                                                     │
│  Exchange: like.events                                              │
│  Queue:    like.events                                              │
│  Message:  {EventID, Action:"like", UserID, VideoID}               │
└──────────────────────────┬─────────────────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────────────────┐
│                    Worker 进程 (后厨)                               │
│                                                                     │
│  2. LikeWorker.Run()                                               │
│     ├── Consume(like.events)                                       │
│     ├── LikeRepository.LikeIgnoreDuplicate()                       │
│     │     └── INSERT IGNORE INTO likes (user_id, video_id)         │
│     ├── VideoRepository.ChangeLikesCount(videoID, +1)              │
│     │     └── UPDATE videos SET likes_count++ WHERE id = ?         │
│     ├── VideoRepository.ChangePopularity(videoID, +1)              │
│     │     └── UPDATE videos SET popularity++ WHERE id = ?          │
│     └── PopularityMQ.Publish() → RabbitMQ                          │
│                                                                     │
│  3. PopularityWorker (另一个Worker实例/goroutine)                   │
│     └── 消费 popularity 消息                                        │
│         └── Redis ZINCRBY hot:video:1m:{minute} 1 {videoID}        │
└─────────────────────────────────────────────────────────────────────┘
```

**用户感受的时间线**：

```
t=0ms   用户点击点赞按钮
t=3ms   API返回"点赞成功"（红心立刻点亮）
t=20ms  Worker开始消费队列消息
t=50ms  INSERT INTO likes（点赞记录落库）
t=80ms  UPDATE videos SET likes_count = likes_count + 1（计数更新）
t=100ms UPDATE videos SET popularity = popularity + 1（热度更新）
t=120ms Redis ZINCRBY（热榜更新）
t=200ms 其他用户刷新看到点赞数+1
```

**用户感知**：3ms 看到红心亮了 ✅。**后台**：200ms 内所有事情处理完了。完美。

### 加分点
- 能进一步画出"点赞"和"取消点赞"的分支逻辑
- 能画出 Redis 挂了时的降级链路（MQ → 同步直写 DB）
- 能画出 Outbox 模式的时间线更新链路（发布视频时的双写保证）

## 问题 2：如果让你重写这个系统，哪些地方可以做得更好？

⭐⭐⭐ **难度**：深度（最常见的面试题，没有之一）  
**考察点**：架构演进意识、技术视野、批判性思维

### 问题
> "假设现在流量翻了 100 倍（从 1 万 DAU 到 100 万 DAU），哪些地方需要重构？你的优化方案是什么？"

### 参考答案

**问题 1：API + Worker 在同一个代码库，无法独立扩容到不同的机器**

现状：两个进程共享代码，但部署时需要分别编译
优化：
1. 拆成独立的 Git 仓库和 CI/CD 流水线
2. 分别编译、独立部署、独立水平扩容

**问题 2：关注流查询性能瓶颈**

现状：每次请求查两次 DB（查关注列表 → 查视频列表）
优化方案 → **推模式（Fan-out）**：
```
用户发布视频
    ↓
查所有粉丝（SELECT follower_id FROM social WHERE vlogger_id = ?）
    ↓
为每个粉丝的 Timeline 写入一条消息 → 粉丝刷关注流直接读自己的 Timeline
```

**问题 3：SingleFlight 只对单进程有效**

现状：API 多实例部署时，每个实例都有自己的 SingleFlight
优化方案 → **分布式锁 + 本地缓存**：
```
多个 API 实例同时查同一个视频
    ↓
抢 Redis 分布式锁（SETNX），抢到的查数据库
    ↓
查到的结果写入 Redis 缓存
    ↓
其他实例从 Redis 缓存读取（不再需要锁）
```

**问题 4：缺少合理的监控和告警**

现状：只有 pprof 做性能分析
优化方案：
1. 接入 Prometheus + Grafana
2. 核心指标：QPS、P99 延迟、错误率、MQ 堆积量
3. 告警规则：P99 > 500ms、队列堆积 > 10000、错误率 > 1%

**问题 5：数据库单点风险**

现状：单个 MySQL 实例
优化方案：
1. 主从复制（Master 写、Slave 读）
2. 分库分表（按 video_id 哈希分片）
3. 连接池监控

### 加分点
- 能提到具体的推拉模式对比（推模型的效果公式：写扩散 vs 读扩散）
- 能提到具体的中间件选型（Prometheus + Grafana）
- 能提到"先不做过度设计"的务实态度：当前架构足够支撑 1 万 DAU，等流量到了 10 万再优化（面试官很看重这种务实的态度）

## 问题 3：视频 Feed 流系统用"推模式"还是"拉模式"？你的项目用的是哪种？

⭐⭐⭐ **难度**：深度（Feed 流系统的灵魂问题）  
**考察点**：推送 vs 拉取、读写扩散、系统设计权衡

### 问题
> "Feed 流系统有两种经典架构：推模式（写扩散）和拉模式（读扩散），你的项目用的是哪种？为什么没有选另一种？"

### 参考答案

**三种模式的对比**：

**拉模式（你项目的方案）**：
```
用户刷"关注流"
    ↓
查询我关注了谁（social 表）
    ↓
查询这些人的视频（video 表 WHERE author_id IN (...)）
```

| 维度 | 拉模式 |
|------|--------|
| 写开销 | 低（只写 1 条 video 记录） |
| 读开销 | 高（每次查询都要 JOIN/IN） |
| 粉丝多的大V影响 | 无影响 |
| 热点问题 | 冷启动数据少时查询慢 |

**推模式（写扩散/扇出）**：
```
大V发布视频
    ↓
查 100 万粉丝
    ↓
给每个粉丝的 Timeline 写一条消息（100 万条写入！）
```

| 维度 | 推模式 |
|------|--------|
| 写开销 | 极高（100 万粉丝 = 100 万条写入） |
| 读开销 | 极低（直接读自己的 Timeline） |
| 粉丝多的大V影响 | 大V一发视频，系统直接崩了 |
| 热点问题 | 需要粉丝数阈值控制（>10万粉丝的大V改拉模式） |

**混合模式（大厂的终极方案）**：

```
普通用户（<10万粉丝）：推模式
    ↓ 发布视频时离线扇出给粉丝
大V用户（>10万粉丝）：拉模式
    ↓ 粉丝刷关注流时实时合并大V的最新视频
```

**你的项目为什么选了拉模式**：
1. 项目规模较小（中小型应用），拉模式实现简单
2. 用户量级没到"大V扇出会打垮系统"的程度
3. 推模式需要额外存储 Timeline（内存/磁盘成本高）
4. 拉模式在用户关注量不大时（几十到几百个），性能完全够用

### 加分点
- 能提出"冷热数据分离"的 Twitter 做法：热推（最近 N 条）提前推，冷数据回源查
- 能提出"推拉结合"的具体阈值：粉丝数 > 10 万的大V用拉模式，普通用户推模式
- 能提到推模式的实际成本：Twitter 早期用推模式，`Celebrity Tweet` 导致系统雪崩，后来改为混合模式

## 问题 4：你的系统中哪些地方用到了"最终一致性"？你觉得最终一致性的风险是什么？

⭐⭐⭐ **难度**：深度  
**考察点**：分布式系统一致性、CAP 理论、业务容忍度

### 问题
> "哪些操作是最终一致的？用户点赞后发现红心亮了，但刷新后红心又没了（数据还没写到 DB），这种情况怎么处理？"

### 参考答案

**你项目中最终一致性的场景**：

| 操作 | 第一步（立刻） | 第二步（异步） | 不一致窗口 |
|------|--------------|--------------|-----------|
| 点赞 | 红心亮（前端本地状态） | Worker 写入 DB | 10-100ms |
| 关注 | 前端显示"已关注" | Worker 写入 DB | 10-100ms |
| 评论 | 前端显示评论 | Worker 写入 DB + 更新计数 | 10-100ms |
| 热度更新 | 无即时反馈 | Worker 更新 Redis ZSET | 1-5s |

**如何解决"红心亮了又灭"的问题（前端优化）**：

```javascript
// 前端乐观更新
function like(videoId) {
    // 1. 立即更新 UI（红心亮）
    updateLikeButton(true);
    
    // 2. 发送请求
    fetch('/like/like', { method: 'POST', body: JSON.stringify({ video_id: videoId }) })
        .then(response => {
            if (!response.ok) {
                // 3. 失败回滚（红心灭）
                updateLikeButton(false);
                showToast('操作失败，请重试');
            }
        })
        .catch(() => {
            // 4. 网络错误也回滚
            updateLikeButton(false);
        });
}
```

**最终一致性的风险**：

1. **业务风控**：用户点赞后立刻刷新，看到点赞数没变，可能认为"APP 有 bug"
2. **重复操作**：用户点了"点赞"，没看到反馈，又点一次 -> Worker 可能收到两条消息（幂等性兜底）
3. **边界情况**：用户点赞后立刻取消点赞，两条消息到达 Worker 的先后顺序不能保证

**CAP 理论的权衡**：
> 你的项目选了 **AP（可用性 + 分区容忍性）**，牺牲了强一致性

这是正确的选择：短视频场景中，用户能接受点赞数延迟几秒更新，但不能接受"点赞转圈 3 秒"。

### 加分点
- 能提到"读己之写"的一致性：用户自己点赞后，在 Feed 流中应该立刻看到。"对于自己的操作读自己的写"，建议在 Service 层做特殊处理：如果当前用户是操作者，走 DB 查确保看到最新数据
- 能提到最终一致性窗口的监控：这个窗口时间过长（超过 1 秒）说明 Worker 消费慢了，需要告警
- 能提到 BASE 理论（通过消息队列实现最终一致性）

## 问题 6：回顾整个项目，你觉得最自豪的设计是什么？为什么？

⭐⭐ **难度**：进阶  
**考察点**：自我总结、技术品味

### 问题
> "如果让你从你的项目里选一个设计讲给我听，你会选哪个？为什么？"

### 参考答案

**推荐回答：冷热分离 + 水印线设计**

理由：
1. **解决了真实问题**——ZSET 不能无限大，但又要保证 99% 的用户请求走缓存
2. **设计简洁**——水印线就是 ZSET 最老一条记录的时间戳，一个字段区分冷热
3. **天然优雅降级**——翻到旧数据时自动切到 MySQL，用户无感知
4. **自动重建**——ZSET 空了也不怕，SingleFlight 自动重建
5. **可解释性强**——白板上画一条带水印线的时间轴，面试官秒懂

### 加分点
- 提到自己当时做这个设计时的思考过程
- 提到上线后效果（如果线上跑过）：缓存命中率从 X% 提升到 Y%
- 提到改进空间：比如把水印线改为动态阈值，根据 Redis 内存使用率自动调整
