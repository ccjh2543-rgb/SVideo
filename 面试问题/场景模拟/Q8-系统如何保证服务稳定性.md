# 面试问答记录 - 第8轮

## 问题
你这个系统是如何保证服务稳定性的，多角度回答？

## 回答

我从 **架构设计、缓存、限流、容错降级、异步解耦、可观测性、部署运维** 七个维度来回答。

### 一、架构设计层面

#### 1.1 API / Worker 分离部署

系统拆分为两个独立进程：

```
API 进程（cmd/main.go）
  └─ 只做：请求校验、缓存读取、MQ 发布
  └─ 不写数据库（除降级情况）

Worker 进程（cmd/worker/main.go）
  └─ 独立部署、独立扩缩容
  └─ 消费 MQ 消息，异步写数据库
```

好处是：API 进程的负载再高，也不会直接影响数据库写入性能。Worker 消费不过来了，消息会在 MQ 中积压，等 Worker 恢复后再慢慢处理，**不会丢数据，也不会拖垮数据库**。

#### 1.2 依赖注入 + 组件可降级

```go
// router.go 中的依赖注入
popularityMQ, err := rabbitmq.NewPopularityMQ(rmq)
if err != nil {
    log.Printf("PopularityMQ init failed (mq disabled): %v", err)
    popularityMQ = nil  // MQ 不可用 → 设为 nil，不走 MQ
}
```

当 RabbitMQ 初始化失败时，`popularityMQ` 被设为 nil。所有用到它的地方都有 nil 检查：

```go
if s.popularityMQ != nil {
    s.popularityMQ.Update(ctx, id, change)
}
// 为 nil 时直接走降级路径
```

**任何外部组件的故障都不会导致服务崩溃**，只是降级到功能降级模式。

#### 1.3 优雅关闭

```go
// 监听 SIGINT / SIGTERM
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()

// 等待关闭信号
<-ctx.Done()

// 10 秒超时关闭
shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()

// 关闭顺序：HTTP Server → RabbitMQ 连接 → Redis → MySQL
server.Shutdown(shutdownCtx)
rmq.Close()
cache.Close()
db.Close()
```

Worker 进程同理，通过 `ctx.Done()` 让消费循环自然退出，处理完当前消息后再关闭，**不丢消息**。

### 二、缓存层面（三级缓存 + 防击穿 + 降级）

这是系统稳定性设计最成熟的部分。

#### 2.1 三级缓存架构

```
请求 → L1 本地内存缓存 (3s TTL)
   ↓ 未命中
 L2 Redis 分布式缓存 (24h TTL)
   ↓ 未命中 / Redis 不可用
 L3 MySQL 数据库（最终数据源）
```

```go
// 批量查视频详情
func (f *FeedService) GetVideoByIDs(ctx context.Context, videoIDs []uint) ([]*video.Video, error) {
    // Step 1: L1 本地缓存（3秒）
    if v, found := f.localcache.Get(key); found { return v }

    // Step 2: L2 Redis（MGet 批量查询）
    results, err := f.rediscache.MGet(ctx, keys...)
    if err == nil {
        // 命中 → 反序列化 → 回填 L1
    } else {
        // Redis 挂了 → 全部降级到 L3
        missedL2 = allIDs
    }

    // Step 3: L3 MySQL + SingleFlight 防击穿
    v, err, _ := f.requestGroup.Do(sfKey, func() (interface{}, error) {
        return f.repo.GetByIDs(ctx, []uint{videoID})
    })
    // 查到了 → 异步回填 L2 和 L1
}
```

**关键稳定设计**：
- L1 3 秒 TTL：高频请求不穿透到 Redis，更不穿透到 DB
- L2 24 小时 TTL：Redis 挂了，重启后缓存还在
- L3 兜底：Redis 完全不可用，用户仍然能看到数据
- 设计哲学：**"缓存可以挂，用户不能刷不出视频"**

#### 2.2 SingleFlight 防缓存击穿

```go
sfKey := fmt.Sprintf("sf:entity:%d", videoID)
v, err, _ := f.requestGroup.Do(sfKey, func() (interface{}, error) {
    // 同一时刻 1000 个并发请求同一个视频 ID
    // 只有 1 个真正查数据库，其余 999 个等待结果
    return f.repo.GetByIDs(ctx, []uint{videoID})
})
```

#### 2.3 分布式锁 + 自旋等待（视频详情）

```go
// 缓存未命中 → 抢分布式锁
token, locked, _ := vs.cache.Lock(ctx, lockKey, 2*time.Second)
if locked {
    defer vs.cache.Unlock(ctx, lockKey, token)
    video, _ := vs.repo.GetByID(ctx, id)
    setCached(video)  // 回填缓存
    return video, nil
} else {
    // 没抢到锁 → 自旋等待别人回填
    for i := 0; i < 5; i++ {
        time.Sleep(20 * time.Millisecond)
        if v, ok := getCached(); ok {
            return v, nil  // 别人已经回填好了
        }
    }
}
```

#### 2.4 Redis 操作超时保护

所有 Redis 操作都有 **50ms 超时**，防止 Redis 慢查询阻塞主线程：

```go
opCtx, cancel := context.WithTimeout(ctx, 50*time.Millisecond)
defer cancel()
_ = cache.ZincrBy(opCtx, windowKey, member, float64(change))
```

### 三、限流层面

#### 3.1 写接口限流

对写操作接口按不同维度限流：

```go
// 按 IP 限流：防止恶意注册/暴力破解
loginLimiter    := ratelimit.Limit(cache, "login",    10, time.Minute, KeyByIP)
registerLimiter := ratelimit.Limit(cache, "register", 5,  time.Hour,   KeyByIP)

// 按用户限流：防止刷点赞/刷评论
likeLimiter    := ratelimit.Limit(cache, "like_write",    30, time.Minute, KeyByAccount)
commentLimiter := ratelimit.Limit(cache, "comment_write", 10, time.Minute, KeyByAccount)
socialLimiter  := ratelimit.Limit(cache, "social_write",  20, time.Minute, KeyByAccount)
```

限流实现基于 **Redis 滑动窗口 + Lua 脚本**，保证原子性：

```go
// 核心限流逻辑
count, err := cache.IncrementWithExpire(ctx, key, window)
if count > maxRequests {
    c.AbortWithStatusJSON(429, gin.H{"error": "too many requests"})
    return
}
c.Next()
```

#### 3.2 令牌桶限流

还有一层全局的令牌桶限流，每秒 1000 请求，桶容量 200：

```go
r.Use(ratelimit.RateLimit())
// 超出则返回 429
```

#### 3.3 未登录用户 Feed 流保护

Feed 流接口使用 `SoftJWTAuth`，未登录用户也能访问，但 `viewerAccountID = 0`，后端会限制未登录用户的查询范围。这既保证了用户体验，又防止了匿名爬虫。

### 四、容错降级层面

#### 4.1 消息队列的双路径降级（核心保障）

所有写操作都采用"先试 MQ，失败降级"的防御性策略：

```
正常路径：
  用户点赞 → Service 校验 → likeMQ.Like() 发布消息 → 返回成功
  → Worker 消费消息 → 写数据库

降级路径（MQ 不可用）：
  用户点赞 → Service 校验 → likeMQ.Like() 失败
  → 本地事务：INSERT likes + UPDATE likes_count + UPDATE popularity
  → 返回成功
```

关键代码：

```go
mysqlEnqueued := true
if s.likeMQ != nil {
    if err := s.likeMQ.Like(ctx, accountID, videoID); err != nil {
        mysqlEnqueued = false  // MQ 挂了，标记降级
    }
}

// MQ 发布失败 → 直接本地事务写入
if !mysqlEnqueued {
    return s.fallbackLikeInTx(ctx, like)  // 本地 ACID 事务兜底
}
```

**MQ 挂了 → 功能降级为同步写入，用户无感知。MQ 恢复 → 自动回到正常路径。**

#### 4.2 Worker 的消息重试

Worker 采用手动 ACK，消费失败时 Nack+Requeue：

```go
// 处理成功 → 确认消费
d.Ack(false)

// 处理失败 → 重新入队重试
d.Nack(false, true)  // requeue = true
```

坏消息（JSON 解析失败、未知 action）直接丢弃，防止死信堆积：

```go
if err := json.Unmarshal(body, &evt); err != nil {
    return nil  // 丢弃，不 Nack
}
```

#### 4.3 热点窗口过期机制

热度窗口 ZSET 设置 2 小时 TTL：

```go
_ = cache.Expire(opCtx, windowKey, 2*time.Hour)
```

自动清理过期的分钟窗口，防止 Redis 内存无限增长。

#### 4.4 防御性 nil 检查

所有外部依赖都做了 nil 保护，确保组件初始化失败不会 panic：

```go
func (c *Client) Ping(ctx context.Context) error {
    if c == nil || c.rdb == nil { return nil }  // 安全返回
    return c.rdb.Ping(ctx).Err()
}

func (c *Client) Lock(...) (string, bool, error) {
    if c == nil || c.rdb == nil { return "", false, nil }
}
```

#### 4.5 Panic 恢复

```go
r.Use(gin.Recovery())  // 捕获 panic，返回 500，进程不挂
```

#### 4.6 Goroutine 安全

使用 `sync.WaitGroup` 和 `GOMAXPROCS` 控制并发 goroutine 数量：

```go
var wg sync.WaitGroup
sem := make(chan struct{}, runtime.GOMAXPROCS(0))  // 信号量，限制并发数

for _, id := range missedL2 {
    wg.Add(1)
    sem <- struct{}{}  // 占用一个槽位
    go func(videoID uint) {
        defer wg.Done()
        defer func() { <-sem }()  // 释放槽位
        // 查数据库...
    }(id)
}
wg.Wait()
```

### 五、异步解耦层面

#### 5.1 写操作全异步化

所有写操作（点赞、评论、关注、热度）都通过 MQ 异步处理：

```
用户请求 → API 发 MQ 消息 → 立即返回
          ↓
          Worker 消费 → 数据库写入
```

效果：用户操作的响应时间不受数据库写入速度影响，API 进程的 QPS 只受限于 MQ 的发布速度（每秒数万级）。

#### 5.2 Outbox 模式保证消息可靠投递

视频发布时，视频记录和 outbox 消息在同一个事务中写入：

```go
err := db.Transaction(func(tx *gorm.DB) error {
    tx.Create(video)        // 写入视频记录
    tx.Create(outboxMsg)    // 写入待投递消息
    return nil
})
```

OutboxPoller 轮询 outbox 表，将消息投递到 MQ：

```
OutboxPoller (每 100ms 轮询)
  → SELECT * FROM outbox_messages WHERE status = 'pending'
  → 投递到 MQ
  → UPDATE status = 'done'
```

保证：**要么都成功，要么都失败，绝不出现"视频写了但消息没发"的情况**。

#### 5.3 幂等设计

Worker 消费消息时，通过数据库约束实现幂等，重复消费不会产生重复数据：

```go
// 点赞：使用唯一索引 (video_id, account_id)
created, _ := likes.LikeIgnoreDuplicate(ctx, &Like{...})
if !created { return nil }  // 已经点赞过了，跳过

// 关注：同样使用联合唯一索引 (follower_id, vlogger_id)
```

### 七、部署运维层面

#### 7.1 Docker Compose 健康检查

所有基础设施服务配置了 healthcheck，确保依赖就绪后才启动应用：

```yaml
services:
  mysql:
    healthcheck:
      test: ["CMD", "mysqladmin", "ping"]
      interval: 5s
      timeout: 5s
      retries: 20
  redis:
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 20
  rabbitmq:
    healthcheck:
      test: ["CMD", "rabbitmq-diagnostics", "ping"]
      interval: 5s
      timeout: 5s
      retries: 20

  backend:
    depends_on:
      mysql:    { condition: service_healthy }
      redis:    { condition: service_healthy }
      rabbitmq: { condition: service_healthy }
```

#### 7.2 自动重启策略

```yaml
restart: always  # 进程崩溃后 Docker 自动重启
```

#### 7.3 数据持久化

```yaml
volumes:
  mysql_data:     # MySQL：/var/lib/mysql
  redis_data:     # Redis：/data
  rabbitmq_data:  # RabbitMQ 数据
```

容器重启、升级都不丢数据。

#### 7.4 静态编译 + 精简镜像

```dockerfile
ENV CGO_ENABLED=0
RUN go build -trimpath -ldflags="-s -w" -o /out/api ./cmd
RUN go build -trimpath -ldflags="-s -w" -o /out/worker ./cmd/worker
```

静态编译 + 去除调试信息，镜像体积小、启动快、运行时依赖少。

### 八、当前薄弱环节与改进方向

客观地说，当前系统也有一些稳定性短板：

| 薄弱环节 | 问题 | 改进方案 |
|---|---|---|
| **无熔断器** | 某个下游持续故障时，请求持续超时浪费资源 | 引入 gobreaker，对 Redis/MySQL/MQ 做熔断 |
| **无应用层健康检查** | 容器编排无法感知应用是否存活 | 添加 `/health`、`/ready` 端点 |
| **连接池未显式配置** | 生产环境可能因连接泄露导致连接耗尽 | 显式配置 MaxOpenConns / MaxIdleConns / MaxRetries |
| **无 Metrics 监控** | 无法量化系统状态 | 接入 Prometheus 指标（QPS、延迟、错误率） |
| **无结构化日志** | 日志难以检索和分析 | 引入 zap/logrus，统一 JSON 格式日志 |
| **无指数退避重试** | Nack+Requeue 可能频繁重试 | 引入死信队列 + 延迟重试机制 |

### 九、总结

从七个维度总结了系统的稳定性保障：

| 维度 | 核心措施 | 效果 |
|---|---|---|
| **架构设计** | API/Worker 分离、优雅关闭、依赖注入可降级 | 组件故障不扩散 |
| **缓存** | 三级缓存 + SingleFlight + 分布式锁 + 50ms 超时 | 缓存挂了服务不挂 |
| **限流** | Redis 滑动窗口 + 多维度限流 + 令牌桶 | 防止流量冲垮 |
| **容错降级** | MQ 双路径降级 + Worker 重试 + 幂等 + nil 保护 | 功能有损但不中断 |
| **异步解耦** | MQ 全异步 + Outbox 模式 | API 响应不受写操作影响 |
| **可观测性** | pprof + 关键路径日志 | 快速定位问题 |
| **部署运维** | Docker healthcheck + 自动重启 + 数据持久化 | 进程崩溃自动恢复 |
