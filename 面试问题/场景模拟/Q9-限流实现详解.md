# 面试问答记录 - 第9轮

## 问题
你的限流是如何实现的？

## 回答

系统的限流方案全部基于 **Redis + Lua 脚本的滑动窗口计数器**，支持多维度限流。整体分为三层：Lua 脚本、Redis 客户端封装、Gin 中间件。

---

### 一、最底层：Redis Lua 脚本

限流的原子性操作由一个 Lua 脚本保证：

```lua
-- KEYS[1]: 限流 key，例如 "feedsystem:ratelimit:login:192.168.1.1"
-- ARGV[1]: 窗口过期时间（毫秒）

local count = redis.call("INCR", KEYS[1])     -- 递增计数器
if count == 1 then
    redis.call("PEXIRY", KEYS[1], ARGV[1])    -- 第一次创建时设过期时间
end
return count                                    -- 返回当前计数
```

**为什么要用 Lua 脚本？** 因为需要原子性——如果分两步走（先 INCR，再 EXPIRE），在 INCR 和 EXPIRE 之间如果进程挂了，这个 key 就变成了"永远不过期的死 key"。

同时注意脚本里的一个关键细节：

```go
var incrementWithExpireScript = redis.NewScript(`
local count = redis.call("INCR", KEYS[1])
if count == 1 then
  redis.call("PEXPIRE", KEYS[1], ARGV[1])
end
return count
`)
```

**只有第一次 INCR（count == 1）时才设置过期时间**。后续的 INCR 不会重置过期时间。

这个设计专门对应测试中的验证：

```go
// 测试：第二次 INCR 不会延长 TTL
mr.FastForward(5 * time.Second)           // 快进 5 秒
ttlBeforeSecond := mr.TTL(key)            // 记录当前 TTL

count, _ = client.IncrementWithExpire(ctx, key, expire)  // 第二次 +1

ttlAfterSecond := mr.TTL(key)
// 验证：TTL 没有变化
if ttlAfterSecond != ttlBeforeSecond {
    t.Fatal("TTL 被重置了！")
}
```

**为什么要设计成不重置 TTL？** 考虑一个场景：限流窗口是 1 分钟，最大 10 次请求。如果一个用户在 1 分钟内连续请求，第 1 秒发了 10 次，之后 59 秒没再请求。如果每次 INCR 都重置 TTL，那么这个 key 会一直存在到"最后一次请求的 1 分钟后"，窗口被无限拉长，限流效果就失效了。

### 二、中间封装层：Redis Client

```go
type Client struct {
    rdb *redis.Client
}

func (c *Client) IncrementWithExpire(ctx context.Context, key string, expire time.Duration) (int64, error) {
    if c == nil || c.rdb == nil {
        return 0, nil                          // 防御：Redis 不可用时放行
    }
    return incrementWithExpireScript.Run(
        ctx,
        c.rdb,
        []string{key},
        expire.Milliseconds(),                 // 转毫秒传给 Lua
    ).Int64()
}
```

所有 Redis 客户端方法都有 **nil 保护**，Redis 挂了不会 panic，只是放行请求（有损降级，但系统不崩溃）。

### 三、最上层：Gin 中间件

```go
func Limit(
    cache      *rediscache.Client,   // Redis 客户端
    keyPrefix  string,               // 业务标识（如 "login", "like_write"）
    maxRequests int64,               // 窗口内最大请求数
    window     time.Duration,        // 时间窗口（如 time.Minute）
    keyFunc    KeyFunc,              // 限流维度函数
) gin.HandlerFunc {
    return func(c *gin.Context) {
        // 1. 参数校验
        if cache == nil || keyFunc == nil || maxRequests <= 0 || window <= 0 {
            c.Next()       // 参数异常 → 放行
            return
        }

        // 2. 提取限流维度（IP 或 用户ID）
        subject, ok := keyFunc(c)
        if !ok {
            c.Next()       // 无法提取维度 → 放行
            return
        }

        // 3. 构造 Redis key
        key := buildKey(keyPrefix, subject)
        // 例如: "feedsystem:ratelimit:like_write:42"

        // 4. 原子性增加计数器
        count, err := cache.IncrementWithExpire(c.Request.Context(), key, window)
        if err != nil {
            c.Next()       // Redis 异常 → 放行
            return
        }

        // 5. 判断是否超限
        if count > maxRequests {
            c.AbortWithStatusJSON(http.StatusTooManyRequests, gin.H{
                "error": "too many requests",
            })
            return
        }

        c.Next()           // 正常放行
    }
}
```

### 四、两种限流维度

```go
// 1. 按 IP 限流 —— 用于登录、注册等场景
func KeyByIP(c *gin.Context) (string, bool) {
    ip := strings.TrimSpace(c.ClientIP())
    if ip == "" {
        return "", false
    }
    return ip, true
}

// 2. 按用户 ID 限流 —— 用于点赞、评论等登录后的操作
func KeyByAccount(c *gin.Context) (string, bool) {
    accountID, err := jwt.GetAccountID(c)
    if err != nil || accountID == 0 {
        return "", false
    }
    return strconv.FormatUint(uint64(accountID), 10), true
}
```

- `KeyByIP`：未登录场景，防止暴力破解和匿名爬虫
- `KeyByAccount`：已登录场景，精准限制每个用户的操作频率

### 五、路由注册 —— 具体配置

```go
// router.go
// 按 IP 限流
loginLimiter    := ratelimit.Limit(cache, "account_login",    10, time.Minute, KeyByIP)
registerLimiter := ratelimit.Limit(cache, "account_register", 5,  time.Hour,   KeyByIP)

// 按用户限流
likeLimiter    := ratelimit.Limit(cache, "like_write",    30, time.Minute, KeyByAccount)
commentLimiter := ratelimit.Limit(cache, "comment_write", 10, time.Minute, KeyByAccount)
socialLimiter  := ratelimit.Limit(cache, "social_write",  20, time.Minute, KeyByAccount)

// 挂载到路由上
accountGroup.POST("/login",    loginLimiter,    accountHandler.CreateAccount)
accountGroup.POST("/register", registerLimiter, accountHandler.Register)
protectedLikeGroup.POST("/like",   likeLimiter,    likeHandler.Like)
protectedLikeGroup.POST("/unlike", likeLimiter,    likeHandler.Unlike)
protectedCommentGroup.POST("/publish", commentLimiter, commentHandler.PublishComment)
protectedSocialGroup.POST("/follow",   socialLimiter,  socialHandler.Follow)
```

各个接口的限流策略：

| 接口 | Key 前缀 | 最大次数 | 窗口 | 维度 | 设计目的 |
|---|---|---|---|---|---|
| 登录 | `account_login` | 10 | 1 分钟 | IP | 防暴力破解 |
| 注册 | `account_register` | 5 | 1 小时 | IP | 防批量注册 |
| 点赞/取消 | `like_write` | 30 | 1 分钟 | 用户 | 防刷赞 |
| 评论发布 | `comment_write` | 10 | 1 分钟 | 用户 | 防刷评论 |
| 关注/取关 | `social_write` | 20 | 1 分钟 | 用户 | 防批量关注 |

Redis key 的完整格式：
```
feedsystem:ratelimit:account_login:192.168.1.100
feedsystem:ratelimit:like_write:42
feedsystem:ratelimit:comment_write:42
```

### 六、降级策略

整个限流系统内置了 **四层安全降级**：

| 层 | 条件 | 行为 | 后果 |
|---|---|---|---|
| 1 | `cache == nil` | 直接放行 | 不限流，功能正常 |
| 2 | `keyFunc` 无法提取维度（如未登录） | 直接放行 | 不限流，功能正常 |
| 3 | `IncrementWithExpire` 返回 error（Redis 挂了） | 直接放行 | 不限流，功能正常 |
| 4 | `count > maxRequests` | 返回 HTTP 429 | 限流生效 |

前三个都是防崩溃的保护：**Redis 挂了，限流功能降级，但服务不挂**。

---

### 七、这套方案的优劣势

#### 优点

1. **原子性**：Lua 脚本保证 INCR + EXPIRE(once) 在 Redis 中原子执行，没有竞态条件
2. **精度高**：计数器精确到每次请求，不是令牌桶那种"匀速"模型
3. **内存友好**：每个限流 key 只占一个 Redis string，窗口过期后自动删除
4. **多维度灵活**：通过 `KeyFunc` 接口可以扩展到任意维度（设备 ID、Session 等）
5. **降级安全**：四层防御，Redis 挂了服务不挂

#### 与令牌桶的对比

| 维度 | 滑动窗口计数器（本项目） | 令牌桶 |
|---|---|---|
| 实现复杂度 | 极简，一个 Lua 脚本 | 较复杂，需要定时填充 |
| 是否允许突发 | 窗口期内用完额度就要等 | 桶容量允许短期突发 |
| 精度 | 精确计数，超出即拒绝 | 平滑速率控制 |
| 适用场景 | 登录、点赞等精确计数场景 | 通用流量整形 |

---

### 八、总结

一句话概括：**"三层结构，一个 Lua 脚本，两种维度，四层降级"**：

```
Gin 中间件层       ratelimit.Limit(cache, "login", 10, 1min, KeyByIP)
     │ 构造 key + 判断是否超限
     ▼
Redis 封装层       IncrementWithExpire(key, window)
     │ 防御性 nil 检查
     ▼
Lua 脚本层         INCR → count==1 时 PEXPIRE → return count
```

这套方案在小到中型规模下完全够用。如果要支持更大的规模和更复杂的限流策略，可以考虑引入**令牌桶**（允许突发流量）或**分布式限流**（Tair/Redis Cluster + 批量扣减）。
