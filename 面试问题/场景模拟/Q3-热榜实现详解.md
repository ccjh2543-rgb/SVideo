# 面试问答记录 - 第3轮

## 问题
具体讲一下热榜的实现。

## 回答

热榜（热度排行）是我们系统中最复杂的一个模块，它涉及**事件触发 → 消息队列 → 异步 Worker → Redis 滑动窗口 → 快照合并 → 稳定分页**的完整链路。我按照数据流向一步步来讲。

---

### 一、热度分的定义

热度分的计算公式很简单：**热度分 = 点赞数 + 评论数**。

视频表里有个 `popularity` 字段，每一次点赞和每一次发布评论都会使 `popularity + 1`，取消点赞使 `popularity - 1`。在数据库层面用原子操作更新：

```go
// 点赞/评论 → +1
db.Model(&Video{}).Where("id = ?", id).
    Update("popularity", gorm.Expr("popularity + ?", change))

// 取消点赞 → 防止负数
db.Model(&Video{}).Where("id = ?", id).
    UpdateColumn("popularity", gorm.Expr("GREATEST(popularity + ?, 0)", change))
```

---

### 二、事件触发：谁会产生热度变化？

两个行为会触发热度事件：

**1. 点赞/取消点赞**（`like_service.go`）
- 用户点赞时：`popularityMQ.Update(ctx, videoID, +1)`
- 用户取消点赞时：`popularityMQ.Update(ctx, videoID, -1)`

**2. 发布评论**（`comment_service.go`）
- 用户评论时：`popularityMQ.Update(ctx, videoID, +1)`

这两个服务都采用了**双路径发送**策略：优先通过 RabbitMQ 异步发送，如果 MQ 不可用，直接调用 `UpdatePopularityCache` 写入 Redis，保证热榜更新的可用性。

---

### 三、RabbitMQ 消息定义

```go
type PopularityEvent struct {
    EventID    string    `json:"event_id"`
    VideoID    uint      `json:"video_id"`
    Change     int64     `json:"change"`      // +1 或 -1
    OccurredAt time.Time `json:"occurred_at"`
}
```

使用 Topic 交换机 `video.popularity.events`，路由键 `video.popularity.update`，由独立的 Worker 进程消费。

---

### 四、滑动窗口（时间桶）设计 —— 最核心的部分

这是整个热榜的精华所在。我们不维护一个全局的"总热度 ZSET"，而是**按分钟拆分成 60 个独立的 ZSET 窗口**。

```go
func UpdatePopularityCache(ctx context.Context, cache *rediscache.Client, id uint, change int64) {
    // 1. 失效视频详情缓存，保证下次读取时拿到最新热度
    _ = cache.Del(context.Background(), fmt.Sprintf("video:detail:id=%d", id))

    // 2. 当前 UTC 时间截断到分钟，构造窗口 key
    now := time.Now().UTC().Truncate(time.Minute)
    windowKey := "hot:video:1m:" + now.Format("200601021504")
    // 例如：hot:video:1m:202604301530

    // 3. ZINCRBY 累加，同一分钟内同视频的多次事件累加到一个 ZSET 里
    member := strconv.FormatUint(uint64(id), 10)
    _ = cache.ZincrBy(opCtx, windowKey, member, float64(change))

    // 4. 每个窗口 TTL 为 2 小时，防止 Redis 内存爆炸
    _ = cache.Expire(opCtx, windowKey, 2*time.Hour)
}
```

**设计要点**：
- **窗口粒度**：1 分钟。key 格式为 `hot:video:1m:{YYYYMMDDHHmm}`
- **累加操作**：`ZINCRBY`，同一分钟内对同一个视频的多次点赞/评论会合并
- **TTL 2 小时**：分钟窗口不会无限堆积，超时自动淘汰
- **50ms 超时**：所有 Redis 操作都有超时控制，不影响主流程

### 五、Worker 异步消费

Worker 进程独立部署，消费 RabbitMQ 的 `video.popularity.events` 队列：

```go
func (w *PopularityWorker) process(ctx context.Context, body []byte) error {
    var evt PopularityEvent
    json.Unmarshal(body, &evt)
    if evt.VideoID == 0 || evt.Change == 0 {
        return nil
    }
    video.UpdatePopularityCache(ctx, w.cache, evt.VideoID, evt.Change)
    return nil
}
```

Worker 采用**手动 ACK**，处理成功 `Ack(false)`，失败 `Nack(false, true)` 重新入队。QoS 设置为 50，即最多 50 个未确认消息，避免 Worker 积压过多。

---

### 六、查询时的快照合并 —— 最巧妙的设计

当用户请求热榜时，不会直接查 60 个 ZSET，而是先**合并成一个快照 ZSET**，然后在这个快照上做分页。

```go
// 1. 构建过去 60 分钟的窗口 key
asOf := time.Now().UTC().Truncate(time.Minute)
keys := make([]string, 0, 60)
for i := 0; i < 60; i++ {
    keys = append(keys, "hot:video:1m:"+asOf.Add(-time.Duration(i)*time.Minute).Format("200601021504"))
}

// 2. ZUNIONSTORE 合并成一个快照（策略：SUM，分数相加）
dest := "hot:video:merge:1m:" + asOf.Format("200601021504")
exists, _ := f.rediscache.Exists(opCtx, dest)
if !exists {
    _ = f.rediscache.ZUnionStore(opCtx, dest, keys, "SUM")
    _ = f.rediscache.Expire(opCtx, dest, 2*time.Minute)
}

// 3. 在快照上做 ZREVRANGE 分页（offset 偏移）
members, err := f.rediscache.ZRevRange(opCtx, dest, start, stop)

// 4. 从 member（视频 ID 字符串）解析出 ID，批量查视频详情
ids := make([]uint, 0, len(members))
for _, m := range members {
    u, _ := strconv.ParseUint(m, 10, 64)
    ids = append(ids, uint(u))
}
videos, _ := f.repo.GetByIDs(ctx, ids)
```

**为什么用 ZUNIONSTORE 而不是直接在 60 个 ZSET 上查？**
- 如果每次翻页都要查 60 个 ZSET，然后做归并排序，性能太差
- 预合并成快照只需要一次 O(N) 操作，后续所有翻页都在快照上 O(logN) 完成

**为什么快照只保留 2 分钟？**
- 因为热度是实时变化的，快照过期后下一次请求会重新合并，保证实时性
- 2 分钟也足够用户在一个快照内完成多页翻看（稳定分页）

---

### 七、稳定分页机制

热榜的分页参数包括：
- `as_of`：快照版本号（分钟时间戳），同一个 `as_of` 内翻页数据不跳动
- `offset`：在快照 ZSET 中的偏移量

前端翻页时带着这两个参数，后端：
```
as_of 相同 → 复用已有快照 → offset 递增 → 结果稳定
as_of 过期 → 重新合并 → offset 重置 → 数据轻微刷新
```

这保证了用户在翻页时不会看到数据跳动或内容重复。

---

### 八、三级降级策略

为了保证可用性，热榜设计了三条路径，层层兜底：

| 级别 | 数据源 | 触发条件 | 分页方式 |
|---|---|---|---|
| L1 | Redis ZSET 快照 | 正常情况 | `ZREVRANGE offset` |
| L2 | Redis ZUNIONSTORE 重建 | 快照过期 | 自动重新合并 |
| L3 | MySQL 三字段游标 | Redis 不可用 | `popularity DESC, create_time DESC, id DESC` |

降级到 MySQL 时，使用三字段游标分页：
```sql
WHERE (popularity < ?) 
   OR (popularity = ? AND create_time < ?) 
   OR (popularity = ? AND create_time = ? AND id < ?)
ORDER BY popularity DESC, create_time DESC, id DESC
```

热度相同比时间，时间相同比 ID，保证绝对不重复不遗漏。

---

### 九、完整数据流总结

```
用户点赞/评论
    │
    ▼
like_service/comment_service ──MQ失败降级──▶ 直接 UpdatePopularityCache
    │
    ▼
RabbitMQ (video.popularity.events)
    │
    ▼
PopularityWorker (异步消费)
    │
    ▼
UpdatePopularityCache
    ├─ 删除视频详情缓存 (保证一致性)
    └─ ZINCRBY 写入对应分钟窗口 ZSET (hot:video:1m:{time})
                      │
                      ▼
用户请求热榜 → ListByPopularity
    ├─ 构建 60 个分钟窗口 key
    ├─ ZUNIONSTORE 合并为快照 (2分钟有效)
    ├─ ZREVRANGE 分页取视频 ID
    ├─ 批量查视频详情
    └─ Redis 不可用 → MySQL 三字段游标降级
                      │
                      ▼
                   前端展示
```

从这个架构可以看出，我们解决的核心问题有三个：
1. **实时性**：分钟级窗口保证热度变化能快速反映到热榜上
2. **稳定性**：快照机制保证翻页过程中数据不跳动
3. **可用性**：三级降级确保 Redis 挂了热榜也不完全不可用
