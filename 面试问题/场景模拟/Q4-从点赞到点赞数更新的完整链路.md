# 面试问答记录 - 第4轮

## 问题
讲一讲从用户点赞到视频点赞数更新，这之间发生了什么？

## 回答

这个问题的本质是让我们**完整走一遍点赞的端到端数据流**。它涉及异步架构、消息队列、降级策略、幂等设计等关键设计决策。我按照正常路径和降级路径两条线来讲。

---

### 一、整体架构概览

点赞系统采用**异步最终一致性模型**，由三个角色协同完成：

```
用户 HTTP 请求
    │
    ▼
┌──────────────────────────────┐
│   API 进程 (like_service.go)  │  ← 接收请求，发布消息
│   1. 校验参数                 │
│   2. 发 MQ 消息               │
│   3. 立即返回成功              │
└──────────┬───────────────────┘
           │
    RabbitMQ (like.events)
           │
           ▼
┌──────────────────────────────┐
│   Worker 进程 (likeworker.go) │  ← 异步消费，写数据库
│   1. 消费消息                 │
│   2. INSERT 点赞记录          │
│   3. UPDATE likes_count       │
│   4. UPDATE popularity        │
└──────────────────────────────┘
```

API 进程"承诺"了点赞操作，Worker 进程异步"兑现"。如果 MQ 不可用，API 进程自己兜底写入。

---

### 二、正常路径详解

#### 第1步：用户发起 HTTP 请求

前端 POST `/api/v1/video/like`，body 里带着 `video_id`。

#### 第2步：Service 层校验（`like_service.go: Like` 方法）

```go
func (s *LikeService) Like(ctx context.Context, like *Like, accountID uint) error {
    // 2.1 参数校验
    if like == nil || like.VideoID == 0 || accountID == 0 {
        return errors.New("video_id and account_id are required")
    }

    // 2.2 检查视频是否存在
    exist, _ := s.VideoRepo.IsExist(ctx, like.VideoID)
    if !exist {
        return errors.New("video not found")
    }

    // 2.3 检查是否已经点赞（防重复）
    isLiked, _ := s.repo.IsLiked(ctx, like.VideoID, accountID)
    if isLiked {
        return errors.New("user has liked this video")
    }

    like.AccountID = accountID
    like.CreatedAt = time.Now()
```

通过了三层校验：参数合法 → 视频存在 → 没重复点赞。

#### 第3步：发布 MQ 消息（核心异步化）

```go
    // 3.1 发布点赞消息到 like.events
    mysqlEnqueued := true
    if s.likeMQ != nil {
        if err := s.likeMQ.Like(ctx, accountID, like.VideoID); err != nil {
            mysqlEnqueued = false  // MQ 不可用，标记降级
        }
    }

    // 3.2 发布热度消息到 video.popularity.events
    redisEnqueued := true
    if s.popularityMQ != nil {
        if err := s.popularityMQ.Update(ctx, like.VideoID, 1); err != nil {
            redisEnqueued = false  // MQ 不可用，标记降级
        }
    }

    // 如果两个消息都发布成功了，直接返回成功，不写数据库
    if mysqlEnqueued && redisEnqueued {
        return nil
    }
```

**关键设计要点**：
- 这里发了**两个独立的 MQ 消息**：一个给 `likeMQ` 写点赞记录，一个给 `popularityMQ` 更新热榜
- MQ 发布失败**不会导致请求失败**，只是标记 `enqueued = false`，后面走降级
- 两个消息是**独立的**——各自有自己的 Exchange、Queue、Worker

#### 第4步：API 进程立即返回

如果 MQ 发布成功，API 进程**不写数据库**，直接 return nil，前端收到 200。

从用户感知的角度，点赞操作已经"完成"了（丝滑体验），实际的数据库写入由 Worker 异步执行。

#### 第5步：RabbitMQ 路由消息

```
Exchange: like.events (topic)
Binding:  like.*
Routing Key: like.like

消息内容:
{
    "event_id": "aB3xK7mN9pQ2wR5t",
    "action": "like",
    "user_id": 42,
    "video_id": 10086,
    "occurred_at": "2026-04-30T15:30:00Z"
}
```

#### 第6步：Worker 消费消息（`likeworker.go`）

Worker 进程独立部署，运行循环监听队列：

```go
func (w *LikeWorker) process(ctx context.Context, body []byte) error {
    var evt rabbitmq.LikeEvent
    if err := json.Unmarshal(body, &evt); err != nil {
        return nil  // 解析失败直接丢弃，不阻塞队列
    }
    if evt.UserID == 0 || evt.VideoID == 0 {
        return nil  // 无效消息直接丢弃
    }

    switch evt.Action {
    case "like":
        return w.applyLike(ctx, evt.UserID, evt.VideoID)
    case "unlike":
        return w.applyUnlike(ctx, evt.UserID, evt.VideoID)
    }
    return nil
}
```

**手动 Ack**：处理成功调 `d.Ack(false)`，失败调 `d.Nack(false, true)` 重新入队。

#### 第7步：Worker 写数据库（`applyLike`）

```go
func (w *LikeWorker) applyLike(ctx context.Context, userID, videoID uint) error {
    // 7.1 检查视频是否还存在（视频可能已删除）
    exist, _ := w.videoRepo.IsExist(ctx, videoID)
    if !exist {
        return nil  // 静默跳过
    }

    // 7.2 插入点赞记录（幂等！重复消费也不会报错）
    created, _ := w.likeRepo.LikeIgnoreDuplicate(ctx, &video.Like{
        VideoID:   videoID,
        AccountID: userID,
    })
    if !created {
        return nil  // 已经点赞过了，跳过
    }

    // 7.3 原子更新点赞数 +1
    w.videoRepo.ChangeLikesCount(ctx, videoID, 1)

    // 7.4 原子更新热度 +1
    w.videoRepo.ChangePopularity(ctx, videoID, 1)

    return nil
}
```

这一步才是**真正的"更新视频点赞数"**发生的地方。这里用了 `LikeIgnoreDuplicate` 做幂等——即使消息被重复投递，`INSERT` 会因为联合唯一索引冲突（MySQL 1062）而被静默忽略，不会重复加赞。

### 三、两个关键降级路径

这是架构中最有防御性的设计：

#### 场景1：MQ 挂了 → 直接写 MySQL

```go
// Service Like 方法中，mq 发布失败后：
if !mysqlEnqueued {
    return s.fallbackLikeInTx(ctx, like)  // 本地事务兜底
}

func (s *LikeService) fallbackLikeInTx(ctx context.Context, like *Like) error {
    return s.VideoRepo.WithTransaction(ctx, func(tx *gorm.DB) error {
        // 再次检查视频存在和重复点赞（事务内）
        // INSERT INTO likes ...
        // UPDATE videos SET likes_count = likes_count + 1 ...
        // UPDATE videos SET popularity = popularity + 1 ...
    })
}
```

一个事务完成所有操作，保证 ACID。

#### 场景2：popularityMQ 挂了 → 直接写 Redis

```go
if !redisEnqueued {
    video.UpdatePopularityCache(ctx, s.cache, like.VideoID, 1)
}
```

热度更新走 Redis 的 `ZINCRBY`，绕过 MQ。

**为什么要分两个降级路径？**
- 点赞记录必须落 MySQL（持久化存储）
- 热度更新可以只写 Redis（缓存场景，丢失可重建）
- 两者独立降级，互不影响

### 四、完整流程图

```
用户点赞请求 POST /api/v1/video/like {video_id: 10086}
    │
    ▼
┌─────────────────────────────────────────────────┐
│  like_service.Like()                              │
│                                                   │
│  ├─ ① 校验参数                                    │
│  ├─ ② 检查视频存在                                 │
│  ├─ ③ 检查是否重复点赞                             │
│  │                                                 │
│  ├─ ④ likeMQ.Like() ────────── 成功? ──→ 标记完成  │
│  │       │ 失败                                    │
│  │       ▼                                         │
│  │   fallbackLikeInTx()                            │
│  │   ├─ INSERT INTO likes                          │
│  │   ├─ UPDATE likes_count + 1                     │
│  │   └─ UPDATE popularity + 1                      │
│  │                                                 │
│  ├─ ⑤ popularityMQ.Update(+1) ─ 成功? ──→ 标记完成 │
│  │       │ 失败                                    │
│  │       ▼                                         │
│  │   UpdatePopularityCache(Redis ZINCRBY)          │
│  │                                                 │
│  └─ ⑥ 返回成功 ←───────────────────────────────     │
└──────────┬──────────────────────────────────────┘
           │
    ┌──────┴──────┐
    ▼              ▼
  MQ 可用         MQ 不可用 → 已通过降级完成
    │
    ▼
┌─────────────────────────────────┐
│  LikeWorker (异步)               │
│                                 │
│  ├─ Consume LikeEvent            │
│  ├─ applyLike()                  │
│  │   ├─ LikeIgnoreDuplicate      │  ← 幂等插入
│  │   ├─ ChangeLikesCount(+1)     │  ← 真正的点赞数更新
│  │   └─ ChangePopularity(+1)     │
│  └─ Ack(false)                   │
└─────────────────────────────────┘
                              │
                              ▼
                       视频点赞数已更新
```

### 五、架构设计亮点总结

1. **异步解耦**：API 进程只做校验和发消息，不写数据库，响应延迟极低（毫秒级），写操作由 Worker 异步完成。

2. **最终一致性**：用户点赞后立即看到响应，数据库可能延迟几百毫秒才更新，但在 99.9% 的场景下用户无感知。

3. **降级兜底**：MQ 挂了不会导致功能不可用，自动降级为同步写数据库。这是"防御性编程"的体现。

4. **幂等设计**：`LikeIgnoreDuplicate` 利用 MySQL 唯一索引，确保消息重复消费不会重复加赞。

5. **消息可靠性**：Worker 手动 Ack/Nack，消费失败重新入队，保证不丢消息。无效消息（解析失败、未知 action）直接丢弃，防止死信堆积。

6. **独立双队列**：点赞记录和热度更新走不同的 MQ Exchange，各自独立消费、独立降级，互不干扰。
