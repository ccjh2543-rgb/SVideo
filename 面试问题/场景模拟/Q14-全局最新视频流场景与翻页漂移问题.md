# 面试问答记录 - 第14轮

## 问题
你的全局最新视频流有实际运用场景吗，当视频发布量非常大的时候翻页漂移怎么办？

## 回答

这个问题问得很尖锐，我从两个角度来客观回答。

---

### 一、全局最新视频流的实际运用场景

先说结论：**在用户端作为独立 Feed 流，实用价值有限；但在架构层面，它是冷热分离策略的有益技术探索。**

#### 实际产品中"纯最新"Feed 流的使用情况

| 产品 | 是否有"最新"Feed | 用户使用情况 |
|---|---|---|
| 抖音 | 首页是推荐流，"最新"在关注Tab融合展示 | 几乎没有纯时间线入口 |
| 微博 | 有"最新"排序，但默认是"推荐" | 使用率很低 |
| YouTube | 订阅源按时间排序，首页仍是推荐 | 订阅Tab是时间线 |
| Instagram | 探索页推荐，关注页算法排序 | 已不再严格按时间线 |

**核心原因**：纯最新 Feed 流最大的问题是**信息质量和用户体验不可控**——最新发布的视频不一定是用户感兴趣的。如果是爬虫批量灌水，最新 Feed 就会被垃圾内容淹没。

#### 这个功能在这个项目中真正扮演的角色

这个功能不是作为"主 Feed"设计的，它承担了 3 个角色：

1. **冷热分离架构的技术验证**：整个 `ListLatest` 最核心的设计不是"按时间排序"这个功能本身，而是展示了如何用 Redis ZSET 做热数据层、MySQL 做冷数据层，再通过 watermark（水位线）做冷热分界。这是面试中展示架构能力的重要模块。

2. **新内容的快速发现通道**：对于刚发布的视频，在进入推荐系统之前，可以通过最新流被少量用户看到，积累初始互动数据。

3. **全局时间线的支撑数据**：`feed:global_timeline` ZSET 包含了最新 1000 条视频的索引，可以用于其他模块——比如推荐系统的"新内容冷启动"或者运营后台的"内容审核排队"。

---

### 二、翻页漂移问题（重点）

先描述清楚问题，再分析是否真的存在。

#### 2.1 用户感知的翻页漂移是什么

```
时间轴：
t0: 用户进入页面，看到 page 1 = [V1, V2, V3, ..., V10]
t1: 用户看完 page 1，准备翻页
    在这期间，新发布了 5 条视频 [V_new1, V_new2, ..., V_new5]
t2: 用户请求 page 2，传游标 cursor = V10.create_time
    预期结果: [V11, V12, V13, V14, V15, V16, V17, V18, V19, V20]
    实际结果:
      - 如果 cursor 仍落在 ZSET 内：从 ZSET 取，不受影响 ✅
      - 如果 cursor 已越过 watermark：走 MySQL 取，仍然正确 ✅
      - 但新视频的插入导致 ZSET 下标偏移，从 ZSET 取可能漏掉数据 ❓
```

#### 2.2 这个实现到底有没有翻页漂移？

**核心结论：采用时间游标分页，理论上是漂移安全的。但因为 ZSET 裁剪机制，在冷热边界附近存在微小漂移风险。**

##### 为什么时间游标分页本身没有漂移

```sql
-- 每次翻页都是这个查询，游标是 create_time
SELECT * FROM videos
WHERE create_time < ?   -- 这个条件是稳定的！
ORDER BY create_time DESC
LIMIT 10
```

关键点：**create_time 是已发布视频的固有属性，不会因为新视频的插入而改变**。这和 OFFSET 分页完全不同：

```
OFFSET 分页（有漂移）：
  Page 1: OFFSET 0 LIMIT 10 → [V1, V2, ..., V10]
  新插入 5 条 → 数据偏移
  Page 2: OFFSET 10 LIMIT 10 → 现在会看到 [V6, V7, ..., V15] ❌ 重复了！

游标分页（无漂移）：
  Page 1: WHERE create_time < T0 LIMIT 10 → [V1, V2, ..., V10]，游标 = V10.time
  新插入 5 条
  Page 2: WHERE create_time < V10.time LIMIT 10 → [V11, V12, ..., V20] ✅ 正确！
```

新视频的 create_time 比 V10.time 更大，`WHERE create_time < V10.time` 的条件**天然过滤掉了新视频**，所以游标分页在逻辑上不会漂移。

##### 但冷热分离带来了实际却的漂移风险

我们在 ListLatest 中做了冷热分离，问题出在这里：

```
ZSET (热数据)           MySQL (冷数据)
┌──────────────┐       ┌──────────────┐
│ V1  (最新)     │       │ V501         │
│ V2            │       │ V502         │
│ ...           │       │ ...          │
│ V1000 (最老)   │ ← watermark → │ V1001        │
└──────────────┘       └──────────────┘
```

**翻页漂移场景**：

```
t0: ZSET has [V1, V2, ..., V1000], watermark = V500.create_time (假设裁剪到500条)
   用户请求 page 1，cursor=0 → 从 ZSET 取 [V1~V20]
   返回页末游标 cursor = V20.create_time → 传给前端

t1: 新发布 50 条视频 [V_new1 ~ V_new50]
   ZRemRangeByRank → 裁剪到最新的 500 条
   原来在 ZSET 中的 V20~V500 被挤到了 50~530 的位置？
   不，更严重——V1~V50 都被挤出了 ZSET
   watermark 前移了 50 位

t2: 用户请求 page 2，传入 cursor = V20.create_time
   此时 V20 还在 ZSET 中吗？
   如果 ZSET 只保留 500 条，新加了 50 条
   那么原来位置 1~50 的被挤出 → V20 确定被挤出了
   
   请求进入 MySQL 路径：
   SELECT * FROM videos WHERE create_time < V20.create_time LIMIT 20
   
   这个查询返回的结果是[V21, V22, ..., V40] ✅ 仍然正确！

t3: 但如果用户的 cursor 正好等于 old_watermark
   而 old_watermark 对应的视频刚好被挤出 ZSET
   新请求到 MySQL，也仍然正确... 因为 create_time 条件不变
```

**结论：即使有冷热分离，单次翻页在逻辑上也不漂移。** MySQL 的查询条件 `create_time < cursor` 和 ZSET 的查询条件 `score < cursor` 给出的是同一批数据。

##### 但有一个实际体验问题：冷热边界处的"断档"

```
t0: ZSET 有 V1~V500，watermark = V500.create_time
   用户 page 5 的游标是 V95.create_time ← 还在热区
   用户 page 6 的游标是 V115.create_time ← 还在热区
   ...

t1: 新发布 50 条视频
   ZSET 裁剪后 watermark 前移了 50 位
   现在 watermark = V450.create_time

t2: 用户请求 page 6（游标 V115.create_time）
   V115 还在热区吗？ 115 < 450 → 是
   正常返回 [V116~V135]

t_max: 新发布 500 条视频后
   ZSET 全换了，watermark = V1000.create_time
   用户游标 = V115.create_time
   V115 << watermark → 走 MySQL
   正常返回 [V116~V135] ✅ 还是对的
```

**所以即使是长时间的跨页翻看，只要 create_time 条件不变，MySQL 返回的结果也不变。** 真正有感知的漂移不是"数据错了"，而是"翻到某页时突然响应变慢了"——因为从 ZSET 的 O(logN) 降级到了 MySQL 的 O(N) 查询。

#### 2.3 真正的问题：高并发写入下的三种退化

虽然翻页不漂移，但高并发写入场景下，这个方案有三种退化行为：

##### 退化一：ZSET 频繁裁剪 → 所有翻页都打 MySQL

```
每秒发布 100 条视频
ZSET 只保留 1000 条
→ 10 秒后整个 ZSET 就换了一轮
→ 用户翻第二页（10 秒后），cursor 必然在冷区
→ 所有翻页请求都穿透到 MySQL
→ ZSET 变成了几乎没有意义的缓存层
```

ZSET 缓存的"命中窗口"只有 10 秒。这 10 秒内用户能刷多少页？如果每页 20 条，大概刷 1-2 页就没命中率了。**ZSET 变成了"首屏加速器"，仅此而已。**

##### 退化二：MySQL 成为瓶颈

当所有翻页都穿透到 MySQL 时，`WHERE create_time < ? ORDER BY create_time DESC LIMIT 20` 这个查询如果 create_time 上有索引，性能其实尚可，但如果并发量很大（比如 1000 QPS），MySQL 仍然可能扛不住。

##### 退化三：冷热边界处的"重复/遗漏"假象

虽然时间游标不会漂移，但有一个边界问题：

```
ZSET 返回: [V1, V2, ..., V20]
游标 = V20.create_time (设为 T20)

但 ZSET 中可能还有 V19', V18', ... 
这些视频和 V19, V18 的 create_time 完全一样(相同毫秒)

当 cursor=T20 时，MySQL 的 WHERE create_time < T20
会漏掉 create_time == T20 的其他视频！
```

这就是**时间精度不够的问题**——如果有两个视频在同一个毫秒发布，时间游标会漏掉其中一个。项目中用的是毫秒时间戳，这个概率虽然低，但在高并发写入场景下是有可能发生的。

### 三、如果真的要解决这些问题

#### 方案一：游标加 ID 做双字段兜底（推荐）

```go
// 游标从单字段改为双字段
type LatestCursor struct {
    CreateTime int64  // 毫秒时间戳
    ID         uint   // 视频 ID 兜底
}

// SQL 改为：
WHERE (create_time < ?) OR (create_time = ? AND id < ?)
ORDER BY create_time DESC, id DESC
```

这样同毫秒的视频也能被精确分页，不漏不重。

#### 方案二：ZSET 扩容 + 自适应裁剪

```go
// 根据写入频率动态调整 ZSET 大小
var zsetCapacity int64 = 1000
writeRate := getVideoPublishRate()  // 每秒发布量

// 目标是让 ZSET 至少覆盖 5 分钟的翻页量
zsetCapacity = max(1000, writeRate * 60 * 5)

// 对应的裁剪
ZRemRangeByRank(ctx, timelineKey, 0, -(zsetCapacity+1))
```

写入量大时自动扩大 ZSET 容量，保证热数据能覆盖用户正常的翻页深度。

#### 方案三：前端预加载 + 本地缓存分页

前端在请求 page 1 时，后端一次性返回 page 1 + page 2 的数据，前端缓存起来。用户翻到 page 2 时直接从本地取，网络延迟和漂移问题都解决了。

#### 方案四：问清楚这个功能的产品定位（最重要的）

如果产品经理说"要给用户一个最新发布 Tab"，我会反问：

1. **用户真的需要纯时间线吗？** 还是更想要"按时间排序的我关注的人"？（这是关注流做的事）
2. **新视频怎么冷启动？** 是否应该用推荐算法推给可能感兴趣的人，而不是扔进时间线等曝光？
3. **能接受爬虫内容污染首页吗？** 没有内容审核的纯时间线很容易被灌水。

大多数情况下，答案都是"不需要独立的全局最新流"。

### 四、客观总结

| 问题 | 回答 |
|---|---|
| **有实际运用场景吗？** | 作为用户端独立 Feed 流，场景有限。更具价值的是作为**冷热分离架构的技术验证**和**推荐系统的新内容冷启动通道**。 |
| **翻页会漂移吗？** | **时间游标本身不会漂移**。`WHERE create_time < cursor` 的条件不受新数据插入影响。但 ZSET 裁剪 + 冷热分离引入了一个微小边界问题：同毫秒精度的视频可能被遗漏。 |
| **高并发写入下的退化？** | ① ZSET 命中窗口大幅缩短（仅 10 秒左右）→ 翻页快速穿透到 MySQL；② MySQL 压力增大；③ 毫秒级精度的边界丢失。 |
| **最应该改进什么？** | 游标从单字段 `create_time` 改为双字段 `(create_time, id)`，彻底消除同毫秒精度问题。其次是动态调整 ZSET 容量。 |
