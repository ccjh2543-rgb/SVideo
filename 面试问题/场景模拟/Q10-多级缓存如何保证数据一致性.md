# 面试问答记录 - 第10轮

## 问题
多级缓存的数据一致性如何解决？

## 回答

这个问题需要先明确我们系统中有哪些多级缓存场景，然后针对每种场景分别说明一致性策略。

---

### 一、系统中存在的多级缓存场景

我们这个项目涉及三种多级缓存场景：

| 场景 | 缓存层级 | 不一致的主要来源 |
|---|---|---|
| **Feed 流三级缓存** | L1 本地内存(3s) → L2 Redis(24h) → L3 MySQL | L1/L2 的 TTL 时间内数据可能已过时 |
| **视频详情缓存** | Redis `video:detail`(5min) → MySQL | 点赞数/热度变更后缓存未及时失效 |
| **热度排行榜** | Redis ZSET 分钟窗口 → MySQL popularity 字段 | MQ 异步导致 MySQL 和 Redis 短暂不一致 |

---

### 二、核心一致性策略：Cache-Aside + 写时失效

整个系统的一致性策略可以概括为一句话：**"读时回填，写时失效，TTL 兜底"**。

```
读操作（Cache-Aside Pattern）：
  请求 → 查缓存 → 命中 → 返回
                → 未命中 → 查数据库 → 回填缓存 → 返回

写操作（Write-Invalidate）：
  写数据库 → 删除缓存（或将要删除的消息投递到 MQ）
    ↓
  下次读 → 缓存未命中 → 重新从 DB 加载 → 回填缓存
```

这种方案比"写时更新（Write-Update）"更简单可靠，因为：
- 写时删除是幂等的——删一个不存在的 key 也没关系
- 写时更新需要处理并发写的问题（两个写同时更新缓存，后写的可能覆盖了先写的值）

---

### 三、场景一：Feed 流三级缓存

#### 缓存结构

```
L1：go-cache（进程内内存）     TTL = 3 秒
L2：Redis 的 video:entity:N    TTL = 24 小时
L3：MySQL
```

#### 数据流

```go
func (f *FeedService) GetVideoByIDs(ctx context.Context, videoIDs []uint) ([]*video.Video, error) {
    // Step 1: L1 本地缓存
    for _, id := range videoIDs {
        if v, found := f.localcache.Get(key); found {
            videoMap[id] = v  // ✅ L1 命中，3秒内不穿透
            continue
        }
        missedL1 = append(missedL1, id)
    }

    // Step 2: L2 Redis（批量 MGet）
    results, err := f.rediscache.MGet(ctx, cacheKeys...)
    if err == nil {
        for i, res := range results {
            if res != nil {
                videoMap[id] = decode(res)
                f.localcache.Set(key, v, 5*time.Second)  // 回填 L1
                continue
            }
            missedL2 = append(missedL2, id)
        }
    }

    // Step 3: L3 MySQL（SingleFlight 保护）
    v, err, _ := f.requestGroup.Do(sfKey, func() {
        return f.repo.GetByIDs(ctx, []uint{videoID})
    })
    go func() {
        f.rediscache.SetBytes(ctx, cacheKey, b, time.Hour)  // 回填 L2
        f.localcache.Set(cacheKey, v, 5*time.Second)        // 回填 L1
    }()
}
```

#### 一致性保证

| 层 | 保证等级 | 说明 |
|---|---|---|
| L1 → L2 | **最终一致，~3秒** | L1 的 3 秒 TTL 保证最坏情况下 3 秒后自动从 L2 刷新 |
| L2 → MySQL | **最终一致，取决于失效时机** | TTL 24 小时作为兜底，实际通过写操作主动失效 |
| 跨实例 L1 | **不保证一致** | 每个实例独立缓存，不互相感知 |

**关键点：L1 缓存为什么可以容忍不一致？**

Feed 流场景的核心特性是：用户刷 Feed 时，3 秒前的内容是否"绝对最新"并不重要。用户看到一条视频 3 秒前是 100 个赞还是 101 个赞，几乎没有感知。所以 3 秒的 TTL 在用户体验上是完全可以接受的。

### 四、场景二：视频详情缓存（视频详情 + 点赞数）

这是对一致性要求最高的场景——用户点了赞，期望立刻看到点赞数变化。

#### 一致性策略：写时主动失效

变更链路1（点赞/评论触发热度变化）：

```
用户点赞
    ↓
API 进程 → popularityMQ.Update(videoID, +1)
    ↓
PopularityWorker → UpdatePopularityCache(videoID, +1)
    ├─ cache.Del("video:detail:id=10086")      ← 主动删除缓存
    └─ cache.ZincrBy("hot:video:1m:...", +1)   ← 更新热榜
```

变更链路2（视频被删除）：

```go
func (vs *VideoService) Delete(ctx context.Context, id uint, authorID uint) error {
    vs.repo.DeleteVideo(ctx, id)              // 先删数据库
    _ = vs.cache.Del(context.Background(),    // 再删缓存
        fmt.Sprintf("video:detail:id=%d", id))
    return nil
}
```

变更链路3（直接更新热度——MQ 降级路径）：

```go
func (vs *VideoService) UpdatePopularity(ctx context.Context, id uint, change int64) error {
    // 1. 先更新 MySQL（GORM Expr 原子操作）
    vs.repo.UpdatePopularity(ctx, id, change)

    // 2. 尝试发 MQ 消息
    if vs.popularityMQ != nil {
        if err := vs.popularityMQ.Update(ctx, id, change); err == nil {
            return nil  // MQ 发送成功，由 Worker 负责删缓存
        }
    }

    // 3. MQ 不可用 → 直接删缓存（降级路径）
    if vs.cache != nil {
        _ = vs.cache.Del(context.Background(), "video:detail:id=%d", id)
        // 同时直接更新热榜 ZSET
        _ = vs.cache.ZincrBy(opCtx, windowKey, member, float64(change))
    }
}
```

#### 时序分析：最坏情况下的不一致窗口

```
t0: 用户 A 点赞视频 10086
t1: API 进程调用 likeMQ.Like()，发送消息到 RabbitMQ
t2: API 进程调用 popularityMQ.Update()，发送消息
t3: API 返回 200 OK 给用户 A
    ↓
t4: PopularityWorker 消费到消息 → DEL video:detail:id=10086  ← 缓存被删
t5: LikeWorker 消费到消息 → UPDATE likes_count +1
    ↓
t6: 用户 B 请求视频详情 → 缓存未命中 → 查 MySQL → 回填新数据
```

**不一致窗口** = max(t4, t5) - t0。如果 Worker 延迟在百毫秒级别，用户 A 看到"点赞成功"后，用户 B 可能还需要几百毫秒才能看到点赞数更新。对于同一用户（用户 A），如果点赞后立即刷新页面，请求可能先触达 API 进程，而 Worker 还没消费完消息，这时用户 A 自己看到的点赞数也还没变。

**但关键路径有自动修复机制**：用户 A 点赞后，PopularityWorker 会删除缓存，下次任何用户的请求都会触发缓存重建，从 MySQL 拉取最新数据。所以**最多经过一次"缓存未命中→回填"的周期**，数据就一致了。

### 五、场景三：热度排行榜

#### 一致性模型：最终一致 + 快照隔离

热度排行榜的一致性要求比点赞数更低——热榜上的排序不需要实时精确到秒。

```
MySQL popularity（真实热度，持久化）
    ↓ 异步写入（可能延迟几秒）
Redis ZSET 分钟窗口（hot:video:1m:{time}）
    ↓ ZUNIONSTORE 合并（按需）
Redis 快照（hot:video:merge:1m:{time}, TTL 2分钟）
    ↓ ZREVRANGE 分页
用户看到的热榜
```

**三层数据可能不一致的原因**：

1. **分钟窗口的天然延迟**：同一分钟内的多个事件通过 ZINCRBY 累加，但只有这一分钟结束后，这个窗口的数据才"完整"

2. **快照的 2 分钟 TTL**：同一个 `as_of` 快照在 2 分钟内不变，即使新的热度事件已经写入到了新的分钟窗口

3. **MQ 异步的延迟**：热度事件从触发到被 Worker 消费写入 Redis，有毫秒到秒级的延迟

**为什么可以接受？**

热榜本身就是一个"相对"的排序——用户并不要求热榜精确到秒。只要在分钟级别上反映真实热度趋势，就达到了产品目标。

### 六、存在的隐患与改进方向

#### 隐患1：MQ 异步更新 MySQL 后，没有删除视频详情缓存

这是一个比较关键的问题。看 LikeWorker 的流程：

```go
// LikeWorker.applyLike
w.videos.ChangeLikesCount(ctx, videoID, 1)   // MySQL likes_count +1
w.videos.ChangePopularity(ctx, videoID, 1)    // MySQL popularity +1
// ❌ 没有删除 video:detail:id=N 缓存
// ❌ 没有删除 video:entity:N 缓存
```

而 `UpdatePopularityCache`（由 PopularityWorker 执行）会删除 `video:detail` 缓存，但 `video:entity` 缓存（Feed 流三级缓存的 L2）**不会被删除**，只能等 24 小时 TTL 自然过期。

这意味着：Feed 流中显示的视频点赞数，最长可能 **24 小时** 后才更新。

**改进方案**：在 LikeWorker 中补充缓存失效逻辑：

```go
func (w *LikeWorker) applyLike(ctx context.Context, userID, videoID uint) error {
    // ... 原有逻辑 ...

    w.videos.ChangeLikesCount(ctx, videoID, 1)
    w.videos.ChangePopularity(ctx, videoID, 1)

    // ✅ 补充：主动失效所有相关缓存
    detailKey := fmt.Sprintf("video:detail:id=%d", videoID)
    entityKey := fmt.Sprintf("video:entity:%d", videoID)
    _ = w.cache.Del(ctx, detailKey, entityKey)

    return nil
}
```

#### 隐患2：跨实例 L1 缓存不一致

L1 是进程内缓存，如果部署了多个 API 实例，实例 A 的 L1 缓存失效了，实例 B 的还可能有效。这个问题在 Feed 流场景中影响不大（3 秒 TTL），但对一致性要求高的场景可以考虑：

1. **通过 Redis Pub/Sub 广播失效消息**：写操作发生时，通知所有实例删除本地缓存
2. **或者直接放弃 L1 缓存**：只在 TTL 极短的场景下使用（≤ 3 秒）

#### 隐患3：无主动补偿机制

当前系统没有定期校验 MySQL 和 Redis 数据一致性的后台任务。如果因为 bug 或其他原因导致缓存长期不一致，没有自动修复手段。

**改进方案**：添加一个定时任务，定期比对热门视频的 MySQL popularity 和 Redis ZSET 分数，发现不一致时自动纠正。

---

### 七、总结

| 缓存场景 | 一致性策略 | 不一致窗口 | 可接受度 |
|---|---|---|---|
| Feed 流 L1 本地缓存 | TTL 3s 自动过期 | ~3 秒 | ✅ Feed 流场景可接受 |
| Feed 流 L2 Redis 缓存 | TTL 24h + 写时未失效(❌) | 可能很长 | ⚠️ 需要改进 |
| 视频详情 Redis 缓存 | 写时主动失效（Cache-Aside） | ~秒级（取决于 MQ 延迟） | ✅ 用户体验可接受 |
| 热度排行榜 | 分钟窗口 + 快照隔离 | ~分钟级 | ✅ 热榜场景可接受 |

整个系统的设计哲学是 **"性能优先，最终一致，写时尽力失效"**。对于 Feed 流这种场景，用户不要求秒级绝对精确，所以用 TTL 兜底是合理的。但对于点赞数这种用户感知强的数据，应当在写操作完成后主动删除缓存。

**如果要求强一致性**（比如支付场景），就不能用这套多级缓存方案了，需要在读操作时加锁或直接穿透到 MySQL，但这会牺牲性能——这就是 CAP 理论中一致性和可用性的权衡。
