# 面试问答记录 - 第13轮

## 问题
你的项目采用推模式还是其他模式，具体是怎么实现的，有改进的地方吗？

## 回答

这是一个非常好的架构问题。在 Feed 流系统中，"推"和"拉"通常指的就是关注流（Following Feed）的实现策略。我们项目**不是单一模式，而是四种 Feed 类型各用了不同的策略**。

---

### 一、项目中四种 Feed 流的策略

| Feed 类型 | 采用的模式 | 数据来源 |
|---|---|---|
| **最新视频流** `ListLatest` | **推模式（推送到全局 ZSET）** | Redis ZSET `feed:global_timeline` + MySQL 冷数据 |
| **关注流** `ListByFollowing` | **纯拉模式** | MySQL 子查询 `WHERE author_id IN (SELECT vlogger_id FROM social ...)` |
| **点赞数排行** `ListLikesCount` | **数据库排序** | MySQL `ORDER BY likes_count DESC, id DESC` |
| **热度推荐流** `ListByPopularity` | **聚合计算** | Redis ZSET 窗口合并 + MySQL 降级 |

详细说两种核心模式：

---

### 二、最新视频流 —— "推送到全局 ZSET" 模式

这不是传统意义上"推送到每个粉丝的 Inbox"，而是一种**简化的推送模式——推送到一个全局时间线**，所有人都读同一个 ZSET。

#### 实现链路

```
视频发布
    │
    ▼
┌─────────────────────────────────────────┐
│  Publish API                             │
│  DB 事务: INSERT videos + INSERT outbox  │  ← Outbox 模式保证原子性
└─────────────────────────────────────────┘
    │
    ▼  OutboxPoller 轮询（每秒一次）
┌─────────────────────────────────────────┐
│  SELECT * FROM outbox WHERE status=pending │
│  → TimelineMQ.Publish(videoID, createTime)│
│  → DELETE FROM outbox (投递成功)         │
└─────────────────────────────────────────┘
    │
    ▼  Timeline Consumer
┌─────────────────────────────────────────┐
│  ZADD feed:global_timeline              │
│  Score = 发布时间戳                      │
│  Member = videoID                       │
│  ZRemRangeByRank 0 -1001 (只保留1000条)  │
└─────────────────────────────────────────┘
    │
    ▼  ListLatest 读取
┌─────────────────────────────────────────┐
│  ZSET 未命中 → 冷热分离                  │
│  ├─ 热数据：ZRevRangeByScore → 查详情    │
│  ├─ 冷数据：MySQL ListLatest → 返回      │
│  └─ 冷热拼接：热数据不够时从 MySQL 补全   │
└─────────────────────────────────────────┘
```

关键代码：

```go
// OutboxPoller：轮询 outbox 表投递消息
func StartOutboxPoller(db *gorm.DB, tmq *rabbitmq.TimelineMQ) {
    for {
        var messages []video.OutboxMsg
        db.Where("status = ?", "pending").Order("create_time ASC").Limit(100).Find(&messages)

        for _, msg := range messages {
            tmq.PublishVideo(context.Background(), msg.VideoID, msg.CreateTime)
            db.Delete(&msg)  // 投递成功，删除记录
        }
        time.Sleep(1 * time.Second)
    }
}

// Timeline Consumer：写入全局 ZSET
timelineKey := "feed:global_timeline"
redisClient.ZAdd(ctx, timelineKey, oredis.Z{
    Score:  float64(event.CreateTime),
    Member: fmt.Sprintf("%d", event.VideoID),
})
redisClient.ZRemRangeByRank(ctx, timelineKey, 0, -1001) // 裁剪到 1000 条
```

#### 读时的冷热分离

```go
func (f *FeedService) ListLatest(ctx context.Context, limit int, latestBefore time.Time, ...) {
    // 1. 检查 ZSET 最老数据的 watermark
    zsetTail, _ := f.rediscache.ZRangeWithScores(ctx, "feed:global_timeline", 0, 0)
    watermark := int64(zsetTail[0].Score)  // 冷热分界线

    if reqTime <= watermark {
        // 冷数据：查 MySQL
        videos = f.repo.ListLatest(ctx, limit, latestBefore)
    } else {
        // 热数据：查 Redis ZSET
        videoIDs = f.rediscache.ZRevRangeByScore(ctx, "feed:global_timeline", ...)
        // 如果热数据不足 limit 条，从 MySQL 补全
        if len(videos) < limit {
            coldVideos = f.repo.ListLatest(ctx, remainLimit, coldCursor)
            videos = append(videos, coldVideos...)
        }
    }
}
```

### 三、关注流 —— 纯拉模式

关注流的实现是最朴素的**拉模式**：

```go
func (repo *FeedRepository) ListByFollowing(ctx context.Context, limit int, viewerAccountID uint, latestBefore time.Time) ([]*video.Video, error) {
    // 子查询：查我关注了谁
    followingSubQuery := repo.db.WithContext(ctx).
        Model(&social.Social{}).
        Select("vlogger_id").
        Where("follower_id = ?", viewerAccountID)

    // 主查询：查这些人的视频
    query := repo.db.WithContext(ctx).Model(&video.Video{}).
        Where("author_id IN (?)", followingSubQuery).
        Order("create_time DESC")

    if !latestBefore.IsZero() {
        query = query.Where("create_time < ?", latestBefore)
    }

    return query.Limit(limit).Find(&videos).Error
}
```

**没有 Fan-out on Write**，不预写任何 Inbox。每次请求实时查询社交关系表，然后查出关注博主的视频。

### 四、当前架构的优缺点分析

#### 最新流（推送到全局 ZSET）的优缺点

| 维度 | 评价 |
|---|---|
| **优点** | 实现简单，只有 1 个全局 ZSET，不是 N 个用户 Inbox |
| **优点** | 冷热分离设计合理，最近视频走 Redis，旧的走 MySQL |
| **优点** | 裁剪机制（ZRemRangeByRank）防止 ZSET 无限膨胀 |
| **缺点** | **所有用户看到的最新流完全一样**，没有个性化 |
| **缺点** | 裁剪到 1000 条后，更久的内容每次都查 MySQL |
| **缺点** | 全局 ZSET 在千万级视频量下会成为瓶颈 |

#### 关注流（纯拉模式）的优缺点

| 维度 | 评价 |
|---|---|
| **优点** | **零写放大**——发布视频完全不需要写任何人的 Inbox |
| **优点** | 实现极简单，一个子查询搞定 |
| **缺点** | **读放大严重**——每次刷新都要 JOIN social 表 + 关联 videos 表 |
| **缺点** | 用户关注的博主越多，子查询返回的 ID 列表越长，性能越差 |
| **缺点** | 没有缓存预热，首次加载慢 |

**核心矛盾**：推模式是"以空间换时间"（提前算好存起来），拉模式是"以时间换空间"（读的时候现算）。我们的选择是拉模式——因为项目规模下，MySQL 子查询的性能可以接受，而推模式带来的复杂度不值得。

### 五、改进方案

如果要支撑百万级用户、千万级视频，我建议以下改进：

#### 改进一：关注流改为推模式（分层推送）

**核心思路**：博主发布视频时，异步推送到所有粉丝的 Inbox（Redis List/ZSET）。

```go
// 视频发布时（异步，由 Worker 执行）
func fanoutOnWrite(ctx context.Context, videoID uint, authorID uint, createTime time.Time) {
    // 1. 查作者的粉丝列表（分页，防止粉丝太多一次查不完）
    const batchSize = 1000
    var cursor uint = 0
    for {
        followers, _ := socialRepo.GetFollowersByPage(ctx, authorID, cursor, batchSize)
        if len(followers) == 0 {
            break
        }

        // 2. 对每个粉丝，写入 Inbox
        for _, follower := range followers {
            inboxKey := fmt.Sprintf("feed:inbox:%d", follower.FollowerID)
            redisClient.ZAdd(ctx, inboxKey, redis.Z{
                Score:  float64(createTime.UnixMilli()),
                Member: fmt.Sprintf("%d", videoID),
            })
            redisClient.ZRemRangeByRank(ctx, inboxKey, 0, -501) // 每个 Inbox 保留 500 条
        }

        cursor = followers[len(followers)-1].ID
    }
}
```

但是要处理**大 V 问题**：如果一个博主有 1000 万粉丝，推送 1000 万次写操作会打崩系统。

**解决方案：推拉结合（Hybrid）**

```go
// 根据粉丝数决定策略
func fanout(ctx context.Context, videoID uint, authorID uint, fansCount int64, createTime time.Time) {
    const fansThreshold int64 = 100000  // 10 万粉丝阈值

    if fansCount <= fansThreshold {
        // 普通用户 → 推模式：逐个写入粉丝 Inbox
        fanoutToInboxes(ctx, videoID, authorID, createTime)
    } else {
        // 大 V → 拉模式：只写一个"大 V 时间线"，粉丝读的时候合并
        starKey := fmt.Sprintf("feed:star_timeline:%d", authorID)
        redisClient.ZAdd(ctx, starKey, redis.Z{
            Score:  float64(createTime.UnixMilli()),
            Member: fmt.Sprintf("%d", videoID),
        })
    }
}

// 读关注流时
func readFollowingFeed(ctx context.Context, userID uint, ...) {
    // 1. 从自己的 Inbox 读（普通用户的推送内容）
    inboxKey := fmt.Sprintf("feed:inbox:%d", userID)
    inboxVideos, _ := redisClient.ZRevRange(ctx, inboxKey, 0, limit)

    // 2. 查关注的大 V 列表
    starAuthors, _ := socialRepo.GetFollowingStarAuthors(ctx, userID)
    for _, author := range starAuthors {
        starKey := fmt.Sprintf("feed:star_timeline:%d", author.ID)
        starVideos, _ := redisClient.ZRevRangeByScore(ctx, starKey, ...)
        allVideos = merge(allVideos, starVideos)
    }

    // 3. 归并排序后返回
    return sortByTime(allVideos)
}
```

这就是微博/Twitter 采用的经典方案。

#### 改进二：关注流缓存预热

当前关注流的 Redis 缓存 key 包含 `before` 时间戳：

```
feed:listByFollowing:limit=20:accountID=42:before=1746000000000
```

问题是每次翻页的 `before` 都不同，导致**缓存命中率极低**——用户每往下翻一页，都是一个新的 key，都要重新查数据库。

**改进**：缓存"第一页"，后续翻页用拉模式从第二页开始实时计算：

```go
// 只缓存第一页（latestBefore == 0）
if latestBefore.IsZero() {
    cacheKey := fmt.Sprintf("feed:listByFollowing:page1:accountID=%d", viewerAccountID)
    // 命中 → 直接返回
    // 未命中 → 查 DB → 回填缓存
} else {
    // 翻页 → 不缓存，直接查 DB
}
```

这样每个用户只需要缓存 1 个 key，缓存命中率大幅提升。

#### 改进三：延迟合并 + 异步预加载

对于"最新流"的冷热分离，可以进一步优化：

```
ZSET 中的视频（热数据）：最多 1000 条
    ↓ 不够分页时
触发异步任务：将下一批冷数据预加载到 ZSET
    ↓
ZSET 扩到 2000 条，用户翻页不卡顿
    ↓
后台任务持续从 MySQL 拉取旧数据预热到 ZSET
```

这样用户翻到第 5 页、第 10 页时，数据可能还在 ZSET 中，不会突然"卡一下"去查 MySQL。

#### 改进四：列表缓存（List Caching）替代全量缓存

对于点赞数排行和热度排行，当前方案每次翻页都重新查询。可以改用列表缓存：

```go
// 定时任务：每分钟计算一次热门榜前 500
cacheKey := "feed:top_likes:1m"
// 计算结果存为一个有序列表（Redis List 或 ZSET）
// 用户翻页时直接从这个列表里取，不用每次都查库
// 每分钟刷新一次，用户在这一分钟内翻页完全不走数据库
```

### 六、改进优先级总结

| 优先级 | 改进项 | 效果 | 复杂度 |
|---|---|---|---|
| **P0** | 关注流第一页缓存（去掉 before 维度） | 缓存命中率从 ≈0% 到接近 100% | 低 |
| **P1** | 推拉结合（Hybrid）解决关注流性能 | 支撑百万级用户 | 高 |
| **P2** | 热门榜列表缓存（每分钟预计算） | 热门榜翻页不查库 | 中 |
| **P3** | 冷热分离 ZSET 预加载 | 最新流翻页更平滑 | 中 |

### 七、总结

当前项目采用**多模式混合**的策略：

- **最新流**：推模式（推送到全局 ZSET）+ 冷热分离
- **关注流**：纯拉模式（子查询 JOIN）
- **点赞排行/热度排行**：数据库排序 / Redis 聚合

对于项目当前规模（演示/面试项目），这个选择是合理的——实现简单，功能完整。如果要支撑更大规模，核心要改的是**关注流**：从纯拉模式改为**推拉结合**，同时配合**列表缓存**和**异步预加载**来减少数据库压力。
