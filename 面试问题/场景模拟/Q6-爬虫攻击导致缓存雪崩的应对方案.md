# 面试问答记录 - 第6轮

## 问题
如果现在有一个爬虫，反复爬取冷门数据，造成热数据在缓存中被删除，从而导致缓存雪崩等问题，你有什么应对方案？

## 回答

这是一个非常好的系统设计问题。我先分析一下这个场景的**问题本质**，然后从**当前项目已有的防御**到**需要补充的策略**，分层来讲。

---

### 一、问题本质分析

爬虫攻击造成的缓存问题有两个阶段：

**第一阶段：缓存污染（Cache Pollution）**
```
爬虫反复请求冷门视频ID（比如 ID=1,2,3,...,999999）
    ↓
Redis 的 maxmemory-policy 是 allkeys-lru（默认）
    ↓
大量冷门数据挤占 Redis 内存
    ↓
热门视频（真正被用户刷的）被 LRU 淘汰
```

**第二阶段：缓存雪崩（Cache Avalanche）**
```
大量热门视频同时被淘汰出 Redis
    ↓
大量用户请求同时穿透到 MySQL
    ↓
数据库连接被打满 → 延迟飙升 → 雪崩
```

---

### 二、当前项目已有的防御措施

我们这个项目其实已经有几层防护了，我来逐一说明：

#### ① 三级缓存架构（最关键的防护）

```go
// FeedService 的三级缓存结构
type FeedService struct {
    localcache   *cache.Cache        // L1: 本地内存缓存（3秒 TTL）
    rediscache   *rediscache.Client  // L2: Redis 分布式缓存
    repo         *FeedRepository     // L3: MySQL 数据库
    requestGroup singleflight.Group  // SingleFlight 防击穿
}
```

数据查询链路：
```
请求 → L1 本地内存 (3s) → 未命中 → L2 Redis → 未命中 → L3 MySQL
                                                          ↓
                                               SingleFlight合并请求
                                               N个并发只有1个查DB
```

**L1 本地缓存是抵御爬虫的第一道防线**：3 秒内同一个进程内所有请求都不出本地内存，不经过 Redis，更不查数据库。爬虫在同一台机器上 3 秒内反复请求同一个视频，最多只有第一次穿透到 L2。

#### ② SingleFlight 防击穿

```go
sfKey := fmt.Sprintf("sf:entity:%d", videoID)
v, err, _ := f.requestGroup.Do(sfKey, func() (interface{}, error) {
    // 同一个 videoID 同时有 1000 个并发请求
    // 只有 1 个真正查数据库，其余 999 个等待结果
    videoList, err := f.repo.GetByIDs(ctx, []uint{videoID})
    // ...
    return videoList[0], err
})
```

#### ③ 视频详情缓存的分布式锁 + 自旋等待

```go
// 拿到锁的进程查数据库回填
// 没拿到锁的进程自旋等待（5次×20ms=100ms）
for i := 0; i < 5; i++ {
    select {
    case <-ctx.Done(): return
    case <-time.After(20 * time.Millisecond):
    }
    if v, ok := getCached(); ok {
        return v, nil  // 别人回填好了，直接取
    }
}
```

#### ④ Redis 操作 50ms 超时保护

所有 Redis 操作都带 50ms 超时，Redis 挂了也不会拖垮 API 进程：

```go
opCtx, cancel := context.WithTimeout(ctx, 50*time.Millisecond)
defer cancel()
_ = cache.ZincrBy(opCtx, windowKey, member, float64(change))
```

#### ⑤ 限流中间件

```go
// 已有点赞/评论/社交操作的限流
likeLimiter := ratelimit.Limit(cache, "like_write", 30, time.Minute, KeyByAccount)
commentLimiter := ratelimit.Limit(cache, "comment_write", 10, time.Minute, KeyByAccount)
```

### 三、还需要补充的防御策略

虽然有上面的防护，但针对"爬虫大量扫冷门数据"这个特定场景，还需要补充以下策略：

---

#### 策略一：读接口也加限流 + 爬虫指纹识别

目前限流只对写接口（点赞、评论、社交）做了，读接口（Feed流、视频详情）是开放的。需要补充：

```go
// 1. 对未登录的读接口做 IP 维度限流
feedLimiter := ratelimit.Limit(cache, "feed_read", 60, time.Minute, KeyByIP)

// 2. 对已登录的读接口做用户维度限流
feedUserLimiter := ratelimit.Limit(cache, "feed_read_user", 300, time.Minute, KeyByAccount)

// 3. 爬虫特征识别中间件
func CrawlerDetect() gin.HandlerFunc {
    return func(c *gin.Context) {
        ua := c.GetHeader("User-Agent")
        // 识别空 UA、非浏览器 UA、高频相同请求等特征
        // 对可疑请求直接返回 429 或降级响应
    }
}
```

**核心思路**：正常用户一分钟刷不了几十页，但爬虫可以一分钟刷几千次。限流是最直接的防御手段。

---

#### 策略二：缓存空值（Negative Caching）—— 防穿透

爬虫可能扫描不存在的视频 ID（比如 ID=99999999），每次都会穿透到数据库。需要缓存"查不到"的结果：

```go
func (vs *VideoService) GetDetail(ctx context.Context, id uint) (*Video, error) {
    cacheKey := fmt.Sprintf("video:detail:id=%d", id)

    // 1. 查缓存
    cached, err := vs.cache.Get(ctx, cacheKey)
    if err == nil {
        if cached == "NULL" {  // 缓存了"不存在"
            return nil, errors.New("video not found")
        }
        // 反序列化返回...
    }

    // 2. 查数据库
    video, err := vs.repo.GetByID(ctx, id)
    if err != nil {
        if errors.Is(err, gorm.ErrRecordNotFound) {
            // 对不存在的 ID 也缓存，TTL 设短一些（30秒）
            vs.cache.Set(ctx, cacheKey, "NULL", 30*time.Second)
            return nil, errors.New("video not found")
        }
        return nil, err
    }

    // 3. 查到了才正常缓存 5 分钟
    vs.cache.Set(ctx, cacheKey, video, 5*time.Minute)
    return video, nil
}
```

这样爬虫扫不存在的 ID 时，第一次穿透到 DB，之后 30 秒内全被缓存拦截，不会再打到数据库。

---

#### 策略三：布隆过滤器（Bloom Filter）—— 最优雅的方案

在缓存之前加一层布隆过滤器，快速判断一个 ID 是否"可能存在"：

```
请求 videoID = 999999
    ↓
Bloom Filter 判断 ID 是否可能存在
    ↓
    不存在 → 直接返回 "video not found"（绝不查 DB）
    可能存在 → 走正常缓存链路
```

布隆过滤器的特点：
- **空间效率极高**：1000 万个 ID 只需要约 10MB 内存
- **查询时间 O(k)**：常数时间
- **可能有误判**（说存在但实际不存在），但**绝不漏判**（说不存在那就一定不存在）

适合在项目启动时加载所有现有 video ID 到布隆过滤器，增量更新时同步添加。这样爬虫扫任何不存在的 ID，O(1) 时间直接拒绝。

---

#### 策略四：缓存 TTL 抖动 + 热数据保护

防止大量缓存同时过期导致的雪崩，可以做两件事：

**1. TTL 增加随机偏移**

```go
// 不设固定 5 分钟，而是 4-6 分钟随机
baseTTL := 5 * time.Minute
jitter := time.Duration(rand.Int63n(int64(2 * time.Minute)))
actualTTL := baseTTL - time.Minute + jitter  // 4~6 分钟随机
_ = vs.cache.SetBytes(ctx, cacheKey, b, actualTTL)
```

**2. 热数据保活（主动刷新）**

识别访问频率高的热数据，在 TTL 过期前主动刷新，不让它们被淘汰：

```go
// 在 GetDetail 中，如果发现缓存即将过期，异步刷新
func (vs *VideoService) GetDetail(ctx context.Context, id uint) (*Video, error) {
    // ... 正常查缓存逻辑 ...
    
    // 额外检查：缓存还有多久过期？
    ttl, _ := vs.cache.TTL(ctx, cacheKey)
    if ttl < 30*time.Second && ttl > 0 {
        // 热数据即将过期，异步刷新
        go func() {
            refreshCtx, cancel := context.WithTimeout(context.Background(), 200*time.Millisecond)
            defer cancel()
            video, _ := vs.repo.GetByID(refreshCtx, id)
            if video != nil {
                vs.cache.SetBytes(context.Background(), cacheKey, marshal(video), 5*time.Minute)
            }
        }()
    }
    return cachedVideo, nil
}
```

---

#### 策略五：Redis 内存淘汰策略 + key 分级

**1. 设置合理的 maxmemory-policy**

如果一个实例同时存了热数据和冷数据，可以改用 `allkeys-lfu` 策略（Redis 4.0+）：

```
maxmemory-policy allkeys-lfu
```

LFU（Least Frequently Used）比 LRU 更适合这个场景。因为爬虫的冷门数据虽然"最近"被访问了，但"频率"很低（每个 ID 只访问一两次），而热数据被成千上万用户高频访问。LFU 能更好地区分这两者。

**2. key 命名分级，不同 TTL 策略**

对爬虫可能扫的冷门 key 区分对待：

```go
// 正常热数据：TTL 5分钟
cacheKey := "video:detail:hot:id=%d"

// 冷门数据（只被访问了一次）：TTL 30秒
cacheKey := "video:detail:cold:id=%d"
```

当然这需要在业务代码中做判断，会引入复杂度。

---

#### 策略六：本地缓存兜底 + 降级响应

如果最坏情况发生了——Redis 被爬虫打满，MySQL 也被击穿，这时候要用"有损降级"：

```go
// 在 Feed 流接口中
if redisUnavailable {
    // 1. 尝试从 L1 本地缓存获取
    // 2. L1 也没有 → 返回少量数据 + 标记降级
    // 3. 前端根据降级标记显示"加载中"或简化页面
    
    // 极端情况下返回空列表，也比拖垮数据库强
    return ListLatestResponse{
        VideoList: partialVideos,  // 能拿多少拿多少
        HasMore:   false,
    }, nil
}
```

### 四、防御体系全景图

```
爬虫请求
    │
    ▼
┌──────────────────────────────────────┐
│  ① 限流 + 爬虫指纹识别                │  ← 第一道门：拦住大部分爬虫
│  IP 限流 / UA 检测 / 行为特征         │
└──────────┬───────────────────────────┘
           │ 通过
           ▼
┌──────────────────────────────────────┐
│  ② 布隆过滤器（ID 是否存在）          │  ← 第二道门：拦住不存在ID
│  不存在 → 直接返回 404                │
└──────────┬───────────────────────────┘
           │ 可能存在
           ▼
┌──────────────────────────────────────┐
│  ③ L1 本地缓存（3s）                  │  ← 第三道门：3秒内不进Redis
│  命中 → 1ms 返回                      │
└──────────┬───────────────────────────┘
           │ 未命中
           ▼
┌──────────────────────────────────────┐
│  ④ L2 Redis 缓存                      │  ← 第四道门：LFU淘汰策略保护热数据
│  命中 → 回填 L1                       │
│  TTL 随机偏移 4~6min                  │
│  热数据 TTL 过半时主动刷新             │
└──────────┬───────────────────────────┘
           │ 未命中 / Redis不可用
           ▼
┌──────────────────────────────────────┐
│  ⑤ L3 MySQL + SingleFlight           │  ← 最后一道防线
│  N个并发只有1个查DB                   │
│  不存在的ID → 缓存空值 30秒           │
│  Redis挂了 → 降级响应                 │
└──────────────────────────────────────┘
```

### 五、总结

针对爬虫扫冷门数据导致缓存雪崩这个问题，当前项目已经有**三级缓存 + SingleFlight + 分布式锁 + 50ms超时**等保护。但针对这个特定场景，最需要补充的是：

| 优先级 | 策略 | 解决问题 |
|---|---|---|
| **P0** | 读接口限流 + 爬虫指纹 | 从源头减少爬虫请求量 |
| **P0** | 缓存空值（Negative Cache） | 不存在 ID 不穿透 DB |
| **P1** | 布隆过滤器 | 高效拦截不存在 ID |
| **P1** | TTL 随机抖动 | 防止大批量同时过期 |
| **P2** | LFU 淘汰策略 | 更好保护热数据不被冷数据挤掉 |
| **P2** | 热数据主动刷新 | 热数据永不失效 |

其中**读接口限流**和**缓存空值**是投入产出比最高的两个措施，代码改动量小，效果立竿见影。
