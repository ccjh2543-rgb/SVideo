# 面试问答记录 - 第5轮

## 问题
你是如何存储视频的？

## 回答

我们项目的视频存储分为两个层次：**视频文件存在本地磁盘**，**视频元数据存在 MySQL 数据库**。发布流程采用"先上传、后发布"的两步走策略。

---

### 一、视频表结构（MySQL）

视频的所有元数据存储在 MySQL 的 `videos` 表中，由 GORM AutoMigrate 自动创建：

```go
type Video struct {
    ID          uint      `gorm:"primaryKey" json:"id"`
    AuthorID    uint      `gorm:"index;not null" json:"author_id"`
    Username    string    `gorm:"type:varchar(255);not null" json:"username"`
    Title       string    `gorm:"type:varchar(255);not null" json:"title"`
    Description string    `gorm:"type:varchar(255);" json:"description,omitempty"`
    PlayURL     string    `gorm:"type:varchar(255);not null" json:"play_url"`
    CoverURL    string    `gorm:"type:varchar(255);not null" json:"cover_url"`
    CreateTime  time.Time `gorm:"autoCreateTime" json:"create_time"`
    LikesCount  int64     `gorm:"column:likes_count;not null;default:0" json:"likes_count"`
    Popularity  int64     `gorm:"column:popularity;not null;default:0" json:"popularity"`
}
```

这里存储的 `PlayURL` 和 `CoverURL` 都是**字符串类型的 URL 地址**，而不是二进制文件内容。视频文件的物理存储由文件上传模块负责。

---

### 二、视频文件的物理存储（本地磁盘）

#### 存储路径结构

视频文件保存在本地磁盘，通过 Gin 的 `Static` 路由暴露为静态资源：

```go
// router.go 中注册静态文件路由
r.Static("/static", "./.run/uploads")
```

文件按 **用户 + 日期** 进行目录隔离：

```
.run/uploads/
├── videos/
│   ├── {authorID}/
│   │   ├── 20260430/
│   │   │   ├── a3b5c7d9e1f2a4b6.mp4    ← 视频文件
│   │   │   └── ...
│   │   └── 20260501/
│   └── ...
└── covers/
    ├── {authorID}/
    │   ├── 20260430/
    │   │   ├── f8e7d6c5b4a39281.jpg    ← 封面图
    │   │   └── ...
    │   └── ...
    └── ...
```

文件名的生成规则：`randHex(16) + 原始扩展名`，即 32 位随机十六进制字符串，保证唯一性且不可猜测。

#### 上传接口 —— UploadVideo

```go
func (vh *VideoHandler) UploadVideo(c *gin.Context) {
    // 1. 获取上传文件
    f, _ := c.FormFile("file")

    // 2. 校验：大小 ≤ 200MB，格式仅限 .mp4
    const maxSize = 200 << 20  // 200MB
    ext := strings.ToLower(filepath.Ext(f.Filename))
    if ext != ".mp4" { /* 拒绝 */ }

    // 3. 按日期+用户分目录存储
    date := time.Now().Format("20060102")
    relDir := filepath.Join("videos", fmt.Sprintf("%d", authorId), date)
    absDir := filepath.Join(".run", "uploads", relDir)
    os.MkdirAll(absDir, 0755)

    // 4. 生成随机文件名并保存
    filename := randHex(16) + ext  // 32位随机字符串
    c.SaveUploadedFile(f, filepath.Join(absDir, filename))

    // 5. 返回可访问的 URL
    urlPath := path.Join("/static", "videos", strconv.Itoa(authorId), date, filename)
    fullURL := buildAbsoluteURL(c, urlPath)
    // 返回: http://host/static/videos/42/20260430/a3b5c7d9e1f2a4b6.mp4
}
```

封面上传 `UploadCover` 逻辑类似，区别是：最大 10MB，支持 `jpg/jpeg/png/webp` 四种格式。

#### 静态文件服务

用户访问 `http://host/static/videos/42/20260430/a3b5c7d9e1f2a4b6.mp4` 时，Gin 直接从 `.run/uploads/videos/42/20260430/a3b5c7d9e1f2a4b6.mp4` 读取并返回文件内容，无需经过应用层逻辑。

### 三、发布流程（两阶段提交）

上传和发布是两个独立的 API，分两步完成：

#### 第一步：上传文件

```
POST /video/uploadVideo  (multipart/form-data, 需 JWT 鉴权)
  → 校验文件
  → 保存到本地磁盘
  → 返回 play_url: "http://host/static/videos/42/20260430/a3b5c7d9e1f2a4b6.mp4"
```

同样地，上传封面图：
```
POST /video/uploadCover
  → 返回 cover_url
```

这一步只处理文件存储，不涉及数据库。

#### 第二步：发布视频

拿到上传接口返回的 URL 之后，客户端再调用发布接口：

```
POST /video/publish (JSON, 需 JWT 鉴权)
{
    "title": "我的第一条视频",
    "description": "hello world",
    "play_url": "http://host/static/videos/42/20260430/a3b5c7d9e1f2a4b6.mp4",
    "cover_url": "http://host/static/covers/42/20260430/f8e7d6c5b4a39281.jpg"
}
```

Service 层的 `Publish` 方法做了两件事，而且放在**同一个数据库事务**中：

```go
func (vs *VideoService) Publish(ctx context.Context, video *Video) error {
    // 事务保证：视频记录和 outbox 消息要么一起成功，要么一起失败
    err := vs.repo.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {

        // 1. 写入视频元数据到 MySQL
        if err := tx.Create(video).Error; err != nil {
            return err
        }

        // 2. 写入 Outbox 消息表（确保消息可靠投递）
        msg := OutboxMsg{
            VideoID:    video.ID,
            EventType:  "video_published",
            Status:     "pending",
            CreateTime: video.CreateTime,
        }
        if err := tx.Create(&msg).Error; err != nil {
            return err
        }
        return nil
    })
    return err
}
```

事务写入两张表：

| 表 | 作用 |
|---|---|
| `videos` | 存储视频元数据（标题、URL、作者等） |
| `outbox_messages` | 存储待投递的消息（Outbox 模式），status = "pending" |

**为什么需要 Outbox 表？**

这是一个典型的"发消息和写数据库需要原子性"的问题。如果在事务外发 MQ 消息，可能出现：
- 数据库写成功了，MQ 消息没发出去 → 全局时间线没更新
- MQ 消息发出去了，数据库回滚了 → 时间线上多了不存在的视频

Outbox 模式通过本地事务解决了这个问题：先原子地写入 outbox 表，然后由 OutboxPoller 轮询投递，确保消息**至少投递一次**（at-least-once）。

### 四、视频详情缓存

视频详情会被缓存到 Redis 中，key 为 `video:detail:id={id}`，TTL 为 5 分钟：

```go
cacheKey := fmt.Sprintf("video:detail:id=%d", id)
```

`GetDetail` 方法实现了**防缓存击穿**的保护：

1. 先读缓存，命中直接返回
2. 缓存未命中 → 尝试获取分布式锁 `lock:video:detail:id={id}`
3. 拿到锁的进程查数据库并回填缓存
4. 没拿到锁的进程等待（最多 5 次 × 20ms = 100ms），等别人回填
5. 超时后仍未拿到数据，降级直接查数据库

视频热度变化时，`UpdatePopularityCache` 会主动删除这个缓存 key，保证下次读取时拿到最新的热度数据。

---

### 五、总结

视频存储的架构可以概括为：

| 维度 | 存储位置 | 技术 |
|---|---|---|
| 视频文件（.mp4） | 本地磁盘 `.run/uploads/videos/` | Gin Static 静态文件服务 |
| 封面图（jpg/png/webp） | 本地磁盘 `.run/uploads/covers/` | 同上 |
| 视频元数据 | MySQL `videos` 表 | GORM ORM |
| 待投递消息 | MySQL `outbox_messages` 表 | Outbox 模式 |
| 视频详情缓存 | Redis `video:detail:id={id}` | 分布式锁防缓存击穿 |

整个发布流程是：**上传文件拿到 URL → 用 URL 调用发布接口 → 事务写入元数据和 Outbox → OutboxPoller 异步投递到 MQ → Worker 消费更新全局时间线**。

当然，这个方案对于生产环境来说比较"朴素"——视频文件存在单机磁盘，没有分布式文件系统。如果要上生产，通常会换成 OSS/S3 这类对象存储，但当前架构中上传和发布的接口设计是兼容这种替换的，只需要把保存文件的地方从本地磁盘换成对象存储 SDK 即可。
