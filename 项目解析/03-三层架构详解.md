# 03 - 三层架构 Handler-Service-Repository 详解

> 零基础学习指南 · 第三篇：为什么代码要拆三层？

---

## 🤯 灵魂拷问

> **如果我明天要把 MySQL 换成 PostgreSQL，要改多少代码？**

没有分层的项目：搜遍整个项目几千个地方改 SQL。

有分层的项目：**只改 repo.go 一个文件！**

---

## 🎯 三层架构标准定义

```
  用户点按钮
     ↓
[ 前端 Vue ]
     ↓  HTTP 请求
[ Handler ] ← ① 收参数、验参数、返结果
     ↓
[ Service ] ← ② 写业务逻辑：点赞了要做哪几件事？
     ↓
[ Repository ] ← ③ 只做 SQL 增删改查
     ↓
[   MySQL   ]
```

---

## 📋 每层的严格分工

| 层级 | 文件名 | 中文 | ✅ 只能做什么 | ❌ 绝对不能做什么 |
|------|--------|------|-----------|----------------|
| 第一层 | handler.go | 处理器 | 1. 接收前端参数<br>2. 参数校验<br>3. 调用 Service<br>4. 返回 JSON | 写SQL<br>写业务逻辑 |
| 第二层 | service.go | 业务层 | 纯业务逻辑<br>先做什么？后做什么？<br>失败了怎么办？ | 直接写SQL |
| 第三层 | repo.go | 仓库层 | SQL 增删改查<br>数据库表一对一操作 | 写任何业务逻辑 |

---

## 💡 每一层的代码示例

---

### 🔴 第一层：Handler - 酒店前台

```go
// handler.go
func (h *LikeHandler) Like(c *gin.Context) {
    // 1. 拿门禁卡：验证用户有没有登录
    accountId, err := jwt.GetAccountID(c)
    if err != nil {
        c.JSON(401, gin.H{"error": "请先登录"})
        return
    }

    // 2. 收参数：用户说要点赞哪个视频
    var req struct {
        VideoID uint `json:"video_id"`
    }
    if err := c.ShouldBindJSON(&req); err != nil {
        c.JSON(400, gin.H{"error": "参数错误"})
        return
    }

    // 3. 叫服务员：交给 Service 处理
    err = h.service.Like(c.Request.Context(), accountId, req.VideoID)
    if err != nil {
        c.JSON(500, gin.H{"error": err.Error()})
        return
    }

    // 4. 给客人答复：点赞成功！
    c.JSON(200, gin.H{"message": "success"})
}
```

#### Handler 工作心法：

> **我啥业务都不懂，我只负责传话！**

- 用户有没有带门禁卡？→ 没有就滚
- 用户说的话我听得懂吗？→ 听不懂就问
- 听懂了就把活派给 Service
- Service 干完了我就给客人回话

---

### 🟡 第二层：Service - 餐厅经理

```go
// service.go
func (s *LikeService) Like(ctx context.Context, accountId uint, videoId uint) error {
    // 业务逻辑：用户点了一个赞，我要做 4 件事！

    // 1. 先发 MQ 消息告诉后台工人写库
    err := s.likeMQ.PublishLike(ctx, accountId, videoId)
    
    // 2. MQ 发失败了怎么办？降级！直接写 MySQL！
    if err != nil {
        like := &video.Like{AccountID: accountId, VideoID: videoId}
        err = s.repo.Like(ctx, like)
        if err != nil {
            return err
        }
    }

    // 3. 更新视频热度 +1
    s.popularityMQ.IncrLikes(ctx, videoId, 1)

    // 4. 删除缓存，保证一致性
    s.cache.Del(ctx, fmt.Sprintf("video:detail:%d", videoId))

    return nil
}
```

#### Service 工作心法：

> **我才是真正懂业务的人！**

- 点赞 = 写点赞记录 + 更新热度 + 清缓存
- MQ 发失败了 → 自己动手写 MySQL
- 这一层才是项目的灵魂！

---

### 🟢 第三层：Repository - 仓库管理员

```go
// repo.go
func (r *LikeRepository) Like(ctx context.Context, like *Like) error {
    // ✅ 我只做一件事：把这条数据插进数据库！
    return r.db.WithContext(ctx).Create(like).Error
}

func (r *LikeRepository) Unlike(ctx context.Context, accountId uint, videoId uint) error {
    // ✅ 我只做一件事：把这条数据从数据库删掉！
    return r.db.WithContext(ctx).
        Where("account_id = ? AND video_id = ?", accountId, videoId).
        Delete(&Like{}).Error
}

func (r *LikeRepository) IsLiked(ctx context.Context, accountId uint, videoId uint) (bool, error) {
    // ✅ 我只做一件事：数据库里有没有这条记录？
    var count int64
    err := r.db.WithContext(ctx).Model(&Like{}).
        Where("account_id = ? AND video_id = ?", accountId, videoId).
        Count(&count).Error
    return count > 0, err
}
```

#### Repository 工作心法：

> **我啥业务都不懂！给我数据我就存，要数据我就拿！**

- 从来不管你为什么要点赞
- 从来不管你点了赞要做什么
- 我就管和数据库对话

## 🌟 分层的 3 个巨大好处

---

### ✅ 好处 1：换数据库不心痛

**灵魂拷问的答案：**
> 明天把 MySQL 换成 PostgreSQL？

**把 `repo.go` 里这三个函数重写一遍就行了！**

```go
func (r *LikeRepository) Like(...) error {
    // 以前是 MySQL 的写法
    // 现在改成 PostgreSQL 的写法
}
```

✅ Handler 一行不动！
✅ Service 一行不动！

---

### ✅ 好处 2：写单元测试太爽了

要测试「点赞业务逻辑对不对」？

```go
// 测 Service 就行了！
// Mock 掉 Repository 和 MQ，根本不用连真实数据库！

func Test_Like(t *testing.T) {
    // 准备：造一个假的 Repository
    mockRepo := new(MockLikeRepository)
    mockRepo.On("Like", 1, 100).Return(nil)
    
    // 被测：Service
    service := NewLikeService(mockRepo, nil, nil)
    
    // 执行
    err := service.Like(context.Background(), 1, 100)
    
    // 断言
    assert.NoError(t, err)
    mockRepo.AssertExpectations(t)
}
```

测 Service = 测全量业务逻辑！

---

### ✅ 好处 3：新人接手不懵逼

新人来了：
> 「点赞的业务逻辑在哪？」
> → `like_service.go`，5个函数看完就懂了！

> 「点赞的SQL都有哪些？」
> → `like_repo.go`，翻一遍就看完了！

> 「点赞的接口参数是什么？返回什么？」
> → `like_handler.go`，看这一个文件！

没有分层的项目 = 在垃圾堆里找代码！

## ❌ 新手最容易犯的错误

### 反面教材 1：Handler 直接写 SQL

```go
// ❌ 傻逼写法
func (h *LikeHandler) Like(c *gin.Context) {
    accountId, _ := jwt.GetAccountID(c)
    
    // 直接在 Handler 里写 SQL！
    h.db.Exec("INSERT INTO likes ...")   // 😱
    
    c.JSON(200, gin.H{"ok": 1})
}
```

后果：
- 明天要加 MQ 异步？整个 Handler 重写
- 明天要加热度更新？整个 Handler 重写
- 10个地方点赞，10个地方复制粘贴

---

### 反面教材 2：Repository 里写业务

```go
// ❌ 傻逼写法
func (r *LikeRepository) Like(ctx context.Context, like *Like) error {
    // 在 Repository 里更新视频表！
    r.db.Exec("UPDATE videos SET likes_count = likes_count + 1 WHERE id = ?", like.VideoID)  // 😱
    
    // 还删缓存！
    r.cache.Del(...)   // 😱😱😱
    
    return r.db.Create(like).Error
}
```

后果：
- 取消赞的时候忘记减 likes_count
- 后台 Worker 消费的时候又更新了一遍，计数翻倍
- 天知道哪个地方在删缓存
