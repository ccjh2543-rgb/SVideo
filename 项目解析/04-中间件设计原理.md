# 04 - 中间件设计原理详解

> 零基础学习指南 · 第四篇：什么是中间件？它们都在哪个位置干活？

---

## 🤔 先理解名字：为什么叫「中间件」？

```
用户 → [ Nginx ] → [ 限流 ] → [ 鉴权 ] → [ 业务Handler ] → Service → DB
                          ↑↑↑
                    这些就叫「中间件」
```

> ✅ **定义：请求到达真正业务逻辑之前，要经过的一道道关卡！**

就像你去政府办事：
```
你 → 门口保安查健康码 → 取号机限流 → 柜台办事
                ↑↑↑
            这就是中间件！
```

---

## 🛡️ 这个项目的 4 大中间件

| 中间件 | 项目位置 | 作用 | 政府办事比喻 |
|--------|---------|-----|-----------|
| JWT 鉴权 | `middleware/jwt/` | 验证用户有没有登录 | 门口保安，没带身份证不让进 |
| 分布式限流 | `middleware/ratelimit/` | 防止用户刷接口 | 取号机，一天只能办5个 |
| Redis 缓存 | `middleware/redis/` | 常用数据放内存，不用每次查库 | 柜台大厅的公告栏 |
| RabbitMQ | `middleware/rabbitmq/` | 异步解耦 | 快递代收点 |

## 🔐 中间件一：JWT 鉴权

### 工作位置

```
         ↓↓↓ JWT 在这检查 ↓↓↓
请求 → JWT → 业务 Handler → ...
```

### 核心代码

```go
// middleware/jwt/jwt.go
func JWTAuth(repo *account.AccountRepository, cache *redis.Client) gin.HandlerFunc {
    return func(c *gin.Context) {
        // 1. 从 HTTP Header 里拿出 Token
        token := c.GetHeader("Authorization")
        
        // 2. 先查 Redis 缓存有没有这个 token
        accountId, err := cache.Get(ctx, "account:token:"+token)
        
        // 3. Redis 没有 → 回源查 MySQL （缓存自愈）
        if err != nil {
            accountId, err = repo.ValidateToken(token)
            // 验证通过了 → 回填 Redis（自愈）
            cache.Set(ctx, "account:token:"+token, accountId, 24*time.Hour)
        }
        
        // 4. 都不行 → 401 打回去
        if err != nil {
            c.AbortWithStatusJSON(401, gin.H{"error": "请先登录"})
            return
        }
        
        // 5. ✅ 验证通过！把 accountId 放进上下文
        c.Set("account_id", accountId)
        
        // 6. ↓↓↓ 放行！继续走到业务 Handler
        c.Next()
    }
}
```

---

### ✨ JWT 的牛逼设计 - 缓存自愈机制

| 场景 | 处理方式 |
|------|---------|
| ✅ Redis 有 token | 直接用，1ms 返回 |
| ❌ Redis 挂了/没这个 key | 自动去 MySQL 校验 |
| ✅ MySQL 校验通过了 | 自动写回 Redis，下次就快了 |

**Redis 宕机完全不影响登录功能！**

> 比喻：保安忘了你长什么样 → 去人事查档案 → 记住你的脸 → 下次就不用查了

---

### 软鉴权 vs 硬鉴权

| 鉴权方式 | 应用场景 | 没登录怎么办 |
|---------|---------|-----------|
| **硬鉴权 JWTAuth** | 点赞/评论/关注 | ❌ 直接 401 打回去 |
| **软鉴权 SoftJWTAuth** | Feed 信息流 | ⚠️ 默默放过去，给个游客身份 |

> ✅ Feed 流的牛逼设计：
> 登录用户能刷，游客也能刷！只是登录了能看到「我关注的人」的内容。

## 🕒 中间件二：分布式限流

### 工作位置

```
请求 → JWT → 【限流在这】→ 业务 Handler → ...
```

### 5 个精细化限流规则

| 限流规则 | 阈值 | 维度 | 防什么 |
|---------|-----|------|-------|
| 登录限流 | 10次/分钟 | IP 维度 | 暴力破解密码 |
| 注册限流 | 5次/小时 | IP 维度 | 机器人批量注册 |
| 点赞限流 | 30次/分钟 | 用户维度 | 刷赞机器人 |
| 评论限流 | 10次/分钟 | 用户维度 | 水军刷屏灌水 |
| 关注限流 | 20次/分钟 | 用户维度 | 批量炸粉 |

### 实现原理：Redis 滑动窗口计数

```go
key = "ratelimit:like:user:123"
now = 当前时间戳

// ZSET 数据结构：[时间戳1, 时间戳2, 时间戳3...]
redis.ZAdd(key, now, now)          // 把这次请求加进去
redis.ZRemRangeByScore(key, 0, now-60)  // 删除1分钟以前的
count = redis.ZCard(key)           // 统计最近1分钟有多少次

if count > 30 {
    return 429 "您操作太频繁了"
}
```

## 🧊 中间件三：Redis 缓存

### 工作位置

```
           ↓↓↓ 先查缓存 ↓↓↓
Service → Redis 命中？→ 直接返回
           ↓ 没命中
         MySQL 查询 → 回填 Redis
```

### 这个项目用了 Redis 的 4 种数据结构

| 数据结构 | 用途 |
|---------|------|
| STRING | Token 存储、视频详情缓存 |
| ZSET | Feed 热度排行榜、关注时间线、限流计数 |
| SETNX | 分布式锁、防缓存击穿 |
| EXPIRE | 所有 key 都带 TTL 过期 |

---

### ✨ 缓存设计要点

| 问题 | 解决方案 |
|------|---------|
| 缓存击穿 | 单飞 + 分布式锁 SETNX |
| 缓存穿透 | 空值也缓存 1 分钟 |
| 数据一致性 | 更新 DB 后主动 DEL 缓存，而不是更新 |
| 雪崩 | 过期时间加随机偏移量 |

## 📮 中间件四：RabbitMQ 消息队列

### 工作位置

```
        同步返回用户，不用等写库！
              ↓
用户点赞 → Service → RabbitMQ → [在这排队] → Worker 后台慢慢写库
                                    ↓
                              削峰填谷、解耦
```

### 5 个 Topic 交换机

| 交换机 | 路由Key | Payload | 消费者 |
|-------|---------|---------|-------|
| like.events | like.like / like.unlike | {用户,视频,时间} | LikeWorker |
| comment.events | comment.publish/delete | {用户,视频,评论} | CommentWorker |
| social.events | social.follow/unfollow | {粉丝,博主} | SocialWorker |
| video.popularity.events | video.popularity.* | {视频,增量分} | PopularityWorker |
| video.timeline | timeline.* | {视频,创建时间} | TimelineWorker |

---

### ✨ MQ 最牛逼的设计：降级直写

| 场景 | 处理方式 |
|------|---------|
| ✅ MQ 连接正常 | Publish 到 MQ，异步消费 |
| ❌ MQ 连不上/发布失败 | 降级！直接写 MySQL |

**永远不会因为 MQ 挂了，用户就点不了赞！**

这才是工业级的高可用！

---

## 💡 中间件的通用设计哲学

### 1. 面向错误编程

**所有中间件都不是必须的！挂了也能降级运行！**
- Redis 挂了 → 直查 MySQL
- RabbitMQ 挂了 → 直写 MySQL
- 限流挂了 → 不限了也行

### 2. 业务无感知

加限流、加鉴权、加监控
✅ Handler 一行代码都不用改！

### 3. 统一收口

所有接口都要走鉴权、限流、日志
✅ 不会漏掉某个接口被黑产刷爆
