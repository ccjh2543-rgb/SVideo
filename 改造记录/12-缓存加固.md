# 12 - 缓存加固

## 1. 改造前的问题

改造前视频详情缓存：

- 固定 TTL。
- 缓存过期瞬间大量请求同时回源。
- 不存在的视频 ID 会持续穿透到 MySQL。
- 没有逻辑过期，热点 Key 过期时会有明显抖动。

改造后：

- 逻辑过期 + 异步重建。
- 随机 TTL，避免同时失效。
- 布隆过滤器拦截不存在的视频 ID。
- 空值缓存兜底布隆误判。
- 分布式锁防止缓存击穿。

---

## 2. 逻辑过期

### 2.1 数据结构

```go
type LogicalEntry struct {
    Data     json.RawMessage `json:"data"`
    ExpireAt int64           `json:"expire_at"`
}
```

Redis 中保存：

```json
{
  "data": {"id": 1, "title": "demo"},
  "expire_at": 1760000300000
}
```

- `expire_at` 是逻辑过期时间。
- Redis 物理 TTL 更长，保证过期后旧值仍然存在。

### 2.2 读取流程

```text
GetLogical
-> 物理 key 不存在：返回 miss
-> 存在且未过期：返回数据
-> 存在但逻辑过期：返回旧数据 + expired=true
```

视频详情读取：

```go
if video, expired, found := vs.getDetailCache(ctx, cacheKey); found {
    if expired {
        go vs.refreshDetail(id)
    }
    return video, nil
}
```

效果：

- 请求永远不走“缓存刚过期时的慢路径”。
- 旧值立即返回，后台异步重建。
- 热点 Key 不会在同一时刻阻塞大量请求。

### 2.3 写入

```go
physicalTTL := cachelib.Jitter(30*time.Minute, 0.2)
_ = cachelib.SetLogical(ctx, vs.cache, key, data, 5*time.Minute, physicalTTL)
```

逻辑 TTL 5 分钟，物理 TTL 约 30 分钟。

## 3. TTL 抖动

### 3.1 实现

```go
func Jitter(base time.Duration, ratio float64) time.Duration {
    delta := float64(base) * ratio
    offset := (rand.Float64()*2 - 1) * delta
    return time.Duration(float64(base) + offset)
}
```

示例：

```text
base = 30 分钟，ratio = 0.2
实际 TTL 在 24~36 分钟之间随机
```

### 3.2 应用位置

- 视频详情物理 TTL。
- Feed 视频实体 Redis 回填 TTL。
- 空值缓存 TTL。

注意：

- 认证 Token TTL 不加抖动，避免过期时间不可预测。
- 热榜快照 TTL 不加抖动，保证同一版本翻页稳定。

## 4. 布隆过滤器

### 4.1 数据结构

```text
key: bloom:video_ids
type: Redis Bitmap
bits: 1 << 24（约 2MB）
hashCount: 7
```

### 4.2 哈希

使用双重哈希：

```go
positions[i] = (h1 + i*h2) % bits
```

- `h1 = FNV64a(id)`
- `h2 = FNV64a(id) ^ seed`

### 4.3 写入

发布视频成功后：

```go
if vs.bloom != nil {
    _ = vs.bloom.Add(ctx, uint64(video.ID))
}
```

启动时重建：

```go
func (vs *VideoService) RebuildBloom(ctx context.Context) error {
    return vs.bloom.Rebuild(ctx, func(afterID uint, limit int) ([]uint, error) {
        return vs.repo.ListIDsAfter(ctx, afterID, limit)
    })
}
```

### 4.4 查询

```go
exists, err := vs.bloom.Exists(ctx, uint64(id))
if err == nil && !exists {
    return nil, errors.New("video not found")
}
```

### 4.5 fail-open

以下情况直接放行，不拦截：

- 布隆过滤器未启用。
- Redis 出错。
- ID 为 0。

原因：布隆过滤器是优化组件，不能误杀正常请求。

## 5. 空值缓存

布隆过滤器存在误判：

```text
视频不存在，但布隆判断“可能存在”
-> 继续查缓存和数据库
-> 数据库也不存在
```

此时写入空值缓存：

```go
_ = vs.cache.SetBytes(
    ctx,
    fmt.Sprintf("video:null:id=%d", id),
    []byte("1"),
    cachelib.Jitter(time.Minute, 0.2),
)
```

后续请求：

```go
if b, err := vs.cache.GetBytes(ctx, nullKey); err == nil && len(b) > 0 {
    return nil, errors.New("video not found")
}
```

TTL 约 1 分钟，避免长期占用内存。

## 6. 缓存击穿

缓存未命中时：

```text
尝试获取分布式锁 lock:video:detail:id={id}
-> 拿到锁：二次检查缓存 -> 查 DB -> 回填
-> 没拿到锁：最多等待 5 次 × 20ms 读缓存
-> 仍没有：降级直接查 DB
```

关键代码：

```go
lockCtx, cancel := context.WithTimeout(ctx, 50*time.Millisecond)
token, locked, err := vs.cache.Lock(lockCtx, lockKey, 2*time.Second)
cancel()

if err == nil && locked {
    defer func() { _ = vs.cache.Unlock(context.Background(), lockKey, token) }()
    if video, _, found := vs.getDetailCache(ctx, cacheKey); found {
        return video, nil
    }
    video, err := vs.repo.GetByID(ctx, id)
    ...
}
```

## 7. 边界情况

| 场景 | 行为 |
|---|---|
| 逻辑过期 | 返回旧值，异步重建 |
| 物理过期 | 当作 miss，走回源流程 |
| 并发重建 | 分布式锁保证只有一个请求重建 |
| 布隆误判 | 继续查 DB，查不到写空值缓存 |
| 布隆未启用 | 直接放行 |
| Redis 故障 | 跳过缓存，直接查 DB |
| 视频被删除 | 逻辑过期后重建会失败，旧值最多保留物理 TTL |
| 缓存内容是旧格式 | 解析失败当作 miss，重新回填 |
| 空值缓存命中 | 直接返回 not found，不查 DB |

### 7.1 已知不足

1. 视频删除后没有主动删除布隆位，布隆只增不减。
2. 逻辑过期异步重建使用独立 goroutine，进程退出时可能丢失一次重建。
3. 布隆过滤器重建在 API 启动时执行，多实例会重复重建。
4. 空值缓存只覆盖视频详情，其他实体尚未接入。
