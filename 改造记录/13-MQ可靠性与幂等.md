# 13 - MQ 可靠性与幂等

## 1. 改造前的问题

- 消费失败后 `Nack(requeue=true)`，可能无限重试、打满 CPU。
- 没有死信队列，失败消息无法排查和重放。
- 同一消息重复投递时，点赞、评论、粉丝数可能重复累加。
- 接口没有幂等键，客户端超时重试可能产生重复数据。
- Outbox 投递失败只记录日志，没有重试次数和状态。

---

## 2. 死信队列

### 2.1 队列命名

为了避免修改已有队列参数导致 `PRECONDITION_FAILED`，使用 v2 队列：

| 业务 | 主队列 | 死信交换机 | 死信队列 |
|---|---|---|---|
| 点赞 | `like.events.v2` | `like.events.dlx` | `like.events.dlq` |
| 评论 | `comment.events.v2` | `comment.events.dlx` | `comment.events.dlq` |
| 关注 | `social.events.v2` | `social.events.dlx` | `social.events.dlq` |
| 热度 | `video.popularity.events.v2` | `video.popularity.events.dlx` | `video.popularity.events.dlq` |
| 时间线 | `video.timeline.update.queue.v2` | `video.timeline.events.dlx` | `video.timeline.events.dlq` |
| 写扩散 | `video.fanout.queue` | `video.fanout.dlx` | `video.fanout.dlq` |

### 2.2 声明方式

```go
if err := base.DeclareTopicWithDLQ(
    likeExchange,
    LikeQueueName,
    likeBindingKey,
    likeDLX,
    LikeDLQName,
    "#",
); err != nil {
    return nil, err
}
```

主队列参数：

```go
amqp.Table{
    "x-dead-letter-exchange":    dlxExchange,
    "x-dead-letter-routing-key": dlqBindingKey,
}
```

### 2.3 消费失败

Worker 处理失败：

```go
if err := w.process(ctx, d.Body); err != nil {
    log.Printf("worker: failed to process message: %v", err)
    _ = d.Nack(false, false)
    return
}
_ = d.Ack(false)
```

`requeue=false` 让消息进入死信队列，避免无限热循环。

## 3. 消费端幂等

### 3.1 表结构

```go
type ProcessedEventModel struct {
    ID        uint      `gorm:"primaryKey"`
    Consumer  string    `gorm:"size:64;not null;uniqueIndex:uk_consumer_event"`
    EventID   string    `gorm:"size:64;not null;uniqueIndex:uk_consumer_event"`
    CreatedAt time.Time `gorm:"autoCreateTime"`
}
```

唯一键：`(consumer, event_id)`。

### 3.2 TryMark

```go
func (r *ProcessedEventRepository) TryMark(ctx context.Context, consumer string, eventID string) (bool, error) {
    result := r.db.WithContext(ctx).
        Clauses(clause.OnConflict{DoNothing: true}).
        Create(&ProcessedEventModel{Consumer: consumer, EventID: eventID})
    if result.Error != nil {
        return false, result.Error
    }
    return result.RowsAffected > 0, nil
}
```

- `RowsAffected > 0`：首次处理。
- `RowsAffected == 0`：重复消息。

### 3.3 Worker 使用

```go
if w.events != nil {
    first, err := w.events.TryMark(ctx, "like", evt.EventID)
    if err != nil {
        return err
    }
    if !first {
        return nil
    }
}
```

消费者名称：

```text
like
comment
social
popularity
fanout
```

不同消费者使用不同名称，避免同一事件被不同业务误判为重复。

## 4. 接口幂等键

### 4.1 使用方式

客户端请求头：

```http
Idempotency-Key: 7f3c9a2e...
```

中间件：

```go
func Require(cache *rediscache.Client, prefix string, ttl time.Duration) gin.HandlerFunc {
    return func(c *gin.Context) {
        key := strings.TrimSpace(c.GetHeader("Idempotency-Key"))
        if key == "" || cache == nil {
            c.Next()
            return
        }

        accountID, _ := jwt.GetAccountID(c)
        redisKey := fmt.Sprintf("idem:%s:%d:%s", prefix, accountID, key)

        ok, err := cache.SetNX(c.Request.Context(), redisKey, []byte("1"), ttl)
        if err != nil {
            c.Next()
            return
        }
        if !ok {
            c.AbortWithStatusJSON(http.StatusConflict, gin.H{"error": "duplicate request"})
            return
        }

        c.Next()
        if c.Writer.Status() >= http.StatusInternalServerError {
            _ = cache.Del(c.Request.Context(), redisKey)
        }
    }
}
```

挂载：

```text
/video/publish
/like/like
/like/unlike
/comment/publish
```

特点：

- 未携带 key 时放行，兼容旧客户端。
- Redis 故障时 fail-open。
- 服务端 5xx 时删除 key，允许客户端重试。
- 当前只保证“不重复进入业务”，不缓存原始响应。

## 5. Outbox 重试

### 5.1 字段

```go
type OutboxMsg struct {
    ID         uint
    VideoID    uint
    AuthorID   uint
    EventType  string
    CreateTime time.Time
    Status     string
    RetryCount int
    NextRetry  *time.Time
}
```

### 5.2 投递

```go
messages := query pending
where next_retry IS NULL OR next_retry <= now

for _, msg := range messages {
    err := PublishVideo(...)
    if err == nil {
        db.Delete(&msg)
        continue
    }

    retryCount := msg.RetryCount + 1
    if retryCount >= 3 {
        updates["status"] = "failed"
    } else {
        updates["next_retry"] = now.Add(1 << retryCount * time.Second)
    }
}
```

退避：

```text
第 1 次失败：1 秒后重试
第 2 次失败：2 秒后重试
第 3 次失败：4 秒后重试
第 4 次失败：标记 failed
```

## 6. 边界情况

| 场景 | 行为 |
|---|---|
| 重复消息 | `processed_events` 唯一键拦截 |
| 旧消息没有 event_id | 无法判重，按首次处理 |
| 消费失败 | 进入 DLQ，不 requeue |
| DLQ 堆积 | 需要人工查看和重放 |
| Redis 故障 | 接口幂等 fail-open |
| 服务端 5xx | 删除幂等键，允许重试 |
| 客户端重复提交 | 409 duplicate request |
| Outbox 重试 3 次 | 标记 failed |
| Outbox 成功 | 删除记录 |
| 队列参数变更 | 使用 v2 队列名，避免 PRECONDITION_FAILED |

### 6.1 已知不足

1. `processed_events` 在业务处理前写入，处理失败后不会重试；消息会进入 DLQ。
2. 没有 DLQ 消费和自动重放工具。
3. 接口幂等只做“请求去重”，没有缓存原响应。
4. `processed_events` 没有定时清理，需要后续增加。
5. Outbox `failed` 记录没有告警和人工恢复入口。

---

## 7. 后续优化

1. 增加 DLQ 管理接口：查询、重放、丢弃。
2. 把幂等记录改为“处理成功后标记”，配合处理中状态。
3. 接口幂等缓存响应，重复请求直接返回原结果。
4. 增加 Outbox 失败告警。
5. 定期清理过期的幂等记录。
