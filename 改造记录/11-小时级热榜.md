# 11 - 小时级热榜与线性权重衰减

## 1. 改造前的问题

改造前使用 60 个 1 分钟桶，通过 `ZUnionStore SUM` 合并：

```text
hot:video:1m:202610191530
hot:video:1m:202610191529
...
```

问题：

- 所有分钟桶权重相同，1 小时前的热度和刚发生的热度等价。
- 与简历里的“小时级滑动窗口 + 线性权重衰减”不一致。
- 桶数量多，合并和内存成本更高。

改造后：

- 24 个小时桶。
- 越新的小时权重越高。
- 读取时生成快照，保证翻页稳定。

---

## 2. 数据结构

写入：

```text
hot:video:1h:{yyyyMMddHH}   ZSET  member=videoID  score=popularity
TTL: 48 小时
```

读取快照：

```text
hot:video:merge:1h:{asOf}   ZSET  member=videoID  score=加权热度
TTL: 10 分钟
```

示例：

```text
asOf = 2026-10-19 15:00

hot:video:1h:2026101915  权重 24/24 = 1.000
hot:video:1h:2026101914  权重 23/24 ≈ 0.958
...
hot:video:1h:2026101816  权重 1/24  ≈ 0.042
```

## 3. 写入链路

点赞、评论等行为通过 `PopularityMQ` 异步更新热度：

```go
func UpdatePopularityCache(ctx context.Context, cache *rediscache.Client, id uint, change int64) {
    if cache == nil {
        return
    }

    now := time.Now().UTC().Truncate(time.Hour)
    windowKey := "hot:video:1h:" + now.Format("2006010215")
    member := strconv.FormatUint(uint64(id), 10)

    _ = cache.ZincrBy(ctx, windowKey, member, float64(change))
    _ = cache.Expire(ctx, windowKey, 48*time.Hour)
}
```

同时删除视频详情缓存：

```go
_ = cache.Del(context.Background(), fmt.Sprintf("video:detail:id=%d", id))
```

## 4. 读取链路

```text
ListByPopularity(asOf)
-> asOf 按小时截断
-> 生成最近 24 个小时桶 key
-> 生成线性衰减权重
-> ZUnionStoreWeighted 合并到快照
-> ZRevRange 按 offset 分页取视频 ID
-> GetByIDs 查详情
-> buildFeedVideos 补点赞状态
```

关键代码：

```go
asOf := time.Now().UTC().Truncate(time.Hour)
if reqAsOf > 0 {
    asOf = time.Unix(reqAsOf, 0).UTC().Truncate(time.Hour)
}

const windowHours = 24
keys := hotWindowKeys(asOf, windowHours)
weights := linearDecayWeights(windowHours)

dest := "hot:video:merge:1h:" + asOf.Format("2006010215")
exists, _ := f.rediscache.Exists(opCtx, dest)
if !exists {
    _ = f.rediscache.ZUnionStoreWeighted(opCtx, dest, keys, weights, "SUM")
    _ = f.rediscache.Expire(opCtx, dest, 10*time.Minute)
}
```

权重计算：

```go
func linearDecayWeights(hours int) []float64 {
    weights := make([]float64, hours)
    for i := 0; i < hours; i++ {
        weights[i] = float64(hours-i) / float64(hours)
    }
    return weights
}
```

## 5. 为什么需要快照

如果每次翻页都重新 `ZUnionStore`：

- 翻页期间热度变化，会导致数据重复或遗漏。
- 每次请求都做 24 个 ZSET 合并，成本高。

快照策略：

```text
第一次请求：生成快照，TTL 10 分钟
后续请求：直接读快照
10 分钟后：重新生成
```

客户端返回 `as_of`，翻页时带回，保证同一版本。

## 6. 数据库降级

Redis 不可用时：

```go
videos, err := f.repo.ListByPopularity(ctx, limit, latestPopularity, latestBefore, latestIDBefore)
```

数据库使用三字段游标：

```sql
WHERE (popularity < ?)
   OR (popularity = ? AND create_time < ?)
   OR (popularity = ? AND create_time = ? AND id < ?)
ORDER BY popularity DESC, create_time DESC, id DESC
LIMIT ?
```

三个字段保证热度相同、发布时间相同的情况下仍能稳定翻页。

---

## 7. 边界情况

| 场景 | 行为 |
|---|---|
| 当前小时没有数据 | 该小时桶为空，不影响其他桶 |
| 某个桶过期 | `ZUnionStore` 忽略不存在的 key |
| 快照已存在 | 直接读取，保证翻页稳定 |
| 快照过期 | 重新合并 |
| Redis 不可用 | 降级数据库三字段游标 |
| 视频被删除 | 按 ID 查询详情时丢弃 |
| 热度负增长 | `ZINCRBY` 支持负数，快照按最终分数排序 |
| 热度为 0 | 仍可能出现在榜单中，取决于数据量 |
| `as_of` 非法 | 使用当前时间 |

## 9. 后续优化

1. 热度衰减权重可配置，而不是固定 24 小时。
2. 增加定时任务预热快照，减少首次请求延迟。
3. 增加热榜缓存命中率和 ZUnionStore 耗时监控。
4. 对恶意刷热度增加行为风控。
